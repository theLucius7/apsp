# 当前开发数据库基线

本项目尚未正式发布。按用户确认及 [ADR 0122](adr/0122-unreleased-schema-baseline.md)，不维护旧 APSP 开发版本的数据库升级链；面板和 Agent 需要使用同一当前源码基线。历史验收记录中的升级与兼容承诺不适用于当前开发版本。

## 启动行为

- 面板仅有 `crates/panel/migrations/0001_current.sql`，直接创建当前表、约束、函数、索引和初始设置。空库在事务中初始化，并发启动串行执行初始化；失败完整回滚。
- 现有面板数据库必须只有这份基线的成功记录、相同 SQL 校验和及完整结构指纹。历史 0001–0091 记录、校验和不匹配、失败记录或结构变动均拒绝启动，不尝试修复或回填。
- Agent 仅有 `crates/agent-core/src/state/schema.sql`。空库初始化为 SQLite 版本 2，并记录应用标识、源码摘要和结构摘要；旧版本 1、未知库及缺表、缺索引等不完整结构均拒绝启动。拒绝检查在切换 WAL 和改文件权限之前执行，不重写账本。
  例外：已安装服务器上的状态库（Agent 0.3.7 及更早版本，版本 1、应用标识 0）结构与当前基线完全相同，只缺 `schema_identity`。新 Agent 首次打开时，若除这张表外的结构目录与当前基线逐条一致，就在同一事务里补建这张表并记录标识与版本，不改动任何其他表；有任何差异仍拒绝启动、不改文件。
- 重启当前基线不改业务数据，不重新发凭据，不重置流量或重复插入默认设置。调整基线 SQL 后，已有开发库需要手动重建。

## 旧开发环境如何处理

1. 停止对应开发面板和 Agent，核对数据库连接、Compose 项目和状态目录，确认它们不是生产环境或其他项目。
2. 先备份数据库、面板制品及私有环境文件；加密凭据的密钥环独立保管。备份工具按实际凭据表检查所需密钥，不再按历史迁移编号判断。旧备份仍须配合对应旧源码或镜像读取。
3. 为当前面板手动创建独立空 PostgreSQL 数据库，并更新开发环境的 `APSP_DATABASE_URL`。使用 Compose 时选择新的开发项目和私有环境文件，从而创建独立数据卷。不要修改 `_sqlx_migrations` 来绕过校验，不把旧表导入新基线冒充升级。
4. 对 Agent，归档旧状态目录并配置新的空状态目录，重新生成身份、登记服务器。旧设备凭据、序号和新面板记录不能混用；不要只删数据库却保留其余旧身份文件。
5. 启动当前源码构建的面板与 Agent，重新配置开发资源。验证后由操作者决定旧备份及旧开发卷的保留时间。程序和安装脚本均不会自动删除它们。

本次源码修改不操作已有服务、生产数据库或已发布制品，也不发布新的 Agent。已有安装不能直接覆盖部署当前开发基线。`panel.py upgrade` 仍会先备份；遇到旧库启动会失败，它不执行数据库自动升级或重建。

## 生产安装

生产面板随 main 自动部署（`apsp-deploy.timer` 每分钟检查 main，2026-11-07 核实仍在运行）。#249 合并时这里曾写着“用户确认当前没有自动部署”，与事实不符，当晚生产因此停机（见下文），已更正。生产是带真实数据的安装，不能按上面的开发库方式清空重建。2026-11-07 #245 直接部署后，生产库带着已退役迁移 1–90 的记录，面板拒绝启动（08:48–09:15），所有 Agent 连不上面板，旧面板随之把全部节点暂停展示，订阅返回 0 个节点；#246 暂时撤回后恢复。

随后由操作者执行一次性的原地接入 `scripts/baseline-adoption-20261107.sql`，程序本身仍然不做自动升级：

- 只接受迁移记录恰好是退役的 1–90（按版本与校验和的摘要核对）且尚无基线对象的数据库；
- 只补齐基线比第 90 号迁移多出的结构（阿里云账号与资源的新列、`alicloud_traffic_history`），定义逐字取自 `0001_current.sql`；
- 迁移记录改为与空库初始化完全相同的一条（版本 1、`current`、相同校验和），再写入结构指纹；
- 结构指纹必须等于空库初始化的结果，否则整个事务回滚。执行前先完整备份。

接入前在生产结构副本上验证过：当前面板镜像能在接入后的副本上启动，重复执行会被拒绝。业务数据不经导出导入，原样保留。

同日 #249 原地修改了基线（三处 `runtime_version` 检查加入 `1.14.4-apsp.1`、新增 `singbox_user_limits`），附带的接入脚本只在源码基线副本验证，合并前没有在生产执行，合并即被自动部署，部署后面板再次拒绝启动（19:16–19:35），订阅再次一度为空。按同样方法用 `scripts/baseline-adoption-20261107-pr249.sql` 从 #245 的基线接入 #249 的基线：先核对迁移记录与指纹恰好是 #245 的基线，再应用差异、更新校验和与指纹，指纹必须等于空库初始化 #249 的结果。

**以后修改 `0001_current.sql`：** main 合并后一分钟内自动部署。部署器（2026-11-07 起）在换镜像前，把新镜像放进隔离网络、用生产库的结构副本（只有表结构与基线记录）试启动；新镜像拒绝副本时，依次在副本上尝试该版本的 `scripts/baseline-adoption-*.sql`，直到能启动，再把同样的脚本按顺序在生产执行并换镜像。没有脚本能让它启动时部署被拦下，生产继续运行原版本，不会停机。所以修改基线的提交必须附带接入脚本，写法：

- 开头用 `DO` 块核对来源基线：`_sqlx_migrations` 只有一条、校验和等于当前部署的 `0001_current.sql` 的 SHA-384，且 `apsp_schema_baseline.fingerprint` 等于已部署的值；不符就 `RAISE EXCEPTION`，这样对其他数据库执行不会改动任何内容。
- 中间只应用差异，定义逐字取自新的基线文件。差异用 `schema_fingerprint.sql` 去掉 `md5` 后的定义集合，在生产库与空库初始化结果之间比对得到。
- 结尾更新校验和（新文件的 `sha384sum`），用 `schema_fingerprint.sql` 重算并写入指纹，再断言它等于空库初始化的结果，不等就报错回滚。空库结果要用新镜像对空的 PostgreSQL 16 库启动后读取 `apsp_schema_baseline`：sqlx 会先建 `_sqlx_migrations`，其主键索引也计入指纹，直接 `psql -f` 执行基线得到的值不同。
- 整个脚本由部署器以一个事务执行（`psql -1`）；可参照 `scripts/baseline-adoption-20261107-pr249.sql`。Agent 状态库：2026-11-07 逐台核对了全部 18 台服务器的状态库，结构目录都与 0.3.7 的结构一致（与当前基线只差 `schema_identity`），新 Agent 首次打开时按上面的例外记录为当前基线，不需要重新登记设备。以后再修改 `schema.sql`，发布新 Agent 之前同样要先为现有主机的状态库准备接入。

## 开发与恢复约定

未发布阶段修改当前基线，不继续追加历史增量迁移。面板基线是组装层的唯一结构定义，宿主负责通用校验；Agent 基线独立。新增业务默认值写入当前建表定义或初始设置，不能再在每次启动时执行 `ALTER TABLE`、兼容补表或改旧数据。

同基线备份恢复需要匹配源码和 PostgreSQL 主版本，并保留结构标识、业务数据、凭据密钥及制品。恢复到新的 PostgreSQL 主版本应先做隔离验证；结构指纹差异会拒绝启动，禁止手改指纹放行。

现有两跳、混合及有序链路、来源间显式转换、Nexus/Wallos 等外部导入仍是当前业务操作；它们不是旧 APSP 数据库升级入口。云接口、外部订阅格式及跨系统服务支持继续按各自功能约束执行。旧页面别名不再改写，收藏中的无效地址不再显示；Agent 取不到当前监控设置时保留本地样本，不回退旧面板上传方式。

## 稳定内核与逐用户限制的生产接入

#249 的基线增加 `singbox_user_limits` 并允许 `1.14.4-apsp.1` 运行时事实。生产库已于 2026-11-07 19:35 用 `scripts/baseline-adoption-20261107-pr249.sql` 接入（见上文“#249 原地修改了基线”一段）；#249 自带的接入脚本只在 PostgreSQL 18 的源码基线副本上验证过，没有在生产执行，已删除，以免误用。

新内核要随签名发布生效：发布前，生产上的服务器仍运行原内核。

从 S-UI 的基线（`405612a7`，指纹 `7701ab9e`）接入 [ADR 0131](adr/0131-one-model-per-object.md) 的基线使用 `scripts/baseline-adoption-one-model-20261109.sql`：删除两跳旧链路、混合链路与数字编号来源的 17 张表、`singbox_live_chains` 视图、7 个函数及其触发器；两个外部节点视图与两个检查函数只读 B 模型，B 的两个公开编号序列先改归 B 表再改名；`singbox_chains` 与 `singbox_ordered_chain_versions` 在生产是空表，按新定义重建（删列会留下空的列序号，指纹不可能等于空库初始化），连同引用它们的 8 个外键与 `singbox_desired_accesses` 视图。脚本校验来源校验和与指纹、两张链路表为空，结果指纹必须等于空库初始化的值（`00168f4f`）。删除前，数字编号来源的存档行从生产备份导出到 `~/backups/apsp-numbered-sources-archive-20261109/`。

### 旧商务表删除（2026-11-10）

从 ADR 0131 的基线（`838b323f`，指纹 `00168f4f`）接入删除旧商务表的基线（`a1c4b16e`，指纹 `bd3c95e0`）使用 `scripts/baseline-adoption-commerce-20261110.sql`：删除 Nexus 迁移带来、自 2026-11-05（ADR 0113）起已无代码读写的九张表——`singbox_commerce_invitations`、`singbox_commerce_offers`、`singbox_commerce_orders`、`singbox_commerce_settings`、`singbox_payment_exceptions`、`singbox_payment_receipts`、`singbox_payment_topups`、`singbox_wallet_ledger`、`singbox_nexus_records`，连同它们的序列、约束与索引。删除前的行（钱包流水 51、Nexus 记录 4778、订单 1、报价 4、邀请 1、设置 1，其余 3 张为空）已导出到服务器上的受保护存档（目录 700、文件 600，附 SHA256SUMS），不进仓库。脚本校验来源校验和与实际结构指纹，删除不带 CASCADE（有任何依赖就失败），结束时校验结果指纹并更新基线记录；`singbox_commerce_events`（成员账号的内容审计仍在写）与 `singbox_payment_channels`（恢复脚本会停用）不在其内。部署器在合并后先在生产结构副本上试启动并执行它，再在生产执行。

### 会话分表与审计合并（2026-11-14）

从删除旧商务表的基线（`a1c4b16e`，指纹 `bd3c95e0`）接入阶段 F 第一步的基线（`f9a10013`，指纹 `5c70bc13`）使用 `scripts/baseline-adoption-phasef1-20261114.sql`：

- 结构指纹按列在未删除列中的位置计（`row_number() OVER (PARTITION BY attrelid ORDER BY attnum)`），不再用 `attnum`。删除非末尾的列会留下空号，生产库因此永远对不上空库初始化，部署器的 `pg_dump` 结构副本又会重排列号；改后三者一致，以后的基线变更可以删列。`schema_fingerprint.sql` 与基线末尾的内嵌副本同改，历史接入脚本不动；本脚本核对来源时仍按旧算法。
- 设备会话移到资源领域的新表 `device_sessions`（按服务器、按到期时间各一个索引），过期的由资源在维护周期里删除；`sessions` 只留管理员会话，删去 `server_id` 及其检查约束、索引与外键，`admin_id` 改为非空。
- `singbox_commerce_events` 并入 `singbox_operation_events` 后删除：`admin:N`、`administrator:N` 记为管理员编号，其余主体与对象编号写进 `detail`；成员本人的账号事件改用 `security_portal_*`（密码登录即 `security_portal_login`，`authentication` 为 `password`），其余动作名不变。并入后这些记录按隐私设置的保留期清理。

执行时旧面板仍在运行，之后也不回滚，所以复制、转换与删除都在一个事务里：先锁 `servers`、`users`、`sessions` 与两张事件表（删外键本来就要 `servers`、`users` 的排他锁，一次拿齐，不中途升级），结束时核对搬动的行数和结果指纹，再更新基线记录；重复执行会被来源核对拒绝。演练：旧基线空库加合成数据、生产结构副本、生产数据副本（隔离网络，用后删除）都通过，数据副本上 19 个设备会话与 4 个管理员会话分开，202 条商务事件全部并入（操作事件 792 → 994），整个事务约 0.14 秒。
