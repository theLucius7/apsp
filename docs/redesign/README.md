## 结论

上一版方案解决的是“维护者找文件、读文档、跑工具的成本高”。这个问题真实存在，但不是全部：即使按它的目录树搬完，节点、来源、用户、授权与部署仍然保持现在的理解成本。

本方案把重新设计分成三个相互衔接的部分，**先定功能归属、核心对象、操作流程与发布条件，再按新的职责边界决定哪些文件值得移动**：

| 部分 | 文档 | 回答的问题 |
| --- | --- | --- |
| 依据 | [设计依据](01-principles.md) | 用哪些理论和项目原则做判断？得到 R1–R18 十八条规则 |
| 一、产品与业务 | [功能盘点与新归属](02-inventory.md) | 每项功能放在哪里，为什么？ |
| | [核心对象词典](03-objects.md) | 服务器、运行时、节点、链路、来源、用户、策略、用量规则分别是什么？ |
| | [六工作区方案](04-workspaces.md) | 全局页面、对象详情和系统设置怎样分工？ |
| | [三条主线流程](05-flows.md) | 接入并发布服务、授权用户、排查故障怎样连续完成？ |
| | [状态设计](06-states.md) | 保存、下发、应用、验证、失败分别如何表达？ |

| 三、工程整理 | [工程整理子方案](08-engineering.md) | 文档、工具、测试、前端与模块说明怎样整理？上一版方案的哪些判断要纠正？ |
| 执行 | [执行计划](09-execution.md) | 按什么顺序做，每步的完成标准是什么？现行规范有哪些冲突要先解决？ |

一级结构采用六个工作区：**概览 / 服务器 / 网络服务 / 监测与诊断 / 费用与续费 / 系统**。服务器详情只是关联对象的筛选视图；代理用户继续归 sing-box 业务域。

### 扫描的主要发现

1. **功能大多有清楚的对象，混乱主要来自位置与用语。** “订阅”在界面与代码中有五种含义；线路质量分在四处；侧栏实际是 5 组，文档分别写四组和六组（[功能盘点](02-inventory.md#1-盘点结论)）。
2. **历史模型仍在日常路径上。** 三代链路、两套来源与 Nexus 兼容桥还会出现在新建与日常界面中；兼容桥没有独立模块，10 个源文件直接查询它（[收敛方案 §3](07-convergence.md#3-兼容流程独立)）。
3. **状态回答不了“改动生效了没有”。** 没有“已下发”这一步；旧设备的“已应用”没有回执；超时被记成失败；“健康”有两个意思（[状态设计 §1](06-states.md#1-问题)）。
4. **发布缺少候选版本身份。** 运行时版本写在三个数据库约束里，每次升级内核都是一次基线变更（#249 的停机就是这样发生的）；面板不核对内核制品是否已导入，#249 部署后到签名发布导入前，所有服务器的新配置都无法下发；门禁定义在仓库外；面板报告的版本号不随提交变化；结构指纹的期望值没有编译进程序（[收敛方案 §5](07-convergence.md#5-候选版本身份与发布门禁)）。
5. **上一版方案的四处源码判断需要纠正**，另外发现：目录移动会让分层检查静默地少查；`tools/` 中有一批文件随安装器分发到每台服务器（[工程整理 §2](08-engineering.md#2-对上一版方案的源码纠正)）。
6. **测试有执行缺口。** 前端单元测试与浏览器回归都不在 CI 中；日常运维工具与设备侧恢复脚本的测试从未进入 CI；一项只需要 PostgreSQL 的测试被标为忽略（[工程整理 §6](08-engineering.md#6-测试入口与发现规则)）。
7. **现行规范有 23 处冲突**，其中七项需要用户决定（[执行计划 §3–§4](09-execution.md#3-当前规范冲突清单)）。

## 与 ADR 0125 的关系

2026-11-08 的 [ADR 0128](../adr/0128-domain-architecture.md) 取代了 ADR 0125 的模块清单与登记口，改为九个领域与平台、领域、应用三层。对照：`proxy` → 流量服务与服务权益（`legacy` 子模块成为两个领域内的兼容模块）；`dns` → 名称与证书；`cloud` → 按对象分回资源、基础网络、成本、作业与观测，云接口的技术实现归平台；`costs` → 成本；`alerts`、`lines` → 观测；`overview` → 观测与应用层的组合页面；`lab` → 回到所属领域，成熟度单独标记；内核 → 平台、平台治理与资源。逐项功能见[领域归属表](../domain-map.md)。下面保留当时与 ADR 0125 的对齐记录。

同一天合入 main 的 [ADR 0125](../adr/0125-feature-modules.md) 是**现行规则**，回答代码、数据与上游归谁：内核只提供身份、设备、平台服务三块机制；`proxy`（分 nodes、users、delivery、portal、runtime、legacy 六个子模块）、`dns`、`cloud`、`costs`、`alerts`、`lines`、`overview`、`lab` 八个功能模块；每张表一个所有者；上游代码归功能的 `upstream/`；分八个阶段迁移，由 `tools/check-feature-boundaries.py` 守护。

本方案是**提议**，回答它没有覆盖的部分：工作区与入口、对象的统一语言、主线流程、状态表达、模型收敛、发布门禁与恢复，以及文档、工具与测试的整理。两者的关系：

| 方面 | 处理 |
| --- | --- |
| 代码与数据的领域 | 采用 ADR 0125 的功能模块作为 R2 所说的“稳定领域”；对象词典的上下文、写入权与它一致（[对象词典 §2、§4](03-objects.md#2-五个界限上下文)） |
| “与侧栏一一对应” | 按**入口级**理解：每个入口只属于一个功能模块；工作区（侧栏分组）由几个功能的入口组成，分组写在各功能的清单里，调整分组不搬目录（[工程整理 §7.1](08-engineering.md#71-入口属于功能工作区只是分组)） |
| `lab` 模块 | 它的叶子规则（核心功能不依赖实验功能）与 R6 一致；模块名表达了级别，其中一项转正时按 R18 评估改名或归入所属功能，不因级别变化来回搬代码（[工程整理 §10](08-engineering.md#10-暂缓与不做)） |
| 迁移顺序 | 执行计划的步骤 3、5 落在迁移阶段中（ADR 0128 起为阶段 B–F），本方案补充每步的完成标准；步骤 2（发布衔接）是新增工作（[执行计划 §6](09-execution.md#6-与路线图和-adr-0128-的关系)） |
| 本方案提议改变 ADR 0125 或 architecture.md 现有表述的地方 | 侧栏按六工作区重组（ADR 0125 把分组交给功能地图，模块不变）；界面入口「插件中心」改名「制品与版本」（architecture.md §9 暂时保留原名）；旧地址中已发给代理用户的部分恢复改写（回答 architecture.md §10 的待决定事项）。三项都在[需要用户确认](#需要用户确认)之列 |

## 执行顺序

| 顺序 | 工作 | 完成标准 |
| --- | --- | --- |
| 1 | 校正方案与当前规范：修正源码误判，整理有效规则、术语和功能归属 | 后续开发能依据一套一致的当前说明 |
| 2 | 补齐发布衔接：固定候选版本身份、数据库兼容检查、恢复条件 | 不兼容变更在替换服务前被识别 |
| 3 | 收敛核心模型：节点、链路、来源、用户的新建使用统一路径；兼容流程独立 | 全新使用流程不需要理解历史模型 |
| 4 | 完成工作区与操作流程：六工作区、对象视图、配置发布、授权与诊断流程 | 用户能完成真实任务，并理解当前状态 |
| 5 | 按新职责局部整理代码：按 ADR 0125 的阶段归位代码与数据，并整理文档、工具与测试 | 每一次移动都有明确收益，执行与数据契约保持 |
| 6 | 评估 ADR 0125 未决定的拆分：测试支持库、分片基线的合成与校验、旅程测试的位置 | 根据实际依赖和维护收益决定 |

不依赖业务决定的小型目录整理可以与前几步并行；代码与数据的迁移按 ADR 0125 的阶段进行，本方案不另提整套路径迁移。每一步的输入、产出、验收与风险见[执行计划](09-execution.md)。

## 需要用户确认

方案中的选择以“最简单且符合既定架构”为准；下面几项涉及产品方向或不可逆操作，落实前需要用户确认，详见[执行计划 §4](09-execution.md#4-需要用户确认的事项)：

1. 六工作区与入口名称（「网络服务」「地址与域名」「云资源」「外部来源」「付费服务」「制品与版本」），包括统计报表与服务器看板的显示位置；代码所有者按 ADR 0125 不变。
2. 地址策略：已发给用户的链接永不失效，因此恢复门户、邮箱登录与邀请的旧地址改写；控制台地址改写保留至少一个发布版本。
3. 现行交付规则：直接提交 main、集成分支一次交付、每个工作包一个 PR 三条规则同时存在，需要确定一条。
4. 链路与来源统一后，旧模型的删除时间点（需要生产迁移与实机验收，按仓库规则单独授权）。
5. 候选版本清单与部署门禁的落地方式（影响生产自动部署；建议先只记录、不拦截）。
6. 英文界面与“界面只使用中文”的矛盾怎样处理。
7. 2026-10-01 的执行节奏（中途不测试、大步骤完成后集中验证）是否仍然有效。
