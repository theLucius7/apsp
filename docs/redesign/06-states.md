# 状态设计：保存、下发、应用、验证、失败

- 状态：提议（2026-11-07）。
- 依据：[设计依据](01-principles.md) R4、R11、R12；[ADR 0001](../adr/0001-declarative-snapshots.md) 期望状态与观察状态分开，[ADR 0007](../adr/0007-intent-journal.md) 意图日志，[ADR 0064](../adr/0064-runtime-checkpoints-and-recovery-barriers.md) 运行时检查点与恢复边界；Kubernetes 的 spec / status 约定（[设计依据 §3.8](01-principles.md#38-期望状态控制器的状态约定)）。
- 范围：所有会下发到服务器或外部提供方的对象（运行时配置、节点、链路、用户凭据、Agent 设置），以及异步操作（远程命令、批量操作、诊断、来源刷新、DNS 同步、证书签发、云操作）。

## 1. 问题

管理员改了一个节点，界面需要回答四个问题：面板记下了吗？服务器取到了吗？应用了吗？真的能用吗？扫描（main `a32ec49b`）发现现在回答不了：

- **没有“已下发”这一步。** 发布后面板只发一条尽力而为的通知（设备离线时丢弃），Agent 每 60 秒拉取一次清单；应用结果同样尽力发送，不进出盒。“等待设备应用”可能是没取到、正在应用或结果丢了，而且永远不会变成“未知”。唯一的兜底是 300 秒后产生一条严重级别的故障事件“未健康或目标配置未应用”，它把“超时”与“不健康”混在一起，而且位于实验的故障事件模块（`crates/panel-host/src/operations/incidents.rs`）。
- **“已应用”可以没有回执。** 对不支持检查点的旧设备，面板根据心跳中的修订号补记“已应用”和“健康”，而心跳不带健康信息（`crates/panel-host/src/agent_api.rs` 的 `reconcile_hint`）。发布新目标时也不重置健康，所以“已生效”“当前配置健康”可能在新修订应用之前就出现。
- **“健康”有两个意思。** 旧设备上是“正在运行的配置健康”；支持检查点的设备上是“目标修订通过了检查点”，每次重连和每次应用都重置为否。结果是支持检查点的设备在等待核对时被显示为红色的“健康检查未通过”。
- **未知有两个词，人工结束有五种写法，超时被记成失败。** `unknown` 与 `uncertain` 并存；人工核对后分别记为 `reconciled`、`dismissed`、`failed` 加原始结果等；诊断超时、路径探测过期、DNS 请求超时、TLS 握手超时、运维步骤过期都被记为失败。
- **同一件事说法不一。** “等待设备”有六种说法；两套链路引擎对同一步用不同的词；部分状态没有中文标签，终端会话直接显示英文状态码。

## 2. 四个阶段与两种异常

### 2.1 定义

每个下发对象的状态由**期望**与**观察**组成。观察按证据强弱分为四个前进的阶段，加上两种使前进停止的异常：

| | 含义 | 写入者 | 依据 | 界面写法 |
| --- | --- | --- | --- | --- |
| **已保存** | 面板记下了新的期望（新的设置修订） | 面板接口 | 对象修订号与保存时间 | 已保存 · 管理员，2 分钟前 · 等待生成配置 |
| **已下发** | 期望已编译为目标修订，**设备已取走**（外部提供方：已接受请求） | 发布器；面板在设备拉取清单时记录 | 目标修订、取走时间 | 已下发 · 设备 10:02 取走修订 42 |
| **已应用** | 设备报告目标修订已应用 | Agent 的应用结果（带操作回执） | 回执与时间 | 已应用 · 设备回执 10:02 · 修订 42 |
| **已验证** | 独立的观察证明结果在工作 | 检查点、路径探测、TLS 握手、解析器观测、云接口读回 | 观察结果与时间；有有效期 | 已验证 · 检查点 10:03 · 5 分钟内有效 |
| **失败** | 收到明确的失败报告 | 设备、提供方或面板校验 | 原因；失败后实际在运行什么 | 失败 · 设备报告“端口被占用” · 仍在运行修订 41 · 查看日志 · 重试 |
| **未知** | 超过时限没有明确结果（超时、结果丢失、执行中断） | 面板按时限判断 | 最后一次已知状态与时限 | 未知 · 10:05 后没有收到结果 · 核对 |

### 2.2 规则

1. **阶段属于修订。** 每个阶段描述的是某一个目标修订。保存新修订后，新修订从“已保存”开始，旧修订的运行情况单独显示（“仍在运行修订 41”），不会让新修订继承旧修订的“已应用”或“已验证”。
2. **只有回执才算已应用。** 心跳中的修订号只更新“观察到的运行修订”。旧设备没有回执时显示“已应用（无回执）”并标“兼容”，永远不算已验证；这个分支随旧 Agent 兼容退出（[收敛方案 §3](07-convergence.md#3-兼容流程独立)）。
3. **运行正常与已验证分开。** “运行正常”是运行时进程与健康检查的结论，针对当前正在运行的修订；“已验证”针对目标修订，并且会过期。界面不再使用单独的“健康”一词。
4. **超时是未知，不是失败。** 超过时限只能说明“没有收到结果”。需要保守处理的动作（例如路径探测超时后不切换候选路径）照常保守执行，但状态写“未知：验证超时”。迟到的结果仍然接受并更新状态，注明“迟到”。
5. **失败分两种。** **未执行**：在执行前被拒绝或前置条件不满足，没有产生任何变更（例如阿里云操作的预检失败）；**执行失败**：执行了但没有达到目标，可能有部分变更，必须写明失败后的实际状态。
6. **未知必须被核对。** 核对由管理员完成，统一记为“已核对”，写明核对人、时间与结论（实际成功、实际失败、放弃跟踪）。
7. **边缘自治照常成立。** 任何阶段的失败或未知都不影响服务器上已应用的配置继续运行；界面始终同时显示“正在运行什么”。
8. **离线是一个独立条件。** 设备离线时显示“离线 · 最后已应用修订 41（10:02）”，期望与观察的其余部分照常显示。

### 2.3 每类对象的依据

| 对象 | 已下发的依据 | 已应用的依据 | 已验证的依据 |
| --- | --- | --- | --- |
| 运行时配置（含节点、用户凭据） | 设备拉取清单时取走的修订（新增记录，不改协议） | 应用结果回执 | 运行时检查点：实际配置文件与进程一致（`runtime_module_checkpoints`，5 分钟有效） |
| 链路 | 各段所在服务器的配置均已下发 | 各段均已应用 | 路径探测：经完整路径访问面板的 `/healthz` 成功（`singbox_path_probes`）；恢复边界已固定 |
| Agent 设置、遥测设置 | 设备取走设置的时间 | 设备回报采用的设置修订 | 无（不需要） |
| DNS 记录 | 提供方接受请求 | 提供方确认 | 解析器观测到期望值（传播另行检查） |
| 证书部署 | 设备已领取 | 执行完成回执 | TLS 握手验证 |
| 云操作 | 官方接口接受请求 | 官方接口读回一致 | 同左（读回即验证） |

## 3. 表达方式

### 3.1 一个状态组件

所有位置使用同一个状态组件：**阶段徽标 + 依据（谁报告）+ 时间 + 下一步**。失败与未知必须带下一步（查看日志、重试、核对、前往对象的家）。悬停或展开时显示四个阶段各自的依据与时间。

颜色按证据强弱，而不是按阶段名：

| 状态 | 色调 |
| --- | --- |
| 已保存、已下发、执行中 | 中性 |
| 已应用 | 中性偏正（有回执，未验证） |
| 已验证 | 正向 |
| 未知、验证已过期、长时间未应用 | 警示 |
| 失败 | 危险 |
| 已核对、已取消、未执行 | 中性，附结论 |

现有漂移视图的颜色是倒置的：较弱的证据（修订一致）显示为正向，较强的证据（配置已核对）显示为警示（`OperationsWorkflows.tsx` 的 `driftNames`），按上表改正。

### 3.2 统一用语

| 统一用语 | 用于 | 替换现有的 |
| --- | --- | --- |
| 已保存 / 等待生成配置 | 面板记下期望，目标修订尚未生成 | 目标配置待发布、等待发布 |
| 已下发 / 等待设备取走 | 目标修订已生成；设备是否已取走 | 已派发、已交付设备、已排队，等待面板分发、等待设备应用（未取走时） |
| 已应用 | 有回执 | 目标配置已应用、已生效、apsp 已接管、路径已应用 |
| 已验证 | 有独立观察 | 实际配置与进程已核对、指定目标验证成功、设备健康与实际运行时已确认 |
| 运行正常 / 运行异常 | 当前运行的修订的健康 | 当前配置健康、健康检查未通过 |
| 未执行 | 执行前被拒绝，没有变更 | 部分位置的“失败”“未开始”“执行前失败” |
| 执行失败 | 执行了但未达到目标 | 应用失败、路径操作失败、执行失败、同步失败 |
| 未知 | 超过时限没有结果 | 结果未知、结果待核对、需要人工核对、执行结果未知，需要核对、官方请求结果未知、结果未知，先核对远端 |
| 已核对 | 人工结束一个未知结果 | 已人工核对结束、已人工结束跟踪 |
| 排队中 / 设备已领取 / 执行中 / 取消中 / 已取消 | 异步操作的过程 | 等待领取、等待设备领取、设备已领取，等待执行结果、等待设备确认取消 |

存储值不为此改名（改约束是基线变更，R15、R18）：界面与接口文案按上表映射；新代码只写 `unknown`，不再引入 `uncertain`。

### 3.3 异步操作

远程命令、批量操作、诊断、来源刷新、DNS 同步、证书签发与云操作使用同一条生命周期：

> 排队中 → 设备已领取（或提供方已接受）→ 执行中 → 成功 / 未执行 / 执行失败 / 未知 / 已取消；未知 → 已核对

- 取消在设备确认前显示“取消中”，确认后才是“已取消”（ADR 0026、0044 的现有规则）。
- “成功”写明依据：设备报告、官方接口读回、握手另验。
- 只有面板侧的过程（如来源刷新）同样适用，“设备已领取”一步省略。

### 3.4 对象自身的状态

下发阶段之外，对象还有自己的生命周期状态，它们与下发阶段并列显示，不混入同一个枚举：

| 对象 | 状态 |
| --- | --- |
| 服务器 | 在线、离线；退役中、已退役、退役未确认 |
| 运行时 | 未安装、已安排安装、等待设备、运行中、安装失败 |
| 用户 | 资格：正常、不限量、未开始、已到期、已用尽、已暂停、已归档、待激活；兼容桥用户另有无套餐、待迁入（标“兼容”） |
| 外部来源 | 最近一次刷新：成功、内容未变、失败（保留上一个成功修订）、已取消、已被新设置取代 |
| 链路 | 准备、验证候选、切换、固定恢复边界、退出旧版本、已应用、恢复、失败、已退役（有序链路 13 个内部阶段归并为这些用语） |

## 4. 配置下发的汇总视图

网络服务首页回答“各服务器上的配置是否都是最新、都在工作”（[六工作区方案 §7](04-workspaces.md#7-网络服务内的结构)）。

**顶部计数**（点击即筛选）：已验证、已应用未验证、等待设备取走（含离线）、长时间未应用、执行失败、未知。

**每台服务器一行：**

| 列 | 内容 |
| --- | --- |
| 服务器 | 名称、在线或离线 |
| 运行时 | 内核版本、运行正常或异常 |
| 目标修订 | 修订号与生成时间 |
| 阶段 | 状态组件：已下发 / 已应用 / 已验证，或失败、未知 |
| 正在运行 | 当前运行的修订；与目标不同时突出显示 |
| 最近失败 | 原因与时间，链接到部署历史 |
| 等待时长 | 从已下发起算 |

**规则：**

- 默认按“需要处理”排序：失败、未知、长时间未应用、离线且有待下发，然后才是其余。
- **长时间未应用**：已下发超过时限（沿用 300 秒）仍无回执，显示为未知并产生一条**警告**；“运行时运行异常”另产生**严重**告警。两者不再合成一条。这条判断从实验的故障事件模块移到网络服务（核心旅程不依赖实验功能；ADR 0125 §5.2 第 4 条：实验功能是叶子）。
- 节点详情、链路详情、用户详情显示同一组件，范围是对象所涉及的服务器：节点是一台，链路是各段所在的服务器，用户是其凭据所在的全部服务器。
- 概览只显示失败、未知、长时间未应用三项的数量并链接到这里。

## 6. 验收

1. 每类下发对象的界面都能分别回答“记下了吗、取走了吗、应用了吗、验证了吗”，并各带依据与时间。
2. 没有任何超时被显示为失败；没有任何心跳推断被显示为已验证。
3. 所有存储的状态值都有统一用语中的标签，由自动检查保证。
4. 在测试环境中分别制造设备离线、应用失败、结果丢失三种情况，汇总视图的计数、每行状态与告警级别都符合 §4。
5. [流程 C](05-flows.md#4-流程-c排查故障)的每一步都能从状态组件得到判断依据，不需要读日志或数据库。
