## 1. 要解决的问题

扫描（2026-11-07，main `d24bd135`）与用户反馈归纳为四类问题。

| 问题 | 表现 | 后果 |
| --- | --- | --- |
| 功能划分不清 | 同一领域分散在多处：线路质量分在“线路检测”“服务器详情 › 线路诊断”“实验功能 › 网络配置”。同一个“订阅”至少指三件事：用户的订阅链接、作为节点来源的订阅来源、管理员付费的订阅服务。 | 用户找不到功能，也说不清它属于哪里 |
| 一个对象有几代模型 | 链路有 `legacy`、`mixed`、`ordered` 三种；订阅来源有数字编号与 UUID 两套；还有 Nexus 导入的节点与权限组。 | 新建、编辑、编译都要理解历史，复杂度随时间累积 |
| 规则互相矛盾 | 侧栏分组数在 AGENTS.md、功能地图、代码注释中各不相同；“旧地址永久可用”与“清理旧页面地址”同时有效。 | 每个会话都要重新判断哪条规则生效 |
| 状态表达不一 | “已保存”“已派发”“目标配置已应用”“应用状态待确认”“安装完成”分属不同功能，判断依据各不相同。 | 用户不知道改动是否已在服务器上生效 |

本方案的判断标准只有两条：

1. 后续开发能依据**一套一致的当前说明**。
2. 全新的使用流程**不需要理解历史模型**。

## 3. 软件工程理论

### 3.1 概念完整性与本质复杂度

Brooks 在《人月神话》（1975）里把**概念完整性**称为系统设计中最重要的考虑：一个系统应当反映一组一致的设计理念，而不是许多好主意的拼接。《没有银弹》（1986）区分了问题本身带来的**本质复杂度**和由做法带来的**偶然复杂度**。

在 apsp：项目由一个人维护、多个 AI 会话并行开发，没有“一个人的头脑”来保证一致，书面的对象词典和规则就是概念完整性的载体。三代链路模型、两套来源、Nexus 兼容层都是偶然复杂度：它们来自演进过程，不来自用户的问题，应当隔离并有退出条件。

### 3.2 按“可能变化的决定”划分模块

Parnas 在《关于把系统分解为模块的准则》（CACM，1972）里比较了两种分解：按处理步骤分，和按**可能变化的设计决定**分（信息隐藏）。后者在需求变化时只需改一个模块。Ousterhout 在《软件设计的哲学》（2018）里把复杂度归结为**依赖与晦涩**，主张“深模块”：接口简单，内部承担复杂度；并主张**把复杂度往下压**，由实现吸收，而不是推给使用者。

在 apsp：

- **侧栏是易变决定。** 2026-10-03 到 11-06 的五周里导航调整了五次（ADR 0084、0086、0098、0102 改分组与入口，0120 改地址）。代码目录若跟着侧栏走，每次导航调整都要搬家；按稳定的领域组织代码，导航只组合页面。
- **运行时内核版本是易变决定。** 它本应藏在运行时制品与适配器之后，现在却写进了数据库 `CHECK` 约束，见[收敛方案](07-convergence.md#4-运行时版本与数据库结构解耦)。
- **外部订阅格式是易变决定。** 它应当藏在唯一的解析器之后，现在 A、B 两套来源各有一份。

### 3.3 内聚、耦合与包原则

Constantine 与 Yourdon（《结构化设计》，1979）提出用内聚和耦合衡量模块。Martin（《敏捷软件开发：原则、模式与实践》，2002）给出包的原则：

- **共同封闭**（CCP）：一起变化的东西放在一起。
- **共同复用**（CRP）：不一起使用的东西不要放在一起。
- **无环依赖**（ADP）：依赖图中没有环。
- **稳定依赖与稳定抽象**（SDP、SAP）：依赖指向更稳定的模块，越稳定的模块越抽象。

在 apsp：

- `protocol`、`adapter-sdk` 是稳定而抽象的契约，适合称为“公共契约”。
- `compiler` 承载代理用户凭据、节点、链路、协议与 TLS 的配置语义，属于代理服务领域。“被多处调用”不是放进通用 `shared/` 的理由（CRP）。
- 插件之间互不依赖（ADP），已由 ADR 0085 与分层检查保证，继续保留。

### 3.4 领域驱动设计

Evans 的《领域驱动设计》（2003）与 Vernon 的《实现领域驱动设计》（2013）提供了几个直接可用的工具：

| 概念 | 含义 | 在 apsp |
| --- | --- | --- |
| 统一语言 | 领域专家与开发者用同一组词，词义在一个上下文内唯一 | [对象词典](03-objects.md)就是统一语言；界面、文档、API、代码注释都用它 |
| 界限上下文 | 一个模型有效的边界；跨边界的同名词可以不同义，但必须显式翻译 | 服务器、网络服务、监测与诊断、费用与续费、系统五个上下文，见[对象词典](03-objects.md#2-五个界限上下文) |
| 聚合 | 必须一起保持一致的对象群，只通过根对象修改 | 链路（含各段）、代理用户（含凭据）、订阅来源（含版本）都是聚合；写入经各自的根对象和修订号 |
| 上下文映射 | 上下文之间的关系：上下游、遵奉者、防腐层等 | Nexus、Xboard、Wallos、CDT 脚本、机场订阅都是外部上下文，经**防腐层**翻译进来 |

“每项功能自己维护”在 DDD 里就是：apsp 不做上游的遵奉者，而是在自己的界限上下文里建模，上游只在防腐层出现。

### 3.5 认知负荷与组织结构

Conway（《委员会如何发明》，1968）观察到系统结构会复制组织的沟通结构。Skelton 与 Pais（《团队拓扑》，2019）把**认知负荷**作为划分边界的首要依据：一个团队能承担的领域有限。

在 apsp：“组织”是一个维护者加多个并行的 AI 会话。每个会话只读得下一部分仓库，所以边界的价值在于**单独读一个领域就能工作**：领域有自己的说明（模块 README），依赖方向明确，规则只有一个现行出处。这也是[工程整理](08-engineering.md)中模块说明与能力清单的理由。

### 3.6 演进式迁移

这一组模式用于在不停机、不一次性重写的前提下替换模型：

- **绞杀者**（Fowler，2004）：新模型逐步接管旧模型的入口，旧模型的使用面缩小到零后删除。
- **并行修改 / 扩展—收缩**（Sato，2014；Ambler 与 Sadalage《数据库重构》，2006）：先扩展出新结构并双写或转换，再迁移使用方，最后收缩删除旧结构。
- **按抽象分支**（Hammant，2007）：在稳定接口后面替换实现。

在 apsp：链路与来源的统一已经按这个思路设计（阶段三迁移方案），代码准备已经完成，缺的是“新建只走新模型”和“旧模型有明确的退出条件”。[收敛方案](07-convergence.md)沿用这条路线，不推翻重来。

### 3.7 发布工程

Humble 与 Farley（《持续交付》，2010）提出：**只构建一次**，测试、验收与上线用同一份产物；部署流水线是进入生产的唯一路径；每个候选版本带着它通过的检查记录。Google SRE（2016）的发布工程一章强调可重现构建、版本身份和**回退是一等操作**。

在 apsp：main 每分钟自动部署到生产。#245、#249 两次停机都源于同一缺口：候选版本缺少与数据库、Agent、运行时一起核对的身份，不兼容只能在替换服务之后才被发现。[收敛方案](07-convergence.md#5-候选版本身份与发布门禁)把“候选版本”定义为一组身份的绑定，并把兼容检查放到替换服务之前。

### 3.8 期望状态控制器的状态约定

Kubernetes 的 API 约定把每个对象分成 `spec`（期望）与 `status`（观察），用 `observedGeneration` 表示控制器已处理到哪一版期望，用带原因、时间的 `conditions` 表达多个正交的状态，而不是一个混合的枚举。apsp 的 `target_rev` / `applied_rev` 已经是同一思路。[状态设计](06-states.md)把它推广到所有会下发到服务器的对象。

### 3.9 文档与决策记录

- **决策记录有状态**（Nygard，《记录架构决策》，2011）：提议、接受、弃用、被取代。apsp 的 ADR 已有部分状态，但替代关系没有反映到索引和协作规则。
- **文档按用途分类**（Procida，Diátaxis）：教程、操作指南、参考、解释四类，读者不同、写法不同。
- **架构按层次描述**（Brown，C4 模型）：系统上下文、容器、组件逐层展开。模块 README 对应组件这一层。

在 apsp：“当前规则、使用文档、开发参考、历史记录”的区分，先判断**有效性**再决定位置，见[工程整理](08-engineering.md#3-文档按有效性整理)。

### 3.10 开关的分类

Hodgson（《功能开关》，2017）把开关分成发布开关、运维开关、权限开关和实验开关，它们的生命周期和持有者不同，混在一起会失控。

在 apsp：“实验”“冻结”描述的是**投入与展示**（产品生命周期），不是代码边界或编译开关。维护级别应当作为元数据记录在能力清单里，决定是否显示、是否允许新增能力；它不决定代码放在哪个目录，也不应直接关闭编译，否则已有对象、进行中的任务和恢复能力会受影响。

## 4. 交互哲学

### 4.1 概念模型与两道鸿沟

Norman 在《设计心理学》（修订版，2013）里区分了设计者的概念模型、系统映像与用户的心理模型：用户只能从系统映像（界面）推断系统如何工作。**执行鸿沟**是“我想做的事，界面上怎么做”；**评估鸿沟**是“我做了之后，系统现在是什么状态”。

在 apsp：评估鸿沟是最大的问题。管理员保存了一个节点，界面需要回答：面板记下了吗？已经发给服务器了吗？服务器应用了吗？客户端真的能连吗？这正是[状态设计](06-states.md)五个阶段的来源。

### 4.2 可用性启发式

Nielsen 的十条可用性启发式（1994）中，与 apsp 关系最大的六条：

| 启发式 | 在 apsp |
| --- | --- |
| 系统状态可见 | 每个会下发的对象显示阶段、依据与时间（R4、R11） |
| 贴近用户的语言 | 对象词典消除“订阅”“套餐”“插件”的多义（R3） |
| 一致与标准 | 所有异步过程用同一套状态词和同一个状态组件 |
| 防错 | 不可用的选项不提供，禁用时说明原因；危险操作写明对象与后果（R12） |
| 识别而非回忆 | 对象详情直接列出关联对象，用户不需要记住“这个节点在哪台服务器、属于哪个策略组” |
| 帮助识别、诊断和恢复错误 | 失败附原因与下一步；排查故障是三条主线之一（[流程 C](05-flows.md#4-流程-c排查故障)） |

### 4.3 先概览，再缩放筛选，按需看细节

Shneiderman 的信息查找口诀（《眼睛说了算》，1996）：先看概览，再缩放和筛选，最后按需查看细节。它直接对应三层结构：工作区首页（概览）、对象列表（筛选与批量）、对象详情（全部状态与操作）。

### 4.4 对象优先

面向对象的用户体验（OOUX，Prater 的 ORCA 流程）主张先确定**对象**（名词），再确定对象之间的**关系**、可执行的**操作**和**属性**，最后才画页面。导航与页面都从对象推导，同一对象在任何位置出现时外观和操作一致。这就是“一个对象一个家，多个入口复用同一实现”（R1）。

### 4.5 信息架构

Rosenfeld、Morville 与 Arango（《信息架构》，第 4 版，2015）区分组织方案：按任务、按受众、按主题、按对象。一个层级内混用多种方案会让用户无法预测东西在哪。

在 apsp：一级导航只用一种方案，即**按工作领域**（六个工作区）。工作区内按对象，对象内按方面（概况、配置、关联、历史）。“实验功能”作为一级分组混入了维护级别这另一种方案，本方案改为在所属领域内标记，见[六工作区方案](04-workspaces.md#5-实验与冻结功能的位置)。

### 4.6 主权型应用与中级用户

Cooper 等（《About Face》，第 4 版，2014）把长时间使用的工具称为**主权型**应用：信息密度高、为熟练使用优化。多数用户会停留在“永远的中级用户”阶段。为完成一个任务而在页面间跳转属于**导航性劳动**，应当尽量消除。

在 apsp：控制台是主权型应用，管理员是中级用户。界面按熟练使用优化，引导只出现在“开始使用”中，不常驻。流程设计以减少跨页面跳转为目标（R10）。

### 4.7 复杂度守恒与渐进披露

Tesler 的复杂度守恒定律：每个应用都有不可减少的复杂度，问题只是由谁承担。渐进披露把不常用的复杂度放到需要时才出现。

在 apsp：兼容、迁移、历史版本、内核差异由系统承担（R13）；高级参数、实验功能在需要时展开。

### 4.8 习惯化与确认

Raskin（《人性化界面》，2000）指出：频繁出现的确认框会被习惯性点过，失去保护作用。比确认更好的是**可撤销**；无法撤销时，确认要写明具体对象和后果，而不是“确定吗？”（R12）。

## 5. 使用理论

### 5.1 以使用为中心的设计

Constantine 与 Lockwood（《为使用而设计》，1999）提出以使用为中心的设计：先列出**用户角色**，再写出每个角色的**基本用例**（去掉具体界面后的用户意图与系统责任），把一起使用的内容组成**交互情境**，最后画出情境之间的**导航图**。它比“为某类用户”的设计更适合工具类软件，因为同一个人在不同时刻扮演不同角色。

本方案按这个顺序展开：角色与用例（本节）→ 交互情境（[六工作区](04-workspaces.md)）→ 导航图与流程（[三条主线](05-flows.md)）。

### 5.2 以活动为中心

Norman（《以人为中心的设计有害论》，2005）主张围绕**活动**设计：一个活动跨越多个对象和多个界面，例如“给朋友开一个账号”同时涉及用户、策略组、套餐、订阅和门户。工具应当支持整个活动，而不是只把每个对象的增删改做好。三条主线流程就是 apsp 的三个核心活动。

### 5.3 待完成的工作

“待完成的工作”（Christensen 等，《哈佛商业评论》，2016；Ulwick，2016）从“用户在什么情境下要完成什么进展”描述需求，而不是从功能清单出发。

| 情境 | 要完成的工作 |
| --- | --- |
| 新买了一台 VPS | 让它尽快开始为大家提供服务，并确认它真的能用 |
| 朋友要用 | 给他一个能用的订阅，额度和到期按约定，以后不用我操心 |
| 有人说连不上 | 尽快知道是他的问题、线路的问题还是服务器的问题，并恢复 |
| 月初 | 知道这个月要花多少钱、哪些快到期 |
| 升级内核或 Agent | 升完不出事，出事能退回 |

### 5.4 角色与频率

| 角色 | 典型任务 | 频率 | 对位置的要求 |
| --- | --- | --- | --- |
| 所有者（主维护者） | 看是否正常、处理告警、加用户、续期、续费 | 每天到每周 | 从概览一步到达 |
| 所有者 | 加服务器、加节点、建链路、换 IP | 每月 | 在工作区内完成，不跨工作区 |
| 所有者 | 升级 Agent 与内核、迁移、备份恢复 | 每季度 | 放在系统，有完整前置检查 |
| 运维管理员 | 服务器与服务的日常操作，无凭据与管理员权限 | 每周 | 与所有者同一界面，按权限裁剪 |
| 只读管理员 | 查看状态与报表 | 按需 | 同一界面，只读 |
| 代理用户 | 拿订阅、看用量与到期、看线路状态 | 按需 | 自己的门户，不进控制台 |
| 访客 | 看公开看板 | 按需 | 公开看板，只读白名单 |
| 自动化调用方 | API 令牌，以后经 MCP 读数据、做受控操作（路线图 M5） | 按需 | 与界面同一套对象与状态 |
| 维护者（工程角色） | 读规则、运行工具、发布版本 | 每次开发 | 仓库导览、模块说明、工具分类 |

频率决定位置：每天的事一步到达，每月的事在工作区内完成，每季度的事放在系统并配完整检查。这延续了 ADR 0098 “按使用逻辑”的做法。

## 6. 设计规则

后续各篇引用下列编号。

| 编号 | 规则 | 依据 |
| --- | --- | --- |
| R1 | **一个对象一个家。** 每类核心对象只有一个所有者模块（写入权）、一个规范详情和一套编辑逻辑；其他位置是筛选视图或链接，复用同一实现。 | DDD 聚合；OOUX；一致性 |
| R2 | **导航与代码分开组织。** 侧栏按工作区组织，代码按稳定领域（ADR 0125 的功能模块）组织；每个入口只属于一个功能，工作区由几个功能的入口组成；页面组合领域组件，导航调整不搬代码。 | Parnas；CCP；ADR 0125 |
| R3 | **统一语言。** 一个词在一个上下文中只指一件事；界面、文档、API、注释使用对象词典的词；外部系统的用语只在边界翻译。 | DDD；贴近用户语言 |
| R4 | **期望与观察分开表达。** 保存、下发、应用、验证、失败与未知是可区分的阶段，各有写入者和判断依据。不把“已通知”说成“已应用”，不把“无回报”说成“失败”。 | ADR 0001；Kubernetes 约定；评估鸿沟 |
| R5 | **新建只有一条路径。** 每类对象只有一个新建入口，使用当前模型；历史模型只经独立的迁移与兼容流程进入，并有退出条件。 | 绞杀者；复杂度守恒；ADR 0085 |
| R6 | **维护级别是元数据。** 核心、支撑、可选、实验、冻结记录在能力清单中，决定显示与投入，不决定目录与编译边界。核心功能不依赖实验与冻结功能（ADR 0125 的叶子规则）。 | 开关分类；CCP；ADR 0125 |
| R7 | **同一设置只有一个编辑位置。** 影响整个面板的设置在系统；属于某个领域的设置在该领域工作区的设置分页；其他位置只读显示并链接。 | 功能地图归类规则 5 |
| R8 | **服务器详情是筛选视图。** 一台服务器的事从服务器进入；关联对象（节点、链路段、解析、告警、费用）在服务器详情中按这台服务器筛选显示，编辑仍在对象自己的家。 | 功能地图归类规则 4；R1 |
| R9 | **先概览，再筛选，按需看细节。** 工作区首页回答“现在怎样、要做什么”，列表负责筛选与批量，详情给出全部状态与操作。 | Shneiderman |
| R10 | **流程连续。** 主线任务在一个情境中完成，下一步就在当前位置提供，用户不需要记住去哪个页面。 | 以活动为中心；导航性劳动 |
| R11 | **状态可见、可追溯。** 每个状态写明依据（谁报告）与时间；失败附原因和可执行的下一步。 | 系统状态可见；帮助恢复 |
| R12 | **防错先于确认。** 用约束防错：不可用的选项不提供，禁用时说明原因。可撤销的操作不确认；不可逆的操作确认时写明对象与后果。 | 防错；习惯化 |
| R13 | **复杂度留在系统里。** 兼容、迁移、历史版本与内核差异由系统吸收，不进入日常流程。 | 复杂度守恒；把复杂度往下压 |
| R14 | **依赖指向稳定的契约。** 公共契约（`protocol`、`adapter-sdk`）稳定而抽象；业务库属于其领域；插件互不依赖。 | SDP、SAP、ADP；ADR 0085 |
| R15 | **按契约给变更分级。** 只动内部实现的变更自由合入；动数据库基线、协议、制品格式或运行时版本的变更是发布事件，必须经过候选版本门禁。 | 并行修改；持续交付 |
| R16 | **文档按有效性管理。** 每份文档写明状态、适用范围、替代关系与未完成条件；每条规则只有一个现行出处。 | ADR 状态；Diátaxis |
| R17 | **每项功能自己维护。** 参考上游，但模型、用语、状态与测试按对象词典重建；上游版本与差异记录为来源说明，不形成运行依赖。 | 用户要求；防腐层 |
| R18 | **移动代码要有收益。** 只有能降低理解成本、修正依赖方向或对齐所有权时才移动；保持包名与公开接口，物理路径的使用者单独迁移，并核对检查器仍覆盖原来的对象。 | 评审意见；Parnas |
