# 三条主线流程

- 状态：提议（2026-11-07）。
- 依据：[设计依据](01-principles.md) R4、R9、R10、R11、R12；以使用为中心的设计与以活动为中心的设计（[设计依据 §5](01-principles.md#5-使用理论)）；工作区见[六工作区方案](04-workspaces.md)，状态用语见[状态设计](06-states.md)。

## 1. 怎样描述流程

三条主线是 apsp 的三个核心活动，对应[设计依据 §5.3](01-principles.md#53-待完成的工作) 的三项待完成的工作。每条流程按**基本用例**写：左边是管理员的意图，右边是系统的责任，不绑定具体控件；然后写在哪里完成、看到什么状态、怎样算完成，以及失败时的分支。

流程设计遵循三条约束：

- **在一个情境中完成**（R10）：下一步就在当前位置提供，不要求管理员记住去哪个页面。跨工作区只出现在刻意的链接处，并在下文标出。
- **每一步都能看见结果**（R4、R11）：用[状态设计](06-states.md)的阶段与依据回答“现在怎样”。
- **用约束防错**（R12）：不可用的选项不提供，禁用时说明原因；只有不可逆的操作才确认。

## 2. 流程 A：接入并发布服务

> 新买了一台 VPS：让它尽快开始提供服务，并确认它真的能用。

前提：管理员有服务器与网络服务的写权限；包含运行时的签名发布已导入面板。

| # | 管理员的意图 | 系统的责任 | 位置 | 看到的状态 |
| --- | --- | --- | --- | --- |
| 1 | 登记一台新服务器 | 创建服务器记录与一次性接入令牌；给出各平台的安装命令 | 服务器 › 添加服务器 | 等待接入 |
| 2 | 在服务器上执行安装命令 | Agent 从 GitHub Release 或镜像下载并独立验签，用令牌接入 | 服务器的终端 | 添加窗口自动变为“已接入 · Agent 版本” |
| 3 | 让它能承载节点 | 写入安装意图并安排第一次发布；Agent 下载、校验运行时制品，应用并回报 | 同一窗口的下一步「安装运行时」；也可在服务器详情 › 网络服务 | 已安排 → 等待设备 → 运行中（内核版本） |
| 4 | 开一个节点 | 校验端口与证书设置；保存期望配置 | 下一步「新建节点」（服务器已预选）；也可在网络服务 › 节点 | 已保存 |
| 5 | 让人能用这个节点 | 把节点加入所选策略组；组内用户获得凭据；编译并下发 | 新建节点表单内的「加入策略组」 | 已下发 → 已应用 |
| 6 | 确认真的能用 | 运行时检查点核对实际配置与进程；可选地从另一台服务器做一次连通探测 | 节点详情 | 已验证（有效期内） |

**完成标准：** 节点在所在服务器上“已验证”，并且至少一个策略组成员的客户端订阅中包含它。

**分支 A2：建一条链路。** 多台服务器上有节点后，在网络服务 › 链路 › 新建链路，选模板（两跳、入口 → 中转 → 落地、含外部节点），按段选择节点或外部节点版本，加入策略组。系统生成不可变版本，按段所在服务器下发，经完整路径探测后切换。完成标准：路径“已验证”，入口计量正常。

**分支 A3：用域名作为公开地址。** 在服务器 › 地址与域名建立解析规则后，节点表单的“公开地址”可以选择这个域名。节点只引用域名，不编辑解析规则；这是流程 A 中唯一的跨工作区链接。

**失败分支：**

| 情况 | 系统给出 | 管理员的下一步 |
| --- | --- | --- |
| 接入令牌过期或设备一直未连接 | 令牌状态与剩余时间；设备能否访问面板地址的检查方法 | 重新生成令牌，或按提示检查网络 |
| 签名发布未导入 | 「安装运行时」不可用，并说明要先在系统 › 制品与版本导入哪个发布 | 导入发布后继续 |
| 运行时安装失败 | 失败原因（下载、验签、服务管理） | 按原因处理后重试 |
| 应用失败（如端口被占用） | 执行失败 · 设备报告的原因 · 仍在运行的修订 | 修改节点后重新保存 |
| 超过时限无结果 | 未知 · 最后一次已知状态 | 核对：设备是否在线、查看运行时日志 |

**与现状的差距：**

- 添加服务器后没有“安装运行时”的下一步；安装入口分散在插件中心、服务器详情 › 插件与概览三处（[功能盘点 §7](02-inventory.md#7-重叠与重复的处理) 第 13 条）。
- 节点创建后要去策略与套餐把它加入策略组；节点页面文字仍写“或直接授权给代理用户”，而 ADR 0112 已取消按人授权。
- 界面没有说明“受管节点在至少一个用户获得授权前不监听端口”，管理员会误以为节点坏了。
- 单个节点没有“确认真的能用”的一步；路径探测只用于链路。

## 3. 流程 B：授权用户

> 朋友要用：给他一个能用的订阅，额度和到期按约定，以后不用我操心。

前提：至少有一个包含可用资源的策略组，以及一个套餐。

| # | 管理员的意图 | 系统的责任 | 位置 | 看到的状态 |
| --- | --- | --- | --- | --- |
| 1 | 开一个账号，定好能用什么、能用多少 | 一个事务内创建用户、套餐快照与策略组成员关系；计算资格；下发凭据 | 网络服务 › 用户 › 新建用户：名称、套餐、策略组在同一表单；速率与连接数限制作为可选项 | 已保存 → 资格“正常” |
| 2 | 把订阅交给他 | 生成客户端订阅（sing-box、Clash Meta、分享链接）与二维码；可选生成门户开通链接或专属地址 | 创建完成后直接显示「交付订阅」 | 凭据已应用于 3/3 台服务器 |
| 3 | 确认他用上了 | 记录客户端订阅的拉取时间与客户端类型 | 用户详情 | 最近订阅拉取：时间、客户端 |
| 4 | 以后不用操心 | 按套餐执行额度、重置周期与到期：资格变化后自动重新发布；提前提醒用户与管理员 | 网络服务首页“需要关注的用户”；概览摘要；用户门户 | 将超额、快到期、已用尽、已到期 |
| 5 | 续期或调整 | “预览 → 应用”生成新的套餐快照；手动重置额度记为补偿，不清空计量 | 用户详情 › 套餐 | 新快照生效时间 |

另一种进入方式：已有用户在门户中用邀请名额邀请他人。被邀请人接受邀请（`/#/join`）后得到同样的用户，套餐与策略组取邀请的默认值；管理员不需要参与。

**完成标准：** 资格“正常”，凭据在全部相关服务器上“已应用”，客户端订阅至少被拉取过一次。

**防错（R12）：**

- 所选策略组没有任何可用资源时，保存前提示，而不是建出一个什么都用不了的用户。
- 运行时不具备逐用户限速能力的服务器上，限制选项不可用并说明原因（需要内核能力 `user-limits`，[收敛方案 §4](07-convergence.md#4-运行时版本与数据库结构解耦)）。
- 重置订阅链接、删除用户是不可逆操作，确认时写明后果（现有文字已经这样做）。

**失败分支：**

| 情况 | 系统给出 | 管理员的下一步 |
| --- | --- | --- |
| 部分服务器离线，凭据未下发 | 用户详情按服务器列出下发状态；订阅中标出尚未应用的资源 | 等服务器上线，或检查该服务器（流程 C） |
| 订阅从未被拉取 | 用户详情提示“尚未使用”，提供重新发送开通链接 | 联系用户 |
| 资格不允许（未开始、已到期、已用尽） | 资格状态与原因 | 调整套餐或续期 |

**与现状的差距：**

- 「创建代理用户」表单只有名称；套餐与策略组要在用户详情的另一个分区里经“预览 → 应用”分配，新建一个能用的用户要跨两个情境。
- 创建完成后没有“交付订阅”的下一步，订阅链接在列表行的弹窗里。
- 用户诊断用“健康”判断“已生效”，可能在新凭据应用前就显示已生效（[状态设计 §5](06-states.md#5-现状对照与改动) 第 3 条）。

## 4. 流程 C：排查故障

> 有人说连不上：尽快知道是他的问题、线路的问题还是服务器的问题，并恢复。

入口有三个，都进入同一份检查清单：

- **从用户进入**：全局搜索用户名 → 用户详情 › 诊断。最常见。
- **从告警进入**：服务器离线、运行时运行异常、长时间未应用、路径验证失败的告警 → 对应对象的详情。
- **从线路质量进入**：延迟、丢包或中国可达性异常 → 涉及的服务器与节点。

**检查清单**由系统按顺序自动执行，每一项显示结论、依据与时间；第一项不通过时，后面的项仍然执行，但界面突出第一处问题：

| # | 检查 | 依据 | 不通过时的下一步（链接到对象的家） |
| --- | --- | --- | --- |
| 1 | 用户能用吗 | 资格：正常、未开始、已到期、已用尽、已暂停 | 用户详情 › 套餐：续期、重置额度、恢复 |
| 2 | 他能用哪些资源 | 策略组的并集；每个资源可用或不可用的原因（策略组未包含、节点已停用、套餐不允许） | 策略与套餐；节点详情 |
| 3 | 他拿到的订阅是最新的吗 | 最近一次拉取的时间与客户端；订阅中的资源与当前可用资源是否一致；专属地址的解析状态 | 提醒用户刷新订阅；地址与域名 |
| 4 | 凭据在服务器上应用了吗 | 每台相关服务器的下发阶段（[状态设计 §2](06-states.md#2-四个阶段与两种异常)） | 服务器详情 › 网络服务 |
| 5 | 服务器与运行时正常吗 | 在线、运行正常、最近失败、正在运行的修订 | 查看运行时日志、重试部署、重启运行时 |
| 6 | 线路通吗 | 链路的路径探测；线路质量中的延迟、丢包、中国可达性；服务器 IP 质量 | 监测与诊断 › 线路质量；必要时运行 TCP 诊断 |
| 7 | 外部节点正常吗 | 所在外部来源的最近刷新、节点版本是否变化、是否仍被采用 | 外部来源详情 |
| 8 | 修好了吗 | 修复后目标对象重新到达“已验证”；告警恢复 | 关闭告警，或记入故障事件（实验） |

**完成标准：** 找到第一处不通过的检查并执行其下一步后，相关对象重新“已验证”，用户的检查清单全部通过。

**与现状的差距：**

- 用户诊断已经能逐个资源给出可用与否的原因（策略组未授权、套餐不允许、节点已停用），是这份清单的基础；缺的是第 3–7 项，它们分散在节点部署、服务器详情、线路检测与外部来源四处。
- 告警只覆盖服务器；下发失败、长时间未应用只出现在实验的故障事件中（[状态设计 §5](06-states.md#5-现状对照与改动) 第 5 条）。
- 线路质量分在四处（[功能盘点 §1](02-inventory.md#1-盘点结论)），排查时要在页面之间来回跳转。
- 用户门户的线路目录只含 Nexus 导入的线路，用户无法自己看到可用资源的状态。

## 5. 流程之间的衔接

| 从 | 到 | 衔接点 |
| --- | --- | --- |
| A 的第 5 步 | B | 节点加入的策略组里已有成员时，提示“这些用户将获得新节点”；还没有成员时，提供「新建用户」 |
| B 的第 4 步 | C | “需要关注的用户”中的已用尽、已到期直接给出流程 C 第 1 项的处理 |
| C 的第 4–5 步 | A | 服务器或运行时的问题回到流程 A 对应的步骤处理 |
| 任一流程的失败与未知 | 概览 | 概览“需要处理的事项”列出，并链接回对象的家 |

## 6. 验收

1. 在空库上，浏览器夹具从“添加服务器”走到“节点已验证”，再到“用户订阅被拉取”，全程不进入实验或冻结页面，除第 2 节标出的地址与域名外不跨工作区。
2. 每个失败分支都能在夹具中制造，界面给出表中的“系统给出”与“下一步”。
3. 流程 C 的检查清单在测试环境中能分别定位四类问题：资格、订阅未更新、凭据未应用、服务器离线。
4. 在测试机上完成一次三条主线的实机走查并记录（[执行计划步骤 4](09-execution.md#步骤-4完成工作区与操作流程)）。
