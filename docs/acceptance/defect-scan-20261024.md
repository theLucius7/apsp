# 2026-10-24 主线缺陷扫描与修复

用户在全部分支合入 `main` 后要求“扫描，进行下一步”。扫描起点是 main `b99eb03`（含 PR #160 运维平台、分支整合、apsp 改名、七个产品区与 shadcn/ui 界面重建、Nexus 导入与费用插件）。路线图的 M0 依赖尚未决定的 D6–D8，因此“下一步”按此前约定理解为：扫描主线，并修复核实的缺陷。

远端 CI 继续暂停，未触发、重跑或恢复。没有访问真实设备、云资源、DNS、支付或通知渠道。

## 扫描方法

| 手段 | 范围 | 结果 |
| --- | --- | --- |
| 自动检查 | `cargo fmt --check`、分层检查、全工作区严格 Clippy | 全部通过；整合方 2026-10-04 的全量本地测试见[整合记录](branch-main-integration-20261004.md)，本轮未重复全量测试 |
| 人工审查（六路并行，只读） | 管理员权限与全部路由；设备群、终端与 Agent；运维、备份、恢复与费用插件；网络配置、网络工作台、DNS 与阿里云；sing-box 插件与整合接缝（含会员与 Nexus 导入）；重建后的界面 | 见下表；高危项和多数中危项已逐条对照源码复核 |

系统性原因：全局守卫只从路径中的 `servers/{n}` 推导服务器范围，网络工作台、网络配置、运维和 DNS 四类前缀交给处理函数自查；处理函数检查了服务器编号，却普遍没有约束三类对象：凭据库引用、全局共享设置、不绑定服务器的对象。
