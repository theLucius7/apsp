# ADR 0047：实时监控、历史粒度、每日汇率与多渠道通知

状态：按用户 2026-10-02 的 NodeFlare 对齐要求实施；本地验证和未验证范围记录在 PROGRESS。CI 继续暂停，不因此签收诊断实机能力或执行生产迁移。

## 背景

已有看板共用完整服务器轮询，Agent 每次上传同时写历史，数据库仅保留两小时原始值和七天的分钟末值。跨币种成本没有可信换算来源，通知仅支持 Telegram。参考本地 NodeFlare `7a7fc0ffe29dddaa21ef11c86e2990d84f3a6cc8` 的采样、实时状态、分层聚合、成本和通知设计，沿用 Apsp 的设备认证、缓存确认、服务器流量与公开看板边界。

## 决策

1. **采样与两类上报分开。** 保持旧的严格 `AgentSettings` 消息不变；`sample_interval_secs` 仍默认 1 秒，`upload_interval_secs` 默认 3 秒。另设 `TelemetrySettings.persist_interval_secs`，默认 60 秒、允许 15–3600 秒，通过新接口协商。新 Agent 将最新实测值送入面板有界内存缓存，历史从原 SQLite outbox 分批上传；只有原持久化事务完成后才 ACK。新接口不可用时继续旧上报方式。新配置与旧设备可共存，不要求同时升级所有设备。
2. **实时状态不充当历史或计费。** 内存缓存过期、面板重启或上报失败后回退最后持久化记录，分别公开采样、接收、持久化样本时间和查询时间，不更新在线心跳或补造数值。看板每 3 秒读取轻量状态，静态信息较慢刷新；客户端可顺序播放已接收的真实样本，不能插值伪造观测。页面隐藏、暂停、切换或权限失效会中止相关请求，旧响应不能覆盖新页面或重新显示已隐藏设备。
3. **系统指标历史分层保存。** 默认保留 30 天，可设 1–3650 天；近两小时保留原始采样，七天内分钟汇总、七至三十天五分钟汇总、更早按小时汇总。每项指标独立保存有效样本数、加权平均、最小和最大值，缺值保持未知；网卡累计计数保留最近值和精确整数字符串，不计算计数器平均。历史接口按所选窗口有界返回，边缘不完整桶明确标记，旧原始历史接口保留兼容。
4. **聚合与重放互不破坏。** 新收据表保存消息身份与摘要，覆盖现有七天迟到/重放接收范围并留余量；清理原始历史不能使旧样本重新参与流量增量或平均数。服务器行锁保护接收、回填与聚合，汇总写入和原粒度删除在同一事务。清理由独立后台任务小批执行，不依赖在线服务器再次上报。旧分钟末值缺少实际样本数，不能冒称精确分钟均值。服务器网卡账本和代理用户计量保持原语义。
5. **每日真实汇率。** 面板从固定 HTTPS Frankfurter v2 获取 CNY 基准汇率，失败可回退同服务 v1；使用官方日期、每币种日期和来源，不采用 NodeFlare 的硬编码估算兜底。成功后 24 小时再拉取，失败保留旧快照、标记过期并一小时后重试；并发和重启由数据库租约抑制重复下载。管理员可手动刷新但有冷却；读取 API 不触发公网请求。每次替换完整来源快照，不混入另一批缺失币种；未知跨币种结果显示不可换算。同币种直接展示原值。
6. **汇率只作资产展示参考。** 看板可选择展示币种、折算月成本和有已知周期/到期日的剩余价值。未填写价格、不具备周期或缺少汇率的数据明确缺失，不补零或推算实际付款。匿名白名单不包含价格、到期成本和管理字段；新增汇率只读接口遵循看板公开开关、禁止缓存，管理刷新必须登录。
7. **每个通知渠道独立投递。** 保留原站内事件和 Telegram，增加通用 Webhook 及常用 JSON 模板预设。同一事件、通知类型、渠道唯一；成功渠道不因另一渠道失败而重发。沿用有界重试、速率限制和可查询发送状态；停用或更换目标只取消对应渠道待发记录，全局关闭仍取消全部。Webhook 地址、请求头及自定义 JSON 只写不回显，模板单次替换，重定向关闭，错误不包含敏感目标或响应正文。
8. **真实聚合参与资源告警。** 资源窗口改用真实聚合的 count/avg/min/max；平均判断按有效样本数加权，持续超限表示窗口内有效观测的最低值也超过阈值，窗口有缺失或过期时保持未知。每分钟存在观测不证明逐秒采样完整，也不认证两次采样之间始终超限。完整分钟最后一条样本不再冒充该分钟均值。通知仍只提醒，不执行付款、停用或远程命令。

## 兼容与验证

新增迁移 `0029_exchange_rates.sql`、`0030_telemetry_history.sql`、`0031_notification_alignment.sql`，升级前沿用面板备份流程；新增协议和接口不修改旧消息必需字段。面板直接声明锁文件已有的 `httpdate 1.0.3`，用于按 RFC 9110 解析 `Retry-After` 的 HTTP 日期及历史兼容日期格式；没有新增包版本或另一份日期解析实现。其余实现复用现有 Rust、React、PostgreSQL、SQLite 依赖。

回归覆盖汇率原子刷新/失败缓存/权限/下载上限，遥测 ACK、重放、历史迁移与聚合边界，公开白名单与隐藏/权限撤销，通知渠道隔离/模板/失败重试，以及真实浏览器的刷新、历史、币种和设置操作。外部接口仅做资料读取；通知测试使用私有回环替身，没有向真实收件人发信。本地验证不代替长期多平台驻留、生产数据库升级、真实渠道送达或诊断实机验收。

汇率接口依据：[Frankfurter v2](https://frankfurter.dev/)、[兼容 v1](https://frankfurter.dev/v1/)。上游工作日日期可能早于抓取日，因此分别展示数据日期与抓取时间。

v2 默认汇率为官方来源的混合参考值，不冒称单独 ECB 直报或实时成交价格；v1 回退来源标记为 `frankfurter-ecb`。两者均固定 CNY 基准，保留每币种的原始日期，缺失币种不补估算。墙钟回退使抓取时间或来源日期位于未来时，保留原值但显示过期，避免冒称新鲜。

通知确认依据：[Discord Execute Webhook](https://docs.discord.com/developers/resources/webhook#execute-webhook)、[Slack incoming webhook](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/)、[Gotify API](https://gotify.net/api-docs)、[ntfy JSON 发布](https://docs.ntfy.sh/publish/#publish-as-json) 和 [RFC 9110 Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after)。Discord 固定 `wait=true` 并校验本次返回消息 ID；Slack 需 `ok`，Gotify 需正整数 ID，ntfy 需消息 ID、`message` 事件及与请求一致的主题。它们仅证明平台确认，不证明接收人已阅读。自建 HTTP/HTTPS 目标由管理员明确授权，可为内网；这不是公网 DNS 或 SSRF 地址过滤。限流等待从请求完成时间计算，单次等待仍限于 1–86400 秒。
