# ADR 0125：按功能划分模块，内核只提供机制

状态：已接受；“与侧栏一一对应”按 [ADR 0126](0126-workspaces-language-and-addresses.md) 第 6 条理解为入口级，「插件中心」名称按其第 2 条调整。

2026-11-07。用户要求：“目前几个功能没有划分好，每个功能我还是自己维护一套吧（虽然参考了上游仓库），做好功能划分，逻辑结构等，深度研究软件工程理论，和这个项目哲学，交互哲学，使用理论。”调查结论、理论依据与完整设计见[功能划分与逻辑结构](../architecture.md)。

## 决策

- apsp 保持模块化单体：一个面板二进制、一个 Agent 二进制，内部按功能强制边界。
- 宿主是内核，只保留身份、设备、平台服务三块机制，提供登记口；不认识任何功能，不含功能的表与 SQL。
- 功能模块：`proxy`（代理服务，内部分为 nodes、users、delivery、portal、runtime、legacy 六个子模块）、`dns`、`cloud`、`costs`、`alerts`、`lines`、`overview`、`lab`。与侧栏一一对应。
- 一个功能一个家：后端 crate、Agent 适配器、表结构片段、前端目录、测试、文档、上游副本都放在该功能下。
- 每张表只有一个所有者；跨功能只经接口或只读视图；外键只指向内核的表。基线按功能分片后仍合成一份并以指纹核验（ADR 0122 不变）。
- 功能之间不直接依赖，需要别的能力时经内核登记的端口取得。实验与冻结功能是叶子。
- 参考过的上游代码，凡是功能依赖的，由该功能在 `upstream/` 里保留可离线构建的副本与许可，构建不下载未固定的文件；旧系统（Nexus）在防腐层之后，迁移完成后删除。
- 用一组小接口代替 22 个方法的 `PanelPlugins`；前端每个功能用 `index.ts` 导出清单，外壳只读清单。
- 边界规则由扩展后的边界检查守住，现有违规只许减少。

## 后果

- 按设计文档第 8 节分阶段迁移，每一步可单独上线、除写明的以外行为不变；改到基线的步骤随附接入脚本。
- ADR 0085 的三层规则不变，本决策把它从 crate 层面延伸到表、SQL、前端和上游代码。
- 第 10 节列出的事项需要用户决定，决定前保持现状。
