# ADR 0138：迁移线路为策略组里的每位成员服务

状态：已接受（2026-11-17）。取代 [ADR 0115](0115-original-permission-groups-as-policy-groups.md) 2026-11-17 补充里的收编做法。

## 背景

生产上 29 条线路全部是迁移线路（`singbox_nexus_runtime_nodes`）。按 ADR 0115，策略组里的迁移线路只下发给有原身份（`singbox_nexus_identities.legacy_uuid`）的用户：`singbox_desired_accesses` 排除迁移线路，运行时发布只列原身份。原身份只由兼容通道发给有成员资料的用户，而兼容期内管理员新建的用户不建成员资料（[ADR 0113](0113-invitation-quota-without-commerce.md)），所以把这样的用户放进「原权限组 · 00」，订阅一直是 0 个节点（用户 171，2026-11-16 起）。

当天的应急修复（`569de5d7`）在策略组落实授权时把这类用户收编进兼容通道，订阅改由原系统生成。用户随后要求“从根本上修复这个问题”：apsp 自己在迁移线路上为这些用户服务，兼容通道只保留它已经服务的用户。

## 决策

- **谁由兼容通道服务（D1）。** 集合函数 `singbox_legacy_served_users()`：有原身份；或兼容通道运行期间有状态不为 `staged` 的成员资料（通道约 10 秒内的下一次交换就会签发原身份，条件与交换本身收编成员的条件相同）。视图、权益与成员摘要按集合连接它（每次查询算一次，不逐行调用），触发器、门户与诊断经 `singbox_legacy_served(用户)` 问单个用户；判断只写在这一处。
- **其他人拿普通凭据（D2）。** `singbox_desired_accesses` 只对兼容通道服务的用户排除迁移线路，其他用户与普通节点一样经策略组在 `accesses` 里得到新的 UUID 与凭据；`singbox_nexus_guard_access` 只拒绝为兼容通道服务的用户在迁移线路上写凭据，删除一律放行（用户后来变成成员时，旧凭据可以删掉；在此之前它们已不在 `singbox_desired_accesses` 里，不会下发）。运行时发布在原身份之后加上这些用户的凭据（`singbox_eligible_accesses`），一并写进记账名单；部署的 `public_nodes` 改由 `nodes` 行按普通发布的格式生成（跟随公网地址的变更，保留配置不动），只带这些普通凭据，不带原身份；公网地址变更让运行中的主机重新发布，配置没变时只刷新订阅读取的投影。apsp 的订阅因此列出这些线路。从原系统迁移来的成员不变：原 UUID、原系统生成的订阅、主机配置逐字节相同。
- **按线路倍率计流量（D3）。** 兼容通道不服务的用户在迁移线路上的流量按该线路的倍率（`singbox_nexus_runtime_nodes.rate`，apsp 自建线路为 1）计入额度，与原面板对其成员的计法相同。倍率在查询时套用（`singbox_usage_charged`，按记录和日汇总上的线路）。线路下线时它的倍率记入 `singbox_nexus_runtime_retired_rates`，已有的流量照旧按它计：补偿额度按计费后的字节记，下线若让倍率回到 1，重置过的用户就会凭空多出额度。在用线路改倍率会按新倍率重算本周期已用量，这一点接受并在此记录。原始流量照旧按字节记录与展示（流量明细、统计图）；这些用户的 `singbox_entitlements` 已用量、订阅头的已用量（按原始上下行比例拆分）与换套餐预览用计费后的值。兼容通道服务的用户（有原计量的按原计量，暂时没有计量的按原始字节）完全按以前的算法。
- **已收编的不撤回（D4）。** 应急修复收编的用户（171）继续由兼容通道服务，不退出成员资料。代码去掉收编；以后管理员新建的用户加入含迁移线路的策略组，直接拿普通凭据。
- **暂停接管的主机（D5）。** 暂停期间主机运行原软件，只认原身份，普通用户在那里没有服务：订阅不列这台主机的线路（`traffic::nexus_nodes::held_host_sql`），诊断把这些线路标为不生效，门户把它们显示为不可用。恢复接管后照常。
- **只属于兼容通道的数据不给普通用户。** 投递给兼容通道的流量只含有原身份的用户（`bridge::enqueue_usage`，与以前相同），设备会话地址只记有原身份的用户（`nexus::sessions::ingest`），原面板不会见到它不认识的用户。普通用户的限速与连接数照旧由 apsp 的用户限制编进配置。
- **成员摘要。** 主机的成员摘要同时包含原身份与普通凭据（线路、用户、UUID，后者经 `singbox_runtime_credentials()` 读取：从迁移线路上的凭据出发，只检查这些凭据的授权），凭据出现、轮换或失效都会让主机重新发布；没有普通用户的主机摘要与以前逐字节相同，部署后不会触发重新发布。
- **热路径。** 发布器每秒检查一次成员摘要并刷新权益，2026-11-13 曾因逐行函数与 JIT 让数据库 CPU 满载。所以兼容通道的判断在视图与权益里是对集合 `singbox_legacy_served_users()` 的一次哈希查找（不逐行调用函数，也不用连接放大行数估计；连接版本在未统计的库里把估计放大到十万行，触发 JIT，单次权益查询 1.3 s）。测试库上按生产规模造数（45 位用户、15 台主机 30 条迁移线路、700 对策略授权、4 位普通用户 64 条迁移线路凭据，已 `ANALYZE`）的 `EXPLAIN ANALYZE` 九次中位数，依次为改前（没有普通用户）/ 第一版 / 现在：成员摘要 1.7 / 12.1 / 2.5 ms，`singbox_desired_accesses` 0.6 / 4.8 / 0.9 ms，`singbox_entitlements` 2.2 / 2.1 / 2.1 ms；第一版与现在的成员名单、期望授权逐项相同。
- **`singbox_eligible_accesses` 不改。** 它对每条凭据各算一遍全体权益，凭据多时变慢；曾改成每次调用先算一次权益，但这让调用方的筛选（按服务器、按用户）不再先缩小凭据，只有零星凭据的服务器也要算整个服务的可用凭据。按真实调用语句（准备语句、预热后、`jit=off` 与面板相同，九次中位数，原定义 / 改写，单位 ms）比较，没有一种在所有情形都不慢，所以保留原定义：

  | 语句 | 全服务 0 条普通凭据（今天的生产） | 38 条（2 人 × 19 条线路） | 600 条（20 人 × 30 条） |
  |---|---|---|---|
  | 发布器 `publisher.rs`，没有普通凭据的服务器 | 0.13 / 0.14 | 0.16 / 5.31 | 0.19 / 13.12 |
  | 发布器，有普通凭据的服务器（4 条 / 40 条） | 0.15 / 0.14 | 12.97 / 5.76 | 125.83 / 14.46 |
  | 迁移主机发布 `runtime_publish.rs` | 0.12 / 0.15 | 13.46 / 7.02 | 107.43 / 11.55 |
  | 订阅 `subscriptions.rs`，一位用户 | 0.10 / 0.14 | 2.91 / 6.07 | 5.12 / 5.52 |

  另试过让筛选能下推、权益只在需要时算一次的写法（`= ANY(ARRAY(...))`），没有普通凭据的服务器同样变慢（5–12 ms）。凭据多的服务器发布变慢是原定义固有的，记在 `open-questions.md` 的后续里。
- **轮换凭据。** 用户后来被兼容通道服务时，他在迁移线路上的旧凭据已不再授权，触发器也不让再改；轮换时这些凭据直接删除，不让整个操作失败。
- **授权随线路变化。** 原面板改了线路所属的原组（`follow_legacy_groups`）或线路下线、准备被撤销（`leave_groups`）时，对受影响的用户重新落实授权；下线与撤销准备先删除线路上的凭据。

## 生产数据核对

2026-11-17 在生产库上只读核对（只读事务，不建任何对象；按旧定义与内联的新定义分别计算）：`singbox_desired_accesses` 新旧都是 0 行（所有线路都是迁移线路，组里没有兼容通道以外的用户）；`accesses` 0 行，可用凭据 0 行；17 台运行中主机的成员名单新旧逐字节相同；40 位用户中 39 位按原计量、没有暂时缺计量的成员，剩下一位（169，兼容通道不服务）计费后的已用量与原始已用量相同。部署后没有主机需要重新发布，额度与订阅不变。

## 取舍

- **继续收编（应急修复）：** 用户的订阅改由原系统生成，原面板每人只认一个组，用户也被绑在兼容通道上，等于把问题推给 1.4。未采用。
- **兼容通道服务的成员也改发普通凭据：** 订阅全部换新，违背 ADR 0115 的前提。未采用。
- **入库时就按倍率折算流量：** 改倍率后历史无法重算，原始字节也会丢失。未采用；查询时折算，下线线路的倍率另存。
- **下线时不删倍率行：** `singbox_nexus_runtime_nodes` 的行代表主机正在运行的线路，发布与设备数都按它走；所以另存一张只含下线线路倍率的表，每条线路的倍率始终只在一处。
- **`public_nodes` 完全不带用户：** 订阅只列出主机已应用、且包含该用户当前凭据的线路，这个核对靠部署记录里的用户；不带用户就要另写一套核对。所以与普通发布一样带上普通凭据，只是不带原身份。

## 后果

- 管理员新建的用户与受邀账号的区别只剩订阅由谁生成：受邀账号是成员，订阅由原系统生成；管理员新建的用户由 apsp 生成。兼容通道退出（路线图 1.5）后，成员也改由 apsp 生成订阅，这时本决定的区分随之消失。
- 原面板仍按一个原组列成员的线路，ADR 0115 的这条限制只对成员保留。
- 新建用户的门户、诊断与订阅预览都按普通路径显示迁移线路。
