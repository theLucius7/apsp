# ADR 0131：每类对象只留一套模型，按本质整合功能，去掉插件外壳

状态：已接受（2026-11-09）。调整 [ADR 0128](0128-domain-architecture.md) 的迁移顺序与“后果”中接口前缀一条，取代[收敛方案](../redesign/07-convergence.md)的分阶段授权与[重新设计执行计划](../redesign/09-execution.md)的步骤顺序。

2026-11-09 用户要求：“我打算激进修改 apsp……整合之前的功能，按照底层逻辑本质，重新划分规划，不要按照 plugin，按照本质修改。”随要求给出的参考方案：确定唯一模型，成批删除旧实现，直接修改调用方，再沿新结构加功能；允许内部接口、目录、表结构破坏性调整；兼容、发布治理与验证不再排在产品前面。

## 背景

ADR 0128 的九个领域已经按对象、规则与不变量划分，划分本身不需要推翻。2026-11-09 的代码里仍不按本质组织的是两类东西：

1. **同一个对象有几套实现。** 链路三套（两跳旧模型、混合、有序），外部来源两套（A、B），部署管理两个界面（节点页的部署弹窗与服务器详情 › 网络服务），运行时发布两条路径（原生编译与 Nexus 保留配置），客户端订阅两个渲染器（apsp 与旧面板），Globalping 与 Cloudflare 客户端各两个，服务器资产两份、生命周期两套。
2. **插件外壳。** `plugins/singbox/panel` 约 4.7 万行，装着流量服务、服务权益、Nexus 兼容、中国可达性与用户操作流程；`plugins/alicloud/panel` 混着资源、基础网络、成本与作业；前端按 `web/src/plugins/*` 分目录；界面有「插件中心」「sing-box 安装」，服务器详情的网络服务分页地址是 `/servers/{id}/plugins`。

2026-11-09 对生产库的只读核对：三套链路的全部表都是 0 行；A 来源已于 2026-11-04 迁到 B（2 个来源、24 个修订、888 个外部节点版本），A 只剩只读存档；兼容桥仍在运行（44 个用户的身份与计量、17 台服务器的运行时接管），43 个迁移用户的订阅仍由旧面板渲染；兼容桥只经数据库函数（`singbox_nexus_*_exchange`）与 apsp 交换数据，不调用 HTTP 接口。

## 决策

### 1. 开发规则：一类对象一套模型

| 项 | 规则 |
| --- | --- |
| 旧实现 | 有替代实现就整套删除：接口、页面、分支、专用测试、脚本与文档一起退出 |
| 内部兼容 | 调用方一起改；不为旧函数名、旧模块路径、旧 crate 名保留包装与再导出 |
| 旧数据模型 | 一次性转换到当前模型；代码随即只认当前模型；旧表随下一次基线变更删除，删除前导出归档 |
| 抽象 | 同一领域内直接调用；只有确有多个实现，或需要逆着依赖顺序调用时才保留接口；只转发参数、没有自己规则的包装合并掉 |
| 版本支持 | 内部统一到约定的 Agent 与运行时组合，不为历史组合保留分支 |
| 验证节奏 | 一个完整大步骤写完，再集中构建并验证受影响的主流程；已有业务测试直接复用，废弃实现的测试随实现删除 |
| 文档 | 现行文档只写当前设计、功能清单、运行说明与下一步；废弃方案退出现行入口，追溯看 Git 历史 |

账号权限、计量规则、数据库事务与外部契约地址（客户端订阅、门户、邀请、专属地址）是业务规则，不在删除之列。

### 2. 按本质整合现有功能

apsp 做的事只有一件：**把“谁可以在哪些服务器上使用什么服务、用多少”变成每台服务器上确定的配置和每个人手里可用的订阅，并证明它确实生效。** 由此有三条主链和五个承载面：

| 本质 | 领域 | 唯一的对象链 |
| --- | --- | --- |
| 供给：提供什么服务、经过哪里 | 流量服务 `traffic` | 服务器上的运行时 → 受管节点与外部节点（外部来源）→ 链路 → 配置版本 → 部署 → 已应用 |
| 使用：谁能用、用多少、拿到什么 | 服务权益与交付 `access` | 用户 → 策略组（能用什么）→ 套餐（多少、多久）→ 用量账本 → 资格 → 客户端订阅、专属地址、门户 |
| 证据与执行：发生了什么、怎样可靠地改 | 观测 `observability`、作业 `operations` | 遥测、计数、拨测、诊断、可达性 → 告警与事件；变更 → 作业与设备任务 → 回执 |
| 承载：机器、网络、名称、钱、平台本身 | `resources`、`networking`、`naming`、`costs`、`governance` | 服务器与云资源；主机网络；域名、记录与证书；续费与计费；管理员、信任、制品与备份 |

过去按插件组织的功能按本质归位：

| 过去的位置 | 本质 | 归入 |
| --- | --- | --- |
| sing-box：节点、链路、外部来源、运行时安装、配置编译、发布与部署、运行时运维 | 供给 | `traffic`；界面在网络服务与服务器详情 › 网络服务 |
| sing-box：代理用户、策略组、套餐、用量、限制、客户端订阅、专属地址、门户、邀请、指南与提醒、用户操作流程与诊断 | 使用 | `access`；界面在网络服务 › 用户、策略与套餐 |
| sing-box：中国可达性 | 证据 | `observability`；界面在监测与诊断 › 线路质量 |
| sing-box：Nexus 节点接管与兼容桥 | 历史迁移 | 收拢为一个兼容模块，兼容桥退出（路线图 1.5）后整体删除 |
| 插件中心：版本与下载 | 平台信任的制品 | `governance`；系统 › 制品与版本 |
| 插件中心：逐台“安装 sing-box”的总表 | 运行时是服务器上的服务实例 | `traffic`；只在服务器详情 › 网络服务安装，网络服务首页汇总状态 |
| DDNS 插件 | 名称 | `naming`；服务器 › 地址与域名 |
| 费用插件 | 钱 | `costs`；费用与续费 |
| 阿里云插件：实例、EIP | 资源 | `resources`；服务器 › 云资源 |
| 阿里云插件：CDT 计费流量与账单 | 钱 | `costs` |
| 阿里云插件：启停与换 IP 的执行 | 执行 | `operations`（此刻能否关机由 `resources` 判断） |
| 阿里云插件：安全组 | 网络 | `networking` |
| 诊断插件（IPQuality、NodeQuality、TcpQuality） | 证据 | `observability` 的诊断工具 |
| 云接口插件 | 技术机制 | 平台 `crates/cloud-api` |

### 3. 每类对象只留的一套模型

| 对象 | 保留 | 删除或合并 |
| --- | --- | --- |
| 链路 | 有序链路，界面与文档直接叫“链路” | 两跳旧模型（`chains.rs`、编译器 `relays.rs`、`legacy-takeover` 命令）与混合模型（`mixed_paths/`、`mixed_conversion.rs`、`POST /chains/batch`）。生产无链路数据，不需要转换 |
| 外部来源 | B 模型（`subscription_sources/`、`subscription_parser/`，界面 `Sources.tsx`、`OrderedSourceImport.tsx`、`SourceEditor.tsx`） | A 模型（`sources/`、`source_migration/`、`/subscription-sources*`、`SubscriptionSources.tsx`、按迁移状态切换的视图与分支） |
| 运行时安装与部署界面 | 服务器详情 › 网络服务（`ServerBusiness`）与运行时操作组件 | 插件中心的启用总表、节点页的独立部署弹窗 `NodeDeployment.tsx`；节点页“查看部署”跳到对应服务器的网络服务 |
| 运行时发布 | 原生编译 | Nexus 保留配置（`compiler/src/preserved.rs`），随兼容桥退出 |
| 客户端订阅 | apsp 编译 | 旧面板渲染与兼容桥的资格、计量分支（路线图 1.4、1.5） |
| 过渡接口与别名 | 领域直接调用 | `Dns01`（ACME 进入 `naming` 后）、`crates/panel/src/plugins.rs` 的 `expenses`、`ddns` 等旧名与 `apsp_panel` 的兼容再导出 |
| 外部服务客户端 | 平台 `crates/cloud-api` 的 Globalping、`crates/naming` 的 Cloudflare | 中国可达性自带的 Globalping、专属地址自带的 Cloudflare |
| 服务器资产与生命周期 | 一份资产记录、一套生命周期 | `fleet_profiles.asset` 并入资产，运维标记不再叫生命周期（路线图 4.4） |

### 4. 不再有插件外壳

- **代码。** `plugins/singbox/panel` 拆为 `crates/traffic` 与 `crates/access`；`plugins/alicloud/panel` 拆回 `resources`、`networking`、`costs`、`operations`、`observability`；设备侧的服务单元与诊断工具的打包脚本放进所属领域的目录。`plugins/` 目录最终不存在。
- **前端。** `web/src/plugins/*` 改为 `web/src/<领域>/`；`web/src/app/` 只放外框、路由、侧栏与组合页面。
- **界面。** 不出现“插件”。「插件中心」改为「制品与版本」，只显示版本、平台与下载；运行时只在服务器详情 › 网络服务安装；服务器详情的网络服务分页地址改为 `/servers/{id}/services`，旧地址改写一个发布版本。
- **接口前缀。** `/api/plugins/...` 仍是接口契约，本决策不改；兼容桥退出后按领域一次性改名（届时没有仓库外的调用方），改名表随那次变更给出。设备上的路径（`/opt/apsp/plugins/sing-box`）属于 Agent 协议，不改。

### 5. 执行顺序：三个大步骤

| 步骤 | 内容 | 完成标准 |
| --- | --- | --- |
| **一 统一主业务模型** | 链路只留有序模型；来源只留 B；插件中心与独立部署弹窗退出；过渡别名删除；sing-box 拆为 `traffic` 与 `access`、阿里云拆回各领域、前端按领域目录；兼容桥的查询收拢到一个模块；旧表、旧视图与运行时版本枚举随一次基线变更清理（附接入脚本，走 PR） | 新建节点、组织链路、分配策略与套餐、生成订阅都只经过一套模型；仓库中没有 `plugins/` 目录与 `legacy`、`mixed`、数字编号来源的代码路径 |
| **二 完整使用流程** | 六个工作区按实际功能落地；节点、链路、策略、套餐、用户之间顺畅跳转；每个功能交付完整入口、表单、结果与下一步，不先铺页面骨架 | [六工作区方案 §9](../redesign/04-workspaces.md#9-验收) 满足；三条主线的浏览器夹具通过 |
| **三 沿新结构加功能** | 已合入的高级配置、会话管理、用户控制真正接通；迁移用户的订阅改由 apsp 生成（路线图 1.4，生产切换另行确认）后兼容桥退出（1.5），删除 Nexus 兼容模块；发布问题阻断功能时直接修通 | 兼容桥与旧面板下线；仓库中没有 Nexus 兼容代码 |

发布治理（候选版本清单、部署门禁的拦截模式）、通用能力矩阵与长期迁移框架不再是新功能的前置工程，遇到实际阻断再修。

### 6. 授权范围

本次要求授权：删除有替代实现的旧模型、旧界面、旧接口、专用测试、脚本与文档；旧数据转换后随基线变更删除（先导出归档，基线变更照常附接入脚本、走 PR，并由部署器在生产结构副本上试启动）。仍需另行确认：没有替代实现的用户可见功能的移除；改变已发给代理用户或客户端的地址；把迁移用户的订阅切到 apsp 渲染（2026-11-02 用户决定暂不换订阅）；真实云资源、DNS 与通知操作。

## 取代与调整

- [收敛方案](../redesign/07-convergence.md) §1 的“收口、迁移、收缩各自授权”：由第 1、6 条取代；§2、§3 中链路与外部来源的处理由第 3 条取代。
- [重新设计执行计划](../redesign/09-execution.md) 的步骤 2–6 顺序：由第 5 条取代；步骤 2（发布衔接）降为按需修复。
- [ADR 0128](0128-domain-architecture.md)：领域、依赖与写入规则不变；“后果”中 `/api/plugins/...` 不改名一条改为第 4 条；阶段 B2–F 的顺序并入第 5 条的步骤一。
- [ADR 0126](0126-workspaces-language-and-addresses.md) §2.1 “插件中心改名需要用户确认”：已确认。

## 后果

- 删除是按完整依赖链进行的：一个模型退出时，它的接口、页面、测试、脚本、文档与边界清单里的路径一起退出，越界清单随之变短。
- 旧模型的表在代码删除后暂留在基线中（空表或只读存档），由步骤一里的那一次基线变更删除；在此之前没有代码读写它们。
- 文档以[功能划分与逻辑结构](../architecture.md)、[领域归属表](../domain-map.md)、[对象词典](../redesign/03-objects.md)、[功能地图](../product-map.md)为现行入口；描述已删除模型的设计文档移出现行入口。
