# ADR 0133：每种底层机制只有一套实现（第一部分：咨询锁与后台任务）

状态：已接受（2026-11-13）。延续 [ADR 0131](0131-one-model-per-object.md)（一类对象一套模型）与 [ADR 0132](0132-platform-only-host-and-domain-addresses.md)（宿主只剩平台机制），处理 [architecture.md §12](../architecture.md#12-扫描结论与余下工作2026-11-13) 里“后台循环”“咨询锁的键”两项与任务心跳的归属。

2026-11-13 用户：“扫描 apsp 和查看仓库记录，优化”，随后说明“目前是底层原理深度统一”。

## 背景

ADR 0131 让每类对象只留一套模型，ADR 0132 把领域代码迁出宿主。贯穿所有领域的底层机制却仍是各写各的，新代码也会照旧再写一份：

1. **咨询锁。** 生产代码里 38 处（另有 3 处在测试里）直接写数字调用 `pg_advisory_xact_lock`，分布在 27 个文件，还有几处按文本取哈希作键。没有登记处，看不出哪些号码已被占用。逐一核对后确有一处无意共用：管理员的工作区偏好锁取“73002000 + 管理员编号”，于是 1 号管理员与“新建或修改管理员”是同一把锁，112 号会与“工具安全通告刷新”是同一把锁，再大的编号可以落到任何更大的键上。
2. **后台任务。** 20 个后台循环各自写间隔、错过的拍、错误日志与心跳。其中 6 个从不写心跳（`expenses` 的名字早已在健康视图的清单里，却从未写入），健康视图看不出它们是否在运行。心跳表登记给平台，写入它的代码却在治理。

## 决策

1. **原则。** 每种底层机制只有一套实现，放在能拥有它的最低一层：平台提供机制，领域只声明自己的参数（键、名称、周期、一拍做什么）。每统一一种机制，同时加一个随 `cargo test` 运行的守卫，禁止在别处再写一份；守卫的例外逐条写明原因，只许减少。平台不认识任何领域，所以领域专有的名字留在领域里，由应用层的测试把各领域的声明放在一起核对。
2. **咨询锁。** 平台 `apsp_panel_host::locks` 提供 `Key`（一个 64 位键，或 PostgreSQL 的“类 + 对象”两个 32 位键）与 `TextKey`（按文本 `hashtextextended(text, seed)` 取键），以及加锁与试锁；每个对象一把锁用 `Key::offset`。各领域在自己的 `src/locks.rs` 声明锁键与用途，号码沿用原值，只在数据库基线函数里使用的键也由所有者声明（如 `singbox_nexus_device_exchange` 的 73201002）。应用层的测试核对：所有声明的号码互不相同；每个 `src/locks.rs` 都在清单里且清单列全；数据库基线与接入脚本里的锁键都已声明。守卫：平台 `locks.rs` 以外的源码出现咨询锁 SQL 就失败。
   - **唯一改动的号码**：管理员偏好锁改为“类 73002000、对象为管理员编号”的两整数键。两整数键与 64 位键是不重叠的两个键空间，任何编号都不会再碰到别的用途。代价是保存工作区偏好不再与新建、修改管理员或刷新工具通告互相等待——它们本来就不该互相等待。
   - **有意共用，保持不变**：739104824 是“DNS 写入”一把锁，覆盖 DDNS 认领与写入、规则迁移与回退、手动修改记录；73201001 是发布锁，基线函数 `singbox_nexus_bridge_exchange` 也取它。声明处写明了共用者。
3. **后台任务与心跳。** 平台 `apsp_panel_host::maintenance::periodic` 是唯一的周期执行器：按 `Cadence`（每隔一段、错过的拍补跑、每拍之后暂停或被唤醒、只在状态变化或隔一段时间才记录）运行一拍，把这一拍的结果写成心跳与失败日志；长任务期间用 `beat_while` 保活。领域只写“一拍做什么”，跨拍的状态（子周期、派生的任务）放在执行器传入的上下文里。心跳的写入与读取收归平台（表本来就登记给平台），治理的健康视图经平台读取并照旧脱敏。
   - **每个后台任务都报心跳**：新增 `expenses`、`exchange-rates`、`member-messages`、`china-reachability`、`subscription-hosts`、`subscription-sources` 六个，健康视图多出这六行，界面为它们（以及原来缺名称的 `operations-job-backups`）加了中文名称。原有心跳的名字与 `details` 不变。
   - **守卫**：应用层 `HEARTBEATS` 列出的心跳名与执行器运行的任务名逐一对应；领域与应用代码里不得再自己写 tokio 间隔循环，三处不是后台循环的用途（控制台事件流、Agent 连接保活、单个来源任务的取消与租约续期）逐条列明。
4. **不在本次。** 对外请求（平台两个 crate 只能依赖 `protocol`，统一要先改层级规则）、网络校验与受控出站、“服务器此刻是否可用”的判断、投递器与六个队列、Cloudflare 与 Globalping 客户端、健康视图改为组合视图、保留期由所有者执行——从第二部分起处理，清单仍在 architecture.md §12。

## 后果

- 新的后台任务与咨询锁只能经这两个机制写，否则测试失败；要增加例外必须写明原因。
- 心跳名是已保存的标识，日志与健康视图靠它保持连续，新增的六个此后同样不能随意改名。
- 日志级别：作业的三个循环（`operations`、`operations-backups`、`operations-job-backups`）一拍失败由执行器记为 WARN，原来是 ERROR；心跳写入失败统一记 WARN（`network-certificates` 原来不记）。
- `subscription-sources` 在下一拍开头收取已完成的任务，仍在认领新任务之前，并发上限与租约续期不变。
- 心跳的 `details` 只按大小截断，不再按键脱敏；现有心跳的 `details` 没有会被脱敏的键，保存的内容不变，健康视图显示前仍经 `guard::redact`。
