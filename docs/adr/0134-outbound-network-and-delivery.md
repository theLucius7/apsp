# ADR 0134：每种底层机制只有一套实现（第二部分：对外请求、网络校验与通知投递）

状态：已接受（2026-11-13）。延续 [ADR 0133](0133-one-implementation-per-mechanism.md) 的原则（平台提供机制，领域声明参数，每种机制配一个随 `cargo test` 运行的守卫）；修改 [ADR 0128](0128-domain-architecture.md) 与 [ADR 0132](0132-platform-only-host-and-domain-addresses.md) 中“平台的两个 crate 都只依赖 `protocol`”这一条。

2026-11-13 用户：“目前是底层原理深度统一”，第一部分上线后说“continue”。

## 背景

[architecture.md §12](../architecture.md#12-扫描结论与余下工作2026-11-13) 里与对外通信有关的重复实现：

1. **对外请求。** 面板各处 14 个 `reqwest` 客户端各自配置超时、重定向、代理与 TLS，测试与夹具里还有 18 个；有界读取响应体的写法 11 份，状态码到错误的映射 2 份，`Retry-After` 的解析 3 份。其中几处沿用 `reqwest` 的默认值：读取环境里的代理变量、最多跟随 10 次重定向。
2. **网络校验。** 判断“公网地址”、受控出站（解析 → 拒绝非公网 → 固定地址 → 连接与 TLS）、TCP 拨号、URL 与主机名检查各有多份，接受的范围不尽相同；配置编译库不依赖平台，另有一份主机名检查。
3. **通知投递。** 六个队列（告警发件箱、云资源通知、续费提醒、中国可达性告警、故障通知、代理用户账号提醒邮件）各写一遍认领、发送与重试，规则各不相同。告警发件箱放在平台里，投递时读观测与作业的表。

这几项没有在第一部分做，因为平台的两个 crate 只能依赖 `protocol`：对外请求的机制若放在 `panel-host`，`cloud-api` 用不到它；放在 `cloud-api`，`panel-host` 的通知渠道又用不到。

## 决策

1. **平台内部分层。** `crates/panel-host` 是平台的底座，工作区依赖仍只能是 `protocol`；`crates/cloud-api` 建在它上面，只能依赖 `protocol` 与 `panel-host`。平台仍不依赖任何领域。`tools/check-core-boundary.py` 按 crate 分别检查。
2. **对外请求一套（`apsp_panel_host::http`）。** 出站客户端只有一种描述 `Outbound`（连接与总超时、只用 HTTPS、固定解析、解析器、产品标识）和一个构建方法；每个客户端一律不走代理、不跟随重定向、不重试、不带 Referer、不解压。需要跟随重定向的两处（发布下载、外部订阅抓取）本来就自己逐跳跟随并逐跳检查。有界读取、状态码到拒绝原因的映射与 `Retry-After` 的解析（带上下限）各一处；`cloud-api` 的传输层改用它们。守卫：`crates/` 中除 `http.rs` 外出现客户端构建即失败（Agent 一侧的 crate 是另一个程序，不在此列）。
3. **网络校验一套（`apsp_panel_host::net`）。** 公网地址判断、解析结果检查、TLS 建立与 TCP 拨号、URL 检查、主机名检查（带选项，各处接受的范围不变）都在这里；配置编译库用的主机名检查放进 `protocol`（只是一个函数，协议消息不变），平台用同一份。守卫：`net.rs` 以外使用标准库的地址分类方法或地址掩码即失败，两处有理由的例外逐条列明。
4. **通知投递一套（`apsp_panel_host::notifications::queue`）。** 平台的投递器负责一轮“认领 → 发送 → 记录”，按队列的 `Policy`（每轮认领多少、锁定还是租约、发送次数上限、翻倍或固定的等待及上下限、被暂缓的消息怎样处理）算出下次时间与是否放弃；各所有者只为自己的表实现 `Queue`。认领与结果只有平台能构造，队列无法另写一套循环。六个队列的规则原样保留（见 `docs/open-questions.md` 同日条目）；表暂不合并，合成一张表留到阶段 F。守卫：基线里带下次尝试时间的表都已登记为所有者的队列；每个 `Queue` 实现都已登记；改写尝试次数或下次时间的语句只在队列实现里；按尝试次数计算等待只在平台的投递器里。
5. **告警发件箱归观测。** `notification_outbox` 与告警的入队、投递代码迁到 `crates/observability`（`alerts::outbox`）；平台声明类型化接口 `notifications::outbox::Outbox`（设置变更时取消过时的待发消息、渠道页的投递统计、健康视图的积压数），由观测实现、应用层接线。此后平台不再读任何领域的表，维护期间暂缓通知的条件在观测里只有一处。越界清单 390 → 377。

## 后果

- 新的对外请求、地址判断与排队投递只能经这三套机制写，否则测试失败。
- 行为变化：OSV 通告、Hetzner、IP 质量刷新、网络工作台的数据源、Cloudflare 区域列表、专属地址的 DNS 接口与旧渲染器转发不再读取环境里的代理变量（生产容器没有代理变量）；后三处不再跟随重定向（它们的目标都不重定向）。声明的响应长度超过上限时先拒绝再读取，错误与原来相同。专属地址的转发与 DNS 接口在 TLS 后端无法启动时返回 502 或“无法连接 Cloudflare”，不再退回默认客户端（实际不会发生）。用户看到的文字与各处的上限都不变。
- 有四处主机名检查语义不同，没有并入（名称记录允许下划线、成员邮件只查字符集、外部订阅的出站主机、可达性目标的规范化）；扫描中发现的几处疑似缺陷照原样保留并记录，留给各自的功能修复。
- 不在本次：Cloudflare 三处与 Globalping 两处客户端、“服务器此刻是否可用”的判断、健康视图改为组合视图、保留期由所有者执行、几类小机制（审计写入、密码散列、短文本、金额、时间、随机码、Cookie、设置读取）。
