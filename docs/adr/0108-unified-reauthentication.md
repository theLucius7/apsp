# ADR 0108：统一的再次验证

状态：已接受。

## 背景

[ADR 0082](0082-control-center.md) 为高风险操作建立了统一的再次验证：请求守卫检查当前会话五分钟内的证明，缺失时返回 403，前端弹出共用的「再次验证身份」，可用 Passkey（[ADR 0059](0059-passkeys-and-proxy-user-access.md)）或密码加已启用的 TOTP 验证，然后重试原请求。

有几处没有接入，而是各自在表单里要求输入管理员密码和验证码，后端再单独校验：

- 生成代理用户开通链接 / 重置用户 Passkey；
- 绑定、删除管理员 Passkey；
- 开始设置、关闭二步验证；
- 修改登录密码；
- 自动化与维护页面、交互式终端各自复制了一份密码弹窗。

结果是同一件事有多套代码，而且这些地方不能用 Passkey 验证。用户反馈：生成开通链接时只能输密码，不能用 Passkey。

## 决策

- 以上接口全部改用请求守卫里的统一证明：`POST /api/security/password`、`/api/security/totp/setup`、`/api/security/totp/disable`、`/api/security/passkeys/register/start`、`/api/security/passkeys/{id}/remove` 列入“本人账号中需要证明的写入”；`POST /api/plugins/sing-box/users/{id}/portal/invitation` 列入插件高风险路由。处理函数不再读取密码或验证码，请求体去掉这些字段，带上旧字段的请求被拒绝（422）。
- 绑定、删除管理员 Passkey 和生成开通链接继续要求 `Origin` 与配置地址一致，这一检查原本随密码校验进行，现在单独保留。
- 修改密码不再要求输入当前密码：证明可以来自 Passkey，也可以来自当前密码。新密码仍不能与当前密码相同。
- 关闭二步验证不再单独要求验证码：用密码取得证明时，已启用的 TOTP 本来就要求一个尚未使用的验证码；用 Passkey 取得证明时不需要。因此丢失验证器但已绑定 Passkey 的管理员可以自行关闭二步验证；只有密码时仍不能关闭。
- 前端各表单删除密码和验证码输入框。提交时如果证明已过期，由共用对话框验证后自动重试；自动化与维护页面的“验证身份并…”按钮改为直接打开共用对话框，与备份页面一致。
- 不变的部分：登录、登录页的二步验证、确认启用二步验证时输入新验证器的验证码（证明的是新验证器，不是身份），以及代理用户门户自己的验证。

## 取舍

- **保留各处的密码表单，再加一个 Passkey 按钮：** 改动小，但多套代码还在，以后新增的地方还会再犯。未采用。
- **修改密码仍要求当前密码：** 常见做法，但只用 Passkey 的管理员就改不了密码；五分钟证明已经覆盖创建管理员、API 令牌这类同等风险的操作。未采用。

## 验证

- `guard` 单元测试覆盖哪些本人账号写入需要证明、哪些不需要；`integration_policy` 覆盖开通链接路由。
- `auth_security` 覆盖二步验证设置、关闭和修改密码：没有证明时返回 403，错误密码拿不到证明，启用 TOTP 后密码证明需要未使用的验证码，旧请求体被拒绝。
- `passkeys` 覆盖绑定、删除和开通链接需要证明、缺少 Origin 被拒绝、旧请求体被拒绝；浏览器虚拟认证器测试覆盖证明过期后在「生成开通链接」里用 Passkey 验证并生成链接。
- `portal-current-snapshot.mjs`、`operations-reconciliation.mjs` 按新表单和共用对话框更新。
