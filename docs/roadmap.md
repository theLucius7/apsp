## 一、定位

**apsp 是自托管的代理网络控制平面**：把分散在各家的 VPS 编成一张可靠的代理网络，入口、中转、落地一处配置，节点和订阅自动下发，流量按用户精确记账，面板离线不断网；每个用户可以自己登录查看订阅、用量与到期。服务器监控、费用与续费、线路质量是为这张网络服务的支撑能力。

后续一年的目标：**先把已经写出来的核心做成可信赖的版本，再取代玩家现在拼装的 Xboard、订阅工具、续费工具和转发面板，最后让 AI Agent 能安全地调用它。**

三条核心旅程：

1. **单机节点**：接入服务器 → 创建 Reality 与 Hysteria2 节点 → 创建代理用户并分配策略组与套餐 → 用户用 Passkey 登录门户、复制订阅 → 客户端连通 → 流量入账、门户显示正确 → 达到额度或到期后的行为符合说明。
2. **入口到落地的链路**：入口机 + 落地机，并用一个机场节点作为中间段 → 用户通过链路连通 → 流量只在入口计一次 → 落地机离线时收到告警。
3. **可靠性**：重启 Agent、重载 sing-box、面板停机一段时间 → 节点不中断，流量不重复、不丢失；面板备份后在新实例恢复，服务器自动重连。

## 四、工作方式

- **每个工作包一个 PR。** CI 恢复后不再整轮集中交付：每个工作包在独立分支完成实现、测试和文档，通过 CI 后合并。这需要更新 AGENTS.md 中的“一次交付”规则（决定 D8）。
- **先实现、后集中验证的节奏保留在工作包内。** 工作包完成后统一验证，失败只补验受影响范围。
- **签收用汇总表。** 每个版本一页 `docs/acceptance/v0.x.md`，列出旅程、环境、版本、结果和未通过项，取代长篇过程记录。
- **并行开发。** 互不重叠的工作包可以由不同会话或工作树同时进行，例如 2.1（编译器与订阅）与 3.1（账本）、3.3（线路质量）；合并顺序以里程碑为准。
- **准入规则。** 新需求先判断是否服务代理网络主线，不符合的进入第七节的候选池；降级和冻结功能只修缺陷与安全问题。
- **每个版本的指标。** 安装到第一个节点可用的时间、面板与 Agent 常驻内存、签收旅程数量、未关闭缺陷数。指标变差视为回归。

## 六、风险

| 风险 | 应对 |
| --- | --- |
| 验证跟不上开发，再次堆积“源码已实现、未签收” | 工作包以签收为完成标准；未签收的功能不进入发布说明 |
| 范围再次膨胀 | 准入规则写入 AGENTS.md；新方向必须先改功能地图与 ADR |
| 测试环境不足，只能在本机夹具上验证 | M0 先准备两台测试 VPS 与测试域名；生产机器不做反复验证 |
| 上游 sing-box 版本变化 | 固定版本，每个次版本评估一次升级，并跑完核心旅程 |
| 亲友不方便使用 Passkey（需要 HTTPS、支持的设备） | 决定 D5 提供可选的邮件验证码登录 |
| Xboard 数据与 apsp 模型不完全对应 | 迁移先预览、逐用户核对，保留原系统直到切换完成 |
| 公开推广的合规风险 | 对外使用“代理网络”“网络连接管理”等中性措辞，不做售卖功能 |
| 单人维护 | 文档与签收表保持当前可读；每个版本都能从文档重新部署和恢复 |

## 七、明确不做与候选池

| 不做 | 原因 |
| --- | --- |
| 与探针比主题、地图和展示效果 | 已商品化且有免费方案；看板保持清晰可用即可 |
| 通用运维面板（终端、文件、防火墙、组网、脚本编排） | 交给 SSH 工具和用户自己的 AI Agent |
| 机场售卖：注册、订单、支付、优惠券、邀请佣金、工单 | 定位是自用和小圈子；运营功能带来合规与维护负担 |
| 个人记账、预算和银行对接 | 费用账本只记录周期费用与续费 |
| 自研 AI 聊天或托管模型 | apsp 提供数据与受控操作即可 |
| 多内核代理（Xray 等） | sing-box 已覆盖主流协议，优先做好多客户端订阅 |

候选池（未排期，进入前须确定所属功能区、级别和验收旅程）：更多 DNS 提供方、面板高可用、移动端小组件、单二进制加 SQLite 的轻量部署形态。

## 八、市场依据

### 谁在长期玩服务器

- **机器多、厂商杂。** 有人十几台服务器分布在腾讯云、阿里云、netcup、甲骨文等多家厂商和零售商家，“不可能每次都去商家后台一个一个看”，还会忘记续费。
- **用途集中在代理网络。** 小机器主要用来做代理、中转、落地；玩家按线路机和性能机区分，线路机看回国延迟、丢包和用量。很多是几十到几百 MB 内存的 NAT / LXC 小鸡。
- **续费是独立的痛点。** 到期、价格、流量重置日分散在各家后台，论坛里有人专门搭配 Wallos、DueGuard 等工具来记录和提醒。
- **AI 成了新负载和新入口。** VPS 上大量出现 Hermes 等 AI Agent、AI 接口中转（CLIProxyAPI、sub2api）；运维越来越多地交给“AI + SSH”。

### 他们现在用什么

| 需求 | 主流选择 | 对 apsp 的启示 |
| --- | --- | --- |
| 探针与监控 | Komari、哪吒、Beszel，零成本的 CF-Server-Monitor | 已商品化，不正面竞争；只做代理网络需要的监控 |
| 节点面板 | 3x-ui、s-ui（单机），Marzban、Remnawave（多节点、偏运营） | 单机面板不管链路和多机记账；多节点面板基于 Xray、面向售卖 |
| 多人订阅管理 | Xboard、V2Board 一类机场面板，常被拿来给熟人自用 | 自用只需要用户、套餐、订阅、用量和自助查看；注册、支付、工单都是负担 |
| 订阅管理 | Sub-Store、妙妙屋 | 玩家要多客户端订阅，并混用机场节点 |
| 中转转发 | flvx、哆啦A梦（flux-panel）、nyanpass、realm | 入口 → 落地的转发与按规则计量是长期需求 |
| 续费与费用 | Wallos、DueGuard、探针自带的到期字段 | 需要一处记录所有周期费用并按时提醒 |
| 质量测试 | NodeQuality、融合怪、IPQuality、回程路由脚本 | 关注 IP 是否原生、流媒体与 AI 服务能否解锁、回程线路 |
| 运维操作 | Netcatty（自带 AI 运维 Agent）、Hermes、Muse | 通用运维交给它们；apsp 提供可调用、可审计的接口 |

### 2026-10-24 补充调研

本轮按论坛与竞品 issue 重新核对需求（论坛页面多数只能看到搜索摘要，日期按帖号推算，误差约一到两个月）：

- **空位仍在。** s-ui 维护者承认多服务器管理是该仓库最受期待的功能，但不打算做（[s-ui#729](https://github.com/alireza0/s-ui/issues/729)）。玩家仍在用单机面板、订阅工具、转发面板、探针和续费工具拼装。
- **订阅层的投入产出比最高。** 用户最常问的是客户端里看不到用量、到期和订阅名（[妙妙屋#13](https://github.com/iluobei/miaomiaowu/issues/13)，[NodeSeek：合租如何给人显示到期与剩余流量](https://www.nodeseek.com/post-601147-1)）；小白最常卡在客户端格式不兼容（[V2EX](https://www.v2ex.com/t/1227915)）。
- **信任成为选型理由。** 2026 年密集出现的安全事件包括：面板 Web 终端以 root 运行（[nezha#1202](https://github.com/nezhahq/nezha/issues/1202)）、订阅工具的未授权远程执行（[Sub-Store#634](https://github.com/sub-store-org/Sub-Store/issues/634)）、面板内的赞助横幅（[3x-ui#6844](https://github.com/MHSanaei/3x-ui/issues/6844)）。
- **用户抵触膨胀。** 有用户请求探针停止扩展路线（[Komari#613](https://github.com/komari-monitor/komari/issues/613)）。首页应先显示待办与异常，导航要精简。
- **计量方式。** 用倍率表达线路成本差在多节点与转发面板中很常见（[Remnawave#222](https://github.com/remnawave/panel/issues/222)）。apsp 在额度评估层折算倍率，原始账本保持精确。

### 结论

1. 没有开源项目同时提供“多服务器 sing-box + 入口 / 中转 / 落地链路 + 逐用户精确记账 + 服务器与费用感知”，这是 apsp 的空位，也是它最初的设计重心。
2. 玩家现在用节点面板、Xboard 类面板、订阅工具、转发面板和续费工具拼出这套能力。apsp 应把与代理网络相关的部分合成一套，而不是复制每个工具的全部功能。
3. 安全是选型理由：Agent 最小权限、默认不开放远程执行，应成为默认行为。
4. AI 是新入口：面板要成为 AI 可调用、可审计的数据与操作源，而不是自己做运维工具。
