# 后续路线图

- 状态：**提议**，2026-10-24 起草，同日按 [ADR 0087](adr/0087-narrow-positioning-proxy-network.md) 收窄定位后修订。各阶段的优先级、时间和授权由用户确认后执行；涉及范围变更的事项列在第五节，确认后转为 ADR 或 AGENTS.md 规则。
- 方向依据市场和社区，而不是现有代码：NodeSeek、LINUX DO、V2EX 的近期讨论，以及同类开源项目在 GitHub 上的功能、活跃度和安全公告（数据截至 2026-10-24），出处见文末。

## 一、定位

**apsp 是自托管的代理网络控制平面**：把分散在各家的 VPS 编成一张可靠的代理网络，入口、中转、落地一处配置，节点和订阅自动下发，流量按用户精确记账，面板离线不断网；每个用户可以自己登录查看订阅、用量与到期。服务器监控、费用与续费、线路质量是为这张网络服务的支撑能力。功能分级见[功能地图](product-map.md#功能分级)。

## 二、市场依据

### 谁在长期玩服务器

- **机器多、厂商杂。** 有人十几台服务器分布在腾讯云、阿里云、netcup、甲骨文等多家厂商和零售商家，“不可能每次都去商家后台一个一个看”，还会忘记续费。
- **用途集中在代理网络。** 小机器主要用来做代理、中转、落地；玩家按线路机和性能机区分，线路机看回国延迟、丢包和用量。很多是几十到几百 MB 内存的 NAT / LXC 小鸡。
- **续费是独立的痛点。** 到期、价格、流量重置日分散在各家后台，论坛里有人专门搭配 Wallos、DueGuard 等工具来记录和提醒。
- **AI 成了新负载和新入口。** VPS 上大量出现 Hermes 等 AI Agent、AI 接口中转（CLIProxyAPI、sub2api）；运维越来越多地交给“AI + SSH”。

### 他们现在用什么

| 需求 | 主流选择 | 对 apsp 的启示 |
| --- | --- | --- |
| 探针与监控 | Komari、哪吒、Beszel，零成本的 CF-Server-Monitor | 已商品化，不正面竞争；只做代理网络需要的监控 |
| 节点面板 | 3x-ui、s-ui（单机），Marzban、Remnawave（多节点、偏运营） | 单机面板不管链路和多机记账；多节点面板基于 Xray、面向售卖 |
| 多人订阅管理 | Xboard、V2Board 一类机场面板，常被拿来给熟人自用 | 自用只需要用户、套餐、订阅、用量和自助查看；注册、支付、工单都是负担 |
| 订阅管理 | Sub-Store、妙妙屋 | 玩家要多客户端订阅，并混用机场节点 |
| 中转转发 | flvx、哆啦A梦（flux-panel）、nyanpass、realm | 入口 → 落地的转发与按规则计量是长期需求 |
| 续费与费用 | Wallos、DueGuard、探针自带的到期字段 | 需要一处记录所有周期费用并按时提醒 |
| 质量测试 | NodeQuality、融合怪、IPQuality、回程路由脚本 | 关注 IP 是否原生、流媒体与 AI 服务能否解锁、回程线路 |
| 运维操作 | Netcatty（自带 AI 运维 Agent）、Hermes、Muse | 通用运维交给它们；apsp 提供可调用、可审计的接口 |

### 竞品的走向

| 项目 | GitHub 星标 / 最近更新 | 值得注意的方向 |
| --- | --- | --- |
| 3x-ui / s-ui | 约 4.8 万 / 约 1 万 | 单机节点面板的事实标准 |
| Remnawave / Marzban | 约 5200 / 约 7500 | 多节点、Xray、偏运营 |
| Sub-Store / 妙妙屋 | 约 1.1 万 / 约 1100 | 多客户端订阅；妙妙屋读取哪吒、Komari 的流量数据 |
| Beszel / 哪吒 / Komari | 约 2.6 万 / 约 1.0 万 / 约 6500 | 哪吒已加入 MCP 接口及审计；哪吒与 Komari 都公布过高危或密集的安全公告 |
| CF-Server-Monitor | 约 2700 | Cloudflare 免费托管；Agent 只单向上报、可非 root 运行；三网延迟、到期提醒 |
| Wallos | 约 8700 | 自托管订阅费用记录：周期、多币种、分类、通知、统计 |
| CLIProxyAPI / sub2api | 约 5.6 万 / 约 4.5 万 | AI 接口中转成为 VPS 上的热门负载 |

### 结论

1. 没有开源项目同时提供“多服务器 sing-box + 入口 / 中转 / 落地链路 + 逐用户精确记账 + 服务器与费用感知”，这是 apsp 的空位，也是它最初的设计重心。
2. 玩家现在用节点面板、订阅工具、转发面板、探针和续费工具拼出这套能力。apsp 应把与代理网络相关的部分合成一套，而不是复制每个工具的全部功能。
3. 安全是选型理由：Agent 最小权限、默认不开放远程执行，应成为默认行为。
4. AI 是新入口：面板要成为 AI 可调用、可审计的数据与操作源，而不是自己做运维工具。

## 三、路线图

### 阶段 1：收窄与可用（v0.4，约 1–2 个月）

| 事项 | 完成标准 |
| --- | --- |
| 界面按分级调整 | 「代理服务」移到侧栏第一组，登录后的默认首页可选服务概览；降级功能标“实验”，冻结功能默认隐藏（系统设置中可显示）；远程命令、终端、文件操作默认关闭，按服务器显式开启 |
| 核心旅程实机签收 | 在专用测试机上跑通下面三条旅程，全部通过才发布 |
| 最小权限 Agent | 公开 Agent 常驻内存；未开启运维能力时 Agent 只做上报、对账和运行时管理；评估非 root 运行 |
| 恢复交付管线 | 恢复 CI；面板与 Agent 发布 v0.4.0 已签版本，发布说明按功能分级组织 |

三条核心旅程：

1. **单机节点**：接入一台服务器 → 创建 Reality 与 Hysteria2 节点 → 创建代理用户并分配策略组与套餐 → 用户用 Passkey 登录门户、复制订阅 → 客户端连通 → 代理流量入账，门户显示正确 → 达到套餐额度或到期后的行为符合说明。
2. **入口到落地的链路**：入口机 + 落地机，并用一个机场节点作为中间段 → 用户通过链路连通 → 流量只在入口计一次 → 落地机离线时收到告警，订阅中的链路状态正确。
3. **可靠性**：重启 Agent、重载 sing-box、面板停机一段时间 → 节点不中断，流量不重复、不丢失；面板备份后在新实例恢复，服务器自动重连。

### 阶段 2：取代拼装的工具（v0.5，约 2–3 个月）

目标是让玩家不再需要 Xboard 类面板、订阅工具、转发面板和续费工具来补 apsp 的空缺。

| 事项 | 完成标准 |
| --- | --- |
| **多客户端订阅** | 同一份节点与授权输出给 mihomo / Clash、Shadowrocket、Surge、sing-box 等客户端（**需解除现有“不提供 Clash 订阅”的限制**）。这是完全取代 Xboard 类系统的前提 |
| **代理用户门户补齐** | 用户自行登录后能看到：各客户端的订阅链接与二维码、本期与累计用量、套餐额度、到期与重置日、可用节点及状态、客户端使用说明；可自行重置订阅链接、管理自己的 Passkey；到期前和流量将尽时通过邮件或 Telegram 提醒用户本人；管理员可发布简单公告 |
| **从 Xboard 类系统迁移** | 读取原系统的用户、套餐、到期、已用流量与节点授权，预览后导入；保留用户的代理凭据（UUID / 密码），客户端重新获取订阅即可继续使用；按需提供旧订阅地址兼容；迁移前后逐用户核对用量与到期。具体依赖原系统的版本与数据结构 |
| **费用与续费账本**（Wallos 式） | 「总览 → 费用与续费」统一列出服务器、域名、机场订阅和手动添加的任意服务；每项记录金额、币种、周期、下次续费、自动续费标记、分类与备注；付款、续费、退款、调价与退订形成历史记录；按显示币种汇总月度与年度支出，提供即将到期列表和续费日历；提醒经现有 Telegram / Webhook 渠道投递，每项可设提前天数；支持导入导出。复用现有资产设置、运维费用账本、退订提醒、到期提醒和每日汇率，不接入支付，不自动续费或退订 |
| 中转规则 | 入口机 → 落地机的转发规则，按规则计流量，可设额度与到期，可作为链路的一段（**需确认转发范围**） |
| 线路质量中心 | 按入口、中转、落地角色展示三网延迟与丢包长期曲线、回程路由、IP 质量与流媒体及主流 AI 服务的解锁状态，并有历史对比；合并网络检测中的基础探测与路由追踪 |
| 合并重复模型 | 服务器资产设置与运维资产档案合并为一份资产记录，作为费用账本中服务器项目的来源 |

Xboard 功能在 apsp 中的对应：

| Xboard | apsp | 处理 |
| --- | --- | --- |
| 用户、套餐、权限组 | 代理用户、套餐、策略组 | 已有；迁移工具负责映射 |
| 节点与节点后端 | 节点、链路，由 Agent 与 sing-box 承载 | 已有；节点需在 apsp 中重新创建或由迁移工具生成草稿，不沿用原节点后端 |
| 流量统计与重置 | 逐用户流量账本、套餐重置周期 | 已有 |
| 多客户端订阅 | 订阅输出 | 阶段 2 补齐 |
| 用户中心 | 代理用户门户 | 阶段 2 补齐 |
| 公告 | 门户公告 | 阶段 2，只做简单公告 |
| 到期与流量提醒（邮件 / Telegram） | 用户提醒 | 阶段 2 |
| 注册、订单、支付、优惠券、邀请佣金、工单、知识库 | — | 不做 |

### 阶段 3：AI 可调用（v0.6，约 2 个月）

| 事项 | 完成标准 |
| --- | --- |
| 只读 MCP 接口 | AI Agent 可读取节点、链路、用户用量、告警、线路质量、即将到期的续费项目；沿用 API 令牌的服务器范围与审计 |
| 受控的 AI 操作 | 只开放固定的业务操作：发布配置、重试部署、暂停或恢复代理用户、记录一笔续费；高风险操作要求管理员二次确认，全部写入审计；不开放任意命令 |
| 冻结功能评估 | 逐项决定移除、拆为独立插件或保持冻结；移除需用户单独授权 |

### 持续进行

- **轻与快**：每个版本公布面板与 Agent 的内存、安装时间和首屏时间，变差视为回归。
- **社区**：在 NodeSeek、LINUX DO 发布版本说明，对外措辞使用“代理网络”“网络连接管理”。
- **安全**：每个版本附安全变更说明；制品保持签名和可复现记录。

## 四、明确不做

| 方向 | 原因 |
| --- | --- |
| 与探针比主题、地图和展示效果 | 已商品化且有免费方案；看板保持清晰可用即可 |
| 通用运维面板（终端、文件、防火墙、组网、脚本编排） | 交给 SSH 工具和用户自己的 AI Agent |
| 机场售卖：注册、订单、支付、优惠券、邀请佣金、工单 | 定位是自用和小圈子；这些运营功能带来合规与维护负担 |
| 个人记账、预算和银行对接 | 费用账本只记录周期费用与续费，不做通用财务 |
| 自研 AI 聊天或托管模型 | apsp 提供数据与受控操作即可 |
| 多内核代理（Xray 等） | sing-box 已覆盖主流协议，优先做好多客户端订阅 |

## 五、需要用户决定

| 问题 | 建议 | 影响 |
| --- | --- | --- |
| 是否解除“不提供 Clash 订阅”的限制 | 解除，统一做多客户端订阅输出 | 修改 AGENTS.md 与 ADR 0076 的范围约束 |
| 中转规则做到什么程度 | 做“入口 → 落地”的规则、计量与限额，不做售卖 | 修改转发相关范围约束，复用网络配置的执行与回退 |
| 原 Xboard 类系统的具体信息 | 提供仓库或版本、数据库结构，以及是否需要保留旧订阅地址 | 决定迁移工具的读取方式和兼容路由 |
| 代理用户是否需要密码或邮件登录 | 保留 Passkey 为主，增加可选的邮件验证码登录，照顾不方便用 Passkey 的亲友 | 新增登录方式与限速；Passkey 要求 HTTPS 域名 |
| 费用账本是否允许与服务器无关的任意项目 | 允许（AI 订阅、域名、机场等），但只记录周期费用，不做预算 | 新增数据模型与迁移，需要 ADR |
| 登录后的默认首页 | 改为服务概览，看板保留为独立入口 | 修改默认路由，公开看板不受影响 |
| 冻结功能何时移除 | 阶段 3 逐项评估，移除前单独授权 | 可能删除接口、表与 Agent 能力 |
| 是否开放 MCP | 先只读，写操作在阶段 3 后半再开 | 新增接口与审计范围 |
