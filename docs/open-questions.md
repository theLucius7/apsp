# 执行中的问题与选择

## 2026-11-14：阶段 F 第六步（成本的云状态迁出资源的行）的取舍

- 问题：按 ADR 0137 的顺序，成本写在云账号与云资源行上的列迁到成本自己的表；作业的列留给第七步。
- 选择：
  - **两张表 `cloud_account_billing`、`cloud_resource_billing`**（沿用分析时的命名，而不是 `alicloud_*`：它们记的是成本对云账号的读数，不是云账号本身）；没有行即原来的默认值。`error_code` 一直只存账单读取的错误，迁过去改名 `bill_error`。
  - **刷新时间与修订号留在资源。** `next_run_at`、`last_attempt_at` 是同一轮刷新（快照、账单与 CDT、自动带宽）的调度，由作业的工作循环运行、资源认领；账单读取失败照旧推迟整轮（改经 `inventory::defer_refresh`），节奏不变。成本在账号锁下经 `inventory::current_account` 核对资源的修订号：账号表单的保存会递增它，电源作业与 CDT 守护也以它为键；另起一个成本的修订号就要资源在每次编辑时去递增它。
  - **`limit_gb` 与自动化开关留到第七步。** 它们是自动带宽的阈值与开关，只有 `billing::exceeded` 读取，属于作业。
  - **明文密钥的旧模式删除。** 生产只读核对：3 个账号都有凭据引用、没有一个存有明文密钥；按 ADR 0131 删除两列、接口字段 `access_key_id`、`access_key_secret`、`legacy_credentials`（现在按未知字段拒绝）、云客户端的明文回退与界面的兼容模式；没有引用的账号调用云接口时报 `credential_unavailable`。接入脚本在仍存有明文密钥时拒绝执行。
  - **独立审阅的小注（只读审阅，接受不改）：** 两个云视图先读账号与资源、再读成本的行，中间提交的编辑可能让一次响应里的账单与修订号不同步（只影响显示，从该视图保存会因修订号冲突而失败，下一次轮询即恢复）；云资源观察在取得观察锁之前、事务之外读取实例账单，历史记录里的账单可能比快照稍旧（下一轮修正）；没有凭据引用的账号报 `credential_unavailable`（原来是 `credential_invalid`，只有已归档的账号会这样，没有代码按它分支）；接入脚本在加表锁之前读、之后写两张基线记录表（之前的脚本也如此，运行时没有冲突的锁）。

## 2026-11-14：三处保留缺陷的修法

- 问题：ADR 0134 合并出站机制时记下、留给各功能修的缺陷，用户要求“处理其他任务修复完成”。
- 选择：
  - **URL 里的主机统一经 `net::url_host` 取出**（只去掉 IPv6 字面量的方括号）：网络工作台的 URL 检查、目标比对、出口发现的本机代理检查与 HTTP 探测原来各自处理或没有处理方括号。原来接受的地址照样接受；`[::]` 与组播仍拒绝。
  - **工作台数据源与外部订阅抓取用同一条出站规则**：先解析，再用 `net::check_resolved` 按 `net::egress_ip` 逐个检查，连接固定到检查过的地址。被拒绝的地址记为“资料源地址解析到回环、内网或保留地址，面板不会连接”，不重试；解析或连接失败照旧重试。生产中没有保存的数据源。
  - **外部节点的主机在转换为 ASCII 后按 RFC 1123 查总长度**（服务器、SNI 与传输层 Host），超长的节点与其他不合法的主机一样记为不支持的节点，抓取本身不失败。不提高解析器的版本号，否则已有版本会被当作不是最新、影响新的授权。生产中保存的 1716 个版本里没有会被拒绝的主机（最长 47 字节）。

## 2026-11-14：阶段 F 第五步（流量服务的发布状态迁出 `servers`）的取舍

- 问题：按 ADR 0137 的顺序，流量服务写在 `servers` 上的发布修订号与待发布标记迁到流量服务自己的表，`server_plugins` 按对象改名。
- 选择：
  - **一张 `runtime_publications`，列名不变。** 修订号与待发布标记总是一起读写；没有行即修订号 0、无待发布。流量服务的 `publications.rs` 是“待发布 / 当前修订号”唯一的回答处，服务权益与作业用它给出的 SQL 片段。
  - **运行时存模块标识 `singbox`。** 其他模块列、能力名与设备清单的键本来都用 `singbox`；只有迁移预览的 `related.plugins` 把它映射回界面显示的 “sing-box”，Agent 协议从不携带这个值。
  - **资源经新接口 `ServerRuntime` 取修订号与运行时**（资源排在流量服务之前，不能直接读流量服务的表）：服务器列表、详情、修改、看板、导出与迁移预览的 JSON 不变。
  - **发布器对服务器行只取 `FOR KEY SHARE`**，再以 `FOR UPDATE SKIP LOCKED` 锁自己的发布行；标记待发布也只取 `FOR KEY SHARE`。发布锁 73201001 不变；行锁守卫的例外 4 → 2。
  - **`runtime_control_requests` 只加索引，不加保留期**：检查点按期望修订号查找由并行顺扫（生产数据副本约 13 ms）变为索引扫描（约 0.3 ms）；保留期会删除数据，另行决定。
  - **独立审阅发现并已修正：** 发布事务的预检路径原来对服务器行取 `FOR UPDATE`；发布的认领改为 `FOR KEY SHARE` 后，这把锁在可重复读快照里会因 Agent 每条消息都写的联系时间而序列化失败，原生服务器的发布可能一再失败。预检读取改为由调用方给锁强度：发布器用 `KEY SHARE`，控制台的预检请求与首次安装仍用 `FOR UPDATE`；回归测试在发布器取得快照后提交联系时间的更新，发布照常完成。
  - **接受的差别：** 发布器的可重复读事务里，删除恰好在取锁前提交时不再强制重试，最坏多出一条已删除服务器的部署记录；发布器会等候短暂以 `FOR UPDATE` 持有服务器行的写入（资产编辑、删除等），而不是跳过；接入脚本拿到 `servers` 的锁后要等 `runtime_control_requests`，与旧面板的事务可能互相等待，PostgreSQL 会中止一方，若中止的是脚本，部署下一分钟重试；修改与删除服务器的审计快照少了修订号与待发布标记（同第四步）。

## 2026-11-14：服务器状态三处语义差别与几处越界的取舍

- 问题：ADR 0136 留下三处语义差别等产品决定；用户把决定交给执行者（“你来合并，然后继续，处理其他任务修复完成”）。另有几处只改代码就能去掉的越界。
- 选择：
  - **都按控制台显示的含义统一。** 计费周期：资产编辑与服务器页对从未保存的计费周期显示“/ 30 天”，成本账本却当作一次性；账本改用资源的类型化默认值（与 `AssetSettings::default()` 共用一个常量），保存为 0 的仍是一次性。网卡：设置页写明“留空统计所有网卡；支持 * 和 ! 排除，逗号分隔”（占位 `eth*,!eth1`，`docs/server-assets.md` 写明排除优先），服务器页、周期流量与告警本来就按这个含义匹配，只有统计按整串精确匹配，填了模式或列表的服务器在统计里整台消失；统计改用资源的同一个匹配函数。故障的“维护中”改用暂缓通知的同一判断，服务器自己的维护期也算。
  - **生产当前不受前两项影响**（2026-11-14 只读核对）：18 台在用服务器都保存了计费周期，网卡设置都为空。
  - **流量服务的部署预检不新开接口。** 平台已有的 `DeviceWork`（作业回答）本来就回答“设备能否接收任务”并提供预检观察，加 `closed_tx` 与 `operation_tx` 两个方法比由流量服务另声明一个接口改动小，也符合 §5.5“向设备派发任务的接口由平台声明一次”。
  - **作业的终端与核对改用治理的函数**（`pin_session_tx`、`pin_recent_proof_tx`、`session_active_sql`）：报错文字与加锁顺序不变，终端控制仍是一条语句。
  - **基础网络迁移的事件改经 `Evidence` 写入**：与其他事件一样记来源 `panel`、在写入时取时间（原来记 `network_server_migration`）；类型与内容不变，只在“历史”里查看原始事件时可见。
- 余下：`naming/acme.rs` 仍读 `network_documents`；名称的证书部署、基础网络的配置与迁移计划经联结读作业的 `fleet_operations`（之后可改用 `operation_tx`）；部署预检仍读资源、基础网络与名称的表；首次安装的检查原来写 `servers.manifest_rev`，已随阶段 F 第五步改经流量服务的发布表。

## 2026-11-14：阶段 F 第四步（观测的列迁出 `servers`）的取舍

- 问题：按 ADR 0137 的顺序，观测写在 `servers` 上的遥测设置、最新指标、采样时间、拨测分配的修订号与指纹、IP 质量的刷新租约迁到观测自己的表。
- 选择：
  - **三张表而不是一张。** 遥测（设置与最新指标，每批更新）、拨测分配（修订号只增，Agent 依赖它）与 IP 质量的刷新租约（只在刷新时存在）写入频率与生命周期不同；都以服务器编号为主键，没有行即默认值。
  - **外键随服务器删除级联。** 服务器只做软删除（`deleted_at`）；真正删除行时这些状态也没有意义。已删除服务器的值照样复制。
  - **遥测批次对服务器行取 `FOR KEY SHARE`。** 资源的行锁新增这一强度（`RowLock::KeyShare`，第五步的发布也会用到）：仍与删除及以 `FOR UPDATE` 锁服务器行的写入串行，不再挡联系时间的更新，也不再改写服务器行。
  - **服务器导出从治理移到应用层**（`crates/panel/src/server_export.rs`）：它联结资源与观测的数据，而治理排在两者之前；地址 `/api/control-center/export/servers` 与权限不变。
  - **审计快照少了这几项。** 修改与删除服务器的审计“修改前”快照（`to_jsonb(servers)`）不再含遥测设置、拨测修订号与指纹、最新指标。修改服务器本来不改这些值，遥测设置的修改走自己的接口；只是删除记录里不再看得到被删服务器的遥测设置。
  - **独立审阅发现、接受不改的差别**（只读审阅，2026-11-14）：遥测设置的修改与删除服务器同时发生时，原来返回 404，现在返回 200 并写入已删除服务器的设置（没有读者）；不带采样时间的旧版指标上报不再与告警评估串行（最坏情况是该轮评估跳过这台服务器，只有旧 Agent 会这样上报）；首次写入遥测行与采集迁移在理论上可能互相等待（接入后每台服务器都有这一行，PostgreSQL 也会检测并中止一方）；批次的 `FOR KEY SHARE` 与联系时间的更新重叠时会产生 MultiXact（只影响清理，引用服务器的外键插入本来也会这样）。

## 2026-11-14：前端重复合并的取舍

- 问题：用户要求按顺序继续，前端重复是第三项。合并必然改变一些页面的显示（文字、位数、样式），按惯例以附截图的 PR 交付，由用户审阅。
- 选择：
  - **以较新的共用实现为准。** 提示用 `ErrorNotice` 与面板 `Notice`，用量条用 `Meter`，状态用 `Badge`；时间、字节、金额、数字统一在 `format.ts`；当前管理员统一经 `lib/actor.ts`（应用只挂一个 30 秒轮询，打开页面不再各自请求）；输入校验统一在 `lib/validate.ts`。

  - **字节统一用共用的 `bytes()`，截断到一位小数**（原来几处是四舍五入，例如 412.37 GiB 由 412.4 变为 412.3）。共用实现的测试写明了原则：读数从不多报已用量（用量与配额不会在未用满时显示为已满）；四舍五入的那几处是与这条原则不一致的副本。用户把决定交给执行者后，保留截断。
  - **云凭据引用的输入更严格**：要求 v1–v5 的 UUID（面板生成的引用本来就是这种格式）。
- 余下：见 architecture.md §12.2“前端的重复（余下）”。

## 2026-11-14：阶段 F 第一步的取舍（ADR 0137）

- 问题：用户要求按顺序继续，阶段 F 是第一项。§12 列的几项“合成一张”里有的并不是同一对象；结构指纹含列的物理序号，删中间列的步骤做不了。决策见 [ADR 0137](adr/0137-phase-f-data-ownership.md)。
- 选择：
  - **先改指纹，再迁列。** 指纹改按未删除列的序号计算，与第一步一起接入，少停一次面板。
  - **第一步只放低风险的三件**：指纹、设备会话分表、服务权益审计流水合一。迁 `servers` 与云资源的列风险更高，各自单独一个 PR；流量服务那部分等作业胶水迁完之后再做。
  - **会话表暂不改名。** 改名会让接入与换镜像之间的旧面板认不出管理员会话，运维文档里也有按表名写的命令；以后单独改。
  - **审计流水按同一事件合并名称。** 口令登录与通行密钥登录都记为 `security_portal_login`，用 `authentication` 区分；其他动作名保持原样，对象编号写进 `detail`。
  - **不合并的照实记录**：预览存储、另三份事件日志、投递表（理由见 ADR 0137）。
- 待用户决定：资产重复合并时，未关联服务器的云资源是否保留“采购金额与到期”（生产从未使用；去掉属于移除功能）。

## 2026-11-14：流量服务里的作业胶水迁到作业的取舍

- 问题：用户要求按顺序继续（“continue，依次”）。部署自动化、分批升级与运行时操作的记录是作业的执行工作，却写在流量服务里并直接读写作业的表。
- 选择：
  - **作业编排，流量服务回答合法性。** 作业排在流量服务之后，可以直接调用流量服务公开的函数（目标配置、候选是否仍是当前、检查点是否已核实、重试是否可行等），不需要新的接口；原来跨两个领域的语句拆成作业与流量服务各自的部分，仍在同一个事务里执行，检查顺序、错误文字与返回的 JSON 不变。
  - **两处时序上的细微差别接受。** 结果未知时请求检查点的流程里，历史记录的插入改在“标记为不健康”之后（调用方已持有作业行锁，无并发影响）；分批升级的成员视图只读已记录的检查结果，不再回退读运行中的运行时操作（两者只在同一瞬间提交的结果上可能不同）。
- 余下：部署预检与首次安装的检查还有 3 条 SQL 读作业的表，见 architecture.md §12.1。

## 2026-11-13：底层机制统一第四部分——服务器状态与小机制的取舍（ADR 0136）

- 问题：服务器状态的判断分散在作业、流量服务、观测、成本与服务权益里，十几类小机制各有几份。决策见 [ADR 0136](adr/0136-server-state-and-small-mechanisms.md)。
- 选择：
  - **判断给成 SQL 片段，由所有者提供。** 这些判断都嵌在更大的查询与事务里，改成函数调用会多出往返并改变事务里的读取时点；所以资源（退役、生命周期、维护期、行锁、资产设置）与作业（维护窗口、拒绝新任务）提供 SQL 片段与加锁函数，调用方拼进自己的语句。守卫保证这些写法只出现在所有者里。
  - **语义不同的照实保留。** 成本账本对未保存的计费周期、统计对网卡名的匹配方式、故障列表的“维护中”标记各有一种含义，合并会改变显示或通知；记入 architecture.md §12.2，等产品定下一种含义。“服务器忙”在几处含义不同（排队操作是否过期、是否包括运行时操作），不是同一个判断。
  - **修正一处并发缺陷。** 创建链路时在加锁的同一条语句里检查退役，等锁期间提交的退役会被漏掉；改为与其他各处相同的“先加锁、再读退役状态”。这是缺陷修正，不是新行为。
  - **随机源统一为操作系统的随机源。** 原来有的用线程随机数生成器；取值的字母表、长度与分布不变。
  - **单行设置表的版本更新不合并。** 五张表的版本列名、语句形式、冲突处理与提示文字都不同，共用一个辅助函数需要拼接 SQL，得不偿失。
- 待产品决定：上面三处语义差别各采用哪一种。

## 2026-11-13：底层机制统一第三部分——健康视图、保留期与供应商客户端的取舍（ADR 0135）

- 问题：健康视图与保留期都是治理替其他领域做事；Cloudflare 与 Globalping 的几份客户端规则各不相同。决策见 [ADR 0135](adr/0135-health-retention-vendor-clients.md)。
- 选择：
  - **健康视图放应用层，而不是给治理加接口。** 另一种做法是治理声明一个“积压摘要”接口由各领域实现；但健康页本来就是几个领域的组合，与全局搜索、云页面总览同类，放应用层不需要新接口，治理也只剩自己的面板状态。
  - **保留期由所有者执行，一个所有者一个事务。** 原来一轮一个事务，一处失败会让其他领域的清理一起回滚；现在各自独立，失败的下一分钟重试。保留时长与删除的内容不变。作业没有合适节奏的现成任务，新增 `operations-retention`；观测与治理放进已有的任务。
  - **专属地址经名称写 DNS 记录。** DNS 记录是名称领域的对象，服务权益排在名称之后，可以直接调用名称公开的函数；这样只有一个 Cloudflare 客户端，提示文字仍由服务权益自己给出。
  - **Globalping 以观测那份为基础。** 它有令牌、限额、轮询与测试替身；更换 EIP 的检查守着一次真实的地址释放，用参数逐项保留原来的语义，并保留它自己的测试。
- 后续可做：服务权益两处直接读 `record_retention_policy`、观测的遥测存储写 `monitoring` 行，可以改经治理的保留期接口（第四部分）。

## 2026-11-13：底层机制统一第二部分——对外请求、网络校验与通知投递的取舍（ADR 0134）

- 问题：用户在第一部分上线后说“continue”。这一批要统一的三类机制都跨平台的两个 crate 与多个领域，需要先定平台内部的层级，再逐项决定默认行为。决策见 [ADR 0134](adr/0134-outbound-network-and-delivery.md)。
- 选择：
  - **`cloud-api` 建在 `panel-host` 之上，而不是反过来或合并成一个 crate。** 对外请求、地址判断是所有对外通信的底座，通知渠道（平台）与供应商接口（`cloud-api`）都要用；放在 `panel-host`、让 `cloud-api` 依赖它，改动最小。反过来会让底座依赖供应商的签名代码；合并会把阿里云签名等供应商细节搬进底座，也要改所有引用路径。
  - **每个出站客户端都不走代理、不跟随重定向、不重试。** 逐处看过：需要跟随重定向的发布下载与外部订阅抓取本来就自己逐跳跟随并逐跳检查地址；改变默认值的七处（OSV、Hetzner、IP 质量、工作台数据源、Cloudflare 区域列表、专属地址的 DNS 接口、旧渲染器转发）目标都不重定向，生产容器也没有代理变量。一种安全的默认值比每处各选一次更不容易出错。
  - **校验函数带选项，各处接受的范围不变。** 主机名、URL 的几份实现接受的范围不同，有的差别像是缺陷。合并时不顺手修：改变接受范围会让已保存的数据或用户输入突然不合法，应该由各自的功能决定。语义不同的四处主机名检查没有并入，见 architecture.md §12.2。
  - **投递器是平台的一个 trait 加一份策略，而不是一张共用的表。** 合表要改基线（阶段 F）；先让六个队列共用一套“认领 → 发送 → 记录”与重试计算，表保持不变。各队列的规则原样保留：告警发件箱与云资源通知（锁定认领、8 次、30 秒起翻倍至多 7 次、等待 1 秒至 1 天）；续费提醒与中国可达性告警（租约 120 秒、5 次、30 秒起、30 秒至 1 天）；故障通知（一次 4 条、租约 300 秒、5 次、被暂缓的推迟 60 秒）；代理用户账号提醒邮件（租约 120 秒、5 次、固定 300 秒）。
  - **告警发件箱经接口接回平台。** 平台的设置与渠道页面、健康视图仍要“取消过时的待发消息”“看投递统计”“看积压”，由平台声明 `Outbox`、观测实现；这样平台不读任何领域的表，维护期间暂缓通知的条件也只在观测里留一处。
- 发现但保留的问题（各自的功能修复时处理）：网络工作台的 URL 检查不接受 IPv6 字面量；工作台的数据源抓取管理员配置的地址时不做公网检查；Cloudflare 区域列表与专属地址的 DNS 接口读取响应时没有大小上限；外部订阅的出站主机在 IDNA 转换后不查长度；发布下载对 IPv4 映射的 IPv6 地址按其中的 IPv4 判断（现在是写明的调用处规则）。（2026-11-14：Cloudflare 的读取上限已随 ADR 0135 的单一客户端解决；工作台的 IPv6 字面量、数据源的公网检查与外部节点主机的长度已修，见当日条目；发布下载的规则保留。）
- 未做：Cloudflare 三处与 Globalping 两处客户端、服务器可用判断、健康视图组合与保留期由所有者执行、几类小机制（architecture.md §12）。

## 2026-11-13：底层机制统一第一部分——咨询锁与后台任务的取舍（ADR 0133）

- 问题：用户说明“目前是底层原理深度统一”。architecture.md §12 列着十几类重复实现，先做哪一类、统一到哪一层、守卫怎么写，需要逐项选择。决策见 [ADR 0133](adr/0133-one-implementation-per-mechanism.md)，这里记取舍。
- 选择：
  - **先做咨询锁与后台任务。** 二者贯穿所有领域、行为可以保持不变，而且是后面几项的地基：保留期改由各所有者执行要靠统一的周期任务，健康视图改成组合视图要靠统一的心跳。对外请求同样底层，但平台的两个 crate 只能依赖 `protocol`，统一要先改层级规则，放到第二部分。
  - **锁键由领域声明，平台只给机制。** 平台不能出现领域用语，一张集中在平台的锁键表就写不出“发布”“DNS 写入”这样的名字；把号码与用途放在所有者的 `src/locks.rs`，由应用层的测试汇总核对唯一性，与路由、后台任务的组合方式一致。
  - **管理员偏好锁改号，其余号码不动。** 它是唯一的无意共用（1 号管理员与“新建或修改管理员”同一把锁），改成两整数键后不可能再与 64 位键相撞；其他号码改动只会带来风险，没有收益。两处有意共用（DNS 写入、发布锁与兼容桥的基线函数）在声明处写明。
  - **每个后台任务都报心跳。** 另一种做法是只给原来就有心跳的任务用执行器，那样“哪些任务该有心跳”仍要逐个判断，健康视图也看不见六个任务。选择全部报告：健康视图多出六行，换来“看不到心跳就是没在运行”这条规则对所有任务成立。
  - **守卫用测试，不用检查脚本。** 这两项只需扫描源码与基线文件，放在应用层与平台的单元测试里随 `cargo test` 运行，不再增加需要单独执行的脚本。
  - **日志级别与收取时机的小变化接受。** 执行器统一以 WARN 记录一拍的失败（作业的三个循环原来是 ERROR），`subscription-sources` 在下一拍开头收取已完成的任务；二者都不改变结果，见 ADR 0133“后果”。
- 未做：对外请求、网络校验与受控出站、服务器可用判断、投递器、Cloudflare 与 Globalping、健康视图组合、保留期由所有者执行（architecture.md §12）。

## 2026-11-13：发布循环的数据库开销（关闭 JIT、每拍一次权益计算）

- 问题：用户要求“扫描 apsp 和查看仓库记录，优化”。只读查看生产时发现数据库容器持续占满一个 CPU 核（自 10-23 启动以来平均约 0.8 核），面板 4 小时内记录了 1148 条超过 1 秒的慢语句。对 `pg_stat_activity` 采样 400 次，约九成的活跃时间在三条查询上：设备数限制策略逐台主机读取成员（193 次）、主机成员摘要（115 次）与套餐资格刷新（88 次），三条都要计算全部用户的 `singbox_entitlements`。原因有两层：
  - **JIT。** 资格函数里的 `singbox_cycle_bounds` 是返回集合的函数，没有行数提示，规划器按默认的 1000 行估算，成本估到 24 亿，于是 PostgreSQL 每次执行都用 LLVM 编译、内联并优化。生产上逐台读取成员的一次执行 1120 毫秒，其中 818 毫秒是编译；关掉 JIT 后，逐台读取成员、主机成员摘要与资格刷新分别是 270、171、218 毫秒。
  - **重复计算。** 发布循环每秒计算两遍全部用户的资格（资格刷新一遍，主机成员摘要一遍），每 10 秒的设备数限制策略再为 17 台主机各算一遍；而且这些都在每秒一轮的发布循环里串行执行，循环实际每轮要两秒以上，每 10 秒还会停顿约 19 秒（17 台 × 约 1.1 秒），配置发布与资格变化的生效随之推迟。
- 选择：
  - **面板的数据库连接关闭 JIT（`jit=off`），而不是只在这几个事务里关。** 面板的语句都是短查询；JIT 只在估算成本很高时启用，而这里的估算本身就错了，换个阈值同样会被错误的估算越过。订阅下载、门户线路等按需请求也调用同一个资格函数，连接级的设置一并覆盖。结果与原来相同，只改执行方式；面板内的备份经 `PGOPTIONS` 带上同一设置，不影响导出。
  - **每轮发布循环只算一次资格，由资格刷新给出。** `entitlements::refresh` 返回这一轮允许的用户；主机成员摘要（流量服务）与设备数限制策略（服务权益）使用这一份，由应用层的发布循环传递，不新增跨领域的 SQL 或接口。资格刷新失败时，两者照旧自己计算。与原来相比，两者用的是本轮开始时的资格而不是几毫秒到几秒之后的：期间提交的变化在下一轮（1 秒后）生效，资格刷新本身也是每秒一次。成员摘要相同则不会重新发布，测试核对了两种来源给出相同的摘要与相同的设备数限制策略，策略组变化仍会让主机重新发布。
  - **设备数限制策略一次算出全部主机。** 一次查询取出所有主机的成员，限额与各主机上看到的地址各读一次，再逐台组装；每台主机的策略与逐台计算时相同（“其他主机上看到的地址”由同一份地址按主机排除得到）。单台主机的查询（`admission_policy`、`limits_on_host`）共用同一个成员查询。
  - **资格变化写回时用同一次计算的结果**，不再为变化的用户再算一遍（同一快照、同一时刻，结果相同）。
- 结果：见 `PROGRESS.md` 本日条目的上线核对。
- 未做（都要改数据库基线，走 PR 并附接入脚本，需要用户同意后在生产执行）：
  - 资格计算本身仍要对兼容桥的用量投递表按周期求和：每次约 20.8 万行（几乎全表），约占一次计算的 190 毫秒。可选做法：覆盖索引 `(user_id, period_end) INCLUDE (uplink, downlink)`，或像 `singbox_usage_daily` 那样按日预汇总。
  - `singbox_cycle_bounds` 加 `ROWS 1`，修正这一类成本估算。
  - `runtime_control_requests` 没有保留期，也没有按服务器的普通索引（只有待处理与过期屏障的部分索引）。按目标版本查找最近一次核对的查询（运行时页面与发布预检调用）对 5.3 万行做并行顺序扫描，约 83 毫秒；某台服务器的配置等待确认预检时，发布循环每秒都会走到这里（自 10-23 起累计顺序扫描 105 万次，扫描当时没有这样的服务器）。需要索引，以及与核对记录外键相容的保留期（删除生产数据需单独授权）。

## 2026-11-13：阶段 B2 收尾、接口地址与路由权限表的取舍（ADR 0132）

- 问题：用户要求“继续重构”“激进一点修改，删掉重复的内容，用底层统一，不再使用之前的 plugin 模式，扫描”，并给出一张六行的归属表（服务器与 Agent 接入归 `resources`，节点、链路与运行时配置归 `traffic`，用户、策略组、套餐与用量归 `access`，DNS 与证书归 `naming`，指标、检测与告警归 `observability`，命令、升级与执行任务归 `operations`）。表与现行架构、表与代码之间有几处对不上，执行中还有几处需要在两种做法里选一种。决策本身见 [ADR 0132](adr/0132-platform-only-host-and-domain-addresses.md)，这里记取舍。
- 选择：
  - **六行的表读作六类主要对象的归属，九个领域不变。** 表没有平台治理、基础网络与成本。一种读法是把九个领域压成六个；另一种是表只说它列出的六类对象归谁。选后一种：九个领域按对象、规则与不变量划分（ADR 0128），这张表没有否定其中任何一条；压成六个要改数据库的归属登记与全部现行文档，是另一个决定。表里没提到的三个领域保持原有对象；代码与表不一致的地方以表为准，由此改了三处：设备连接与接入令牌归资源，Agent 自更新检查归作业，面板备份归作业。数据库基线、Agent 协议与设备上的路径这一步不动，它们各自要走 PR 或 Agent 发布。
  - **备份归作业，尽管 ADR 0128 把“平台备份与恢复”列在治理名下。** 表的最后一行把“执行任务”给了作业；备份的表名（`operations_backup_*`、`operations_restore_drills`）、接口地址（`/api/operations/backups*`）与心跳名（`operations-backups`）本来就写着作业，作业里的面板备份步骤也早已直接调用它，登记在治理时两个领域互相读写对方的表。所以计划、执行、恢复点与恢复演练记录归作业；治理留下的是“谁可以备份与恢复”（权限与再次验证）和恢复后凭据材料的校验。代价是治理的系统健康视图读备份表从读自己的表变成了越界（见下面“四条新记的越界”）。
  - **接口地址按对象所属的领域，旧地址改写一个发布版本。** 三个小选择：
    - 阿里云整组接口放在 `/api/resources/alicloud`，虽然这 26 条路由由四处实现（资源 6、作业 18、成本 1、应用层的总览 1）。另一种做法是按实现方拆到四个前缀，那样同一个页面、同一组对象的接口会散开，旧地址到新地址也不再是按前缀对应。选“地址跟对象走”：云账号与云资源是资源的对象。供应商名留在地址里，因为只有一家实现（ADR 0131：有多个实现才抽象）。
    - `/api/access/statistics`（代理用量统计）的地址按对象改了，处理函数仍在观测。这一步只改地址，代码搬到服务权益记在 [architecture.md §12](architecture.md#12-扫描结论与余下工作2026-11-13)。
    - 不等兼容桥退出再改。ADR 0131 推迟改名的理由是那之前还有仓库外的调用方；核对后，兼容桥只经数据库函数交换数据，设备、订阅客户端与安装脚本都不用这个前缀。可能受影响的只有升级前已打开的页面，以及带管理员会话或管理 API 令牌、按旧地址写的仓库外脚本，例如读取续费日历 `calendar.ics` 的程序（2026-11-08 的功能盘点把它列为外部契约，它需要 `cloud:read` 权限，不是匿名地址）。页面与脚本由改写覆盖一个发布版本，改写删除之后脚本要改用现地址；日历的订阅地址是日历程序里保存的外部契约，它的旧地址长期保留（现地址是 `/api/costs/calendar.ics`）。
  - **路由权限留在治理里的一张表，不改成各领域随路由声明。** 各领域声明看起来更“就近”，但权限是治理的规则，分散之后没有一处能通读，而且等于把刚拆掉的 `Contributions` 钩子换个形式再做一遍。集中的风险是表与路由脱节，由审阅过的结论表守住：`route-policy.tsv` 按路由逐行记结论，Rust 测试对照守卫，`tools/route-policy.py` 对照源码里登记的路由，规则的任何改动都显示为逐条路由的差异。
  - **四条新记的越界照实记入清单。** 越界清单的规则是只许减少，这一步却有 4 条是新记的：治理的系统健康视图读作业的三张备份表（3 条），资源的设备通道读治理的 `sessions`（1 条）。它们不是新写的 SQL，而是代码或表换了所有者之后，原有的 SQL 才显示为跨领域。另一种做法是把表留在原来的所有者名下让数字只减不增，那样清单就不反映真实的归属。选择照实记录；同一步里清单从 432 条减到 392 条（从 main 算是 458 条到 392 条）。消除它们要等健康视图改成应用层的组合视图，以及管理员会话与设备会话拆表（阶段 F）。
  - **三件没有合并的事。** 两个 Globalping 客户端：两处的测量地点、令牌、限额、轮询、结果解析与超时都不同，更换 EIP 的可达性检查守着一次真实的地址释放，合并必须同时保住两种语义与各自的测试。三处 Cloudflare 接口：专属地址的那一份有自己的客户端、分页、错误码处理与中文错误文字，合并会改变超时与用户看到的文字。告警发件箱：它在平台，实际是观测的告警投递队列，迁走需要一个把“设置变了”告诉观测的新接口。三件都会改变行为或要加接口，不属于“行为不变的合并”，留在 architecture.md §12 的清单里，按 `PROGRESS.md` 的“下一步”处理。

  - **用构建产物证明行为不变。** 搬家前后分别构建，101 个产物文件的摘要逐一相同，因此浏览器测试（它们只加载构建产物）不需要重跑；单元测试直接引用源码，全部重跑。

## 2026-11-10：阶段 D 第二步（云能力搬进领域 crate）的取舍

- 问题：第一步之后阿里云 crate 内部已按所有者分开，但仍是一个 crate；资源与基础网络还没有自己的 crate，`impl Cloud` 散在成本与作业的文件里，作业的启停规则写在资源拥有的类型上，Rust 不允许在定义类型的 crate 之外给它加固有方法。
- 选择：
  - **新建资源与基础网络的 crate，只放迁入的云代码。** 领域代码不能移回平台，所以云账号、云资源与安全组放进新的 `crates/resources`、`crates/networking`；宿主里属于这两个领域的代码随阶段 B2 其余部分迁入，到时同一 crate 里按对象分模块。

  - **跨 crate 用到的条目公开。** 原来 `pub(super)` 在第一层模块表示“整个 crate 可见”，搬家后这个范围跨了几个 crate，统一改为 `pub`；更窄的可见性不变。
  - **`Cloud` 的外部方法改为函数，资源类型上的规则改为扩展 trait。** 成本与作业里给 `Cloud` 加的方法改为 `fn(cloud: &Cloud, ...)`（调用处随之改写）；作业给 `Policy`、`State`、`GuardConfig` 写的规则改为作业内部的 trait，调用处只加一行引入。类型存在资源拥有的行里，阶段 F 拆表时随列移到作业。CDT 响应的解析函数与新的查询函数同名，解析函数改名 `parse_traffic`。

  - **不变的部分。** 表名、接口前缀 `/api/plugins/alicloud`、后台任务与心跳名 `alicloud*`、守护名 `alicloud` 不变；依赖检查删除未拆分 crate 的过渡规则，`plugins/` 下再出现 crate 会被当作未登记层级的 crate 拒绝。
  - **客户端合并另做。** 两个 Globalping 客户端与两处 Cloudflare 接口分属观测、作业、名称与服务权益，合并要改外部接口的调用方式与测试替身，不属于这次搬家。

## 2026-11-10：阶段 D 第一步（阿里云 crate 内部按领域重组）的取舍

- 问题：阿里云 crate 装着五个领域的代码，有 22 处代码引用指向排在后面的领域（资源的接口与后台任务引用作业、成本与观测；启停规则与电源状态的类型被资源的模型引用；安全组引用作业的空闲检查），直接搬进各领域 crate 会形成反向依赖。云账号与云资源两张表同时装着资源、成本与作业的列。
- 选择：
  - **分两步，只拆代码（用户选择）。** 第一步在 crate 内重组、行为不变，第二步把文件搬进领域 crate；每一步用现有的云测试验证、单独上线。两张共享表留到阶段 F 拆，期间其他领域写自己的列仍计入越界清单。
  - **账号刷新归作业。** 刷新流程最终要决定自动降速，属于作业；它取得的快照、账单与 CDT 流量由各所有者的函数写入（资源的 `inventory`、成本的 `store_bill`、`store_traffic`），定期清理也改为调用成本与观测各自的 `prune`。这样作业只按依赖顺序向前引用。
  - **组合视图属于应用层。** 云页面一次取 6 个领域的列表，放在应用层的 `overview`，只调用各所有者的列表函数，不直接查别人的表；它暂留在阿里云 crate，因为这些函数还不是公开接口，第二步随模块搬家移入应用 crate。
  - **资源向作业提问用一个接口。** 资源删除与登记前要知道有没有进行中的操作、地址是否在换 IP 中，换密钥前要知道账号下有没有结果待核对的操作，改配置后要取消预览与排队中的操作——这些只有作业知道。资源声明 `work::CloudWork`，作业回答，应用层接线；账号下的资源编号由资源自己读出再传给作业，作业只查自己的表。取消改为一次按资源编号数组更新（同一事务、同一时间戳），状态条件与原来相同。
  - **共享行里的类型随行的所有者。** 账单、CDT 流量、余额、实例账单、启停规则、电源状态与 CDT 守护设置都存在云账号或云资源行里，类型搬进资源的 `model`；按规则判断、读取电源状态与守护计算的代码留在作业的 `power/`。表在阶段 F 拆开时，类型随列一起移到所有者那里。
  - **测试接上真实的作业回答。** 安全组的测试在同一个 crate 里直接调用 `operations::install()`，与应用层的接线相同；第二步分 crate 后再决定是用测试实现还是在应用层的集成测试里覆盖。

## 2026-11-09：阶段 C 其余部分（兼容桥收拢、两个领域互不写对方的表）的取舍

- 问题：拆成两个 crate 之后，阶段 C 还差两项完成标准：兼容桥的表 `singbox_nexus_bridge` 散在 10 个文件；服务权益写 3 张流量服务的表，流量服务写 4 处服务权益的表。
- 选择：
  - **兼容桥收成一个模块，查询形状不改。** 9 个文件里的兼容桥查询形状各异（判断成员、取订阅地址、套餐映射、是否启用），硬改成函数会改动不少大查询。做法是：整句只问兼容桥的改为 `nexus::bridge` 的函数（`is_member`、`enabled`、`synced_since`、`package_unmapped`、`plan_mappings`），嵌在大查询里的改用它的 SQL 片段（`MEMBERS`、`member_sql`、`subscription_base_sql`）。兼容桥退出时删掉这个模块，编译错误就是要改的全部位置。改写依据：兼容桥是单行表（主键 `singleton`），一个用户最多一个身份（主键 `user_id`），所以原来的连接写法与标量子查询结果相同。
  - **谁的表谁来写，事务不拆。** 链路可用性、发布批次检查结果、部署检查的保留由流量服务写；节点删除时的用户凭据、Nexus 接管时的策略组成员由服务权益写。需要在同一事务里完成的（套餐资格刷新与链路可用性、节点删除与凭据清理、接管与策略组成员）由调用方在自己的事务里调用对方：服务权益直接调用流量服务的函数，流量服务经 `users::Users` 调用服务权益。
  - **保留期限留在服务权益。** 部署检查的保留天数来自代理运维的隐私设置（`singbox_operation_privacy`），由服务权益算出截止时间，流量服务只按截止时间删除自己的记录。发布批次检查结果的同步与保留任务分开，由应用层的发布循环在同一个 30 秒步骤里各调一次，心跳仍记为 `operation-retention`。
  - **兼容桥回送的用量由服务权益排队。** 它写的是兼容桥的队列，倍率是流量服务保留线路的属性，改为服务权益调用流量服务的 `nexus_nodes::runtime_rates` 取得精确的小数文本，再在一条语句里写入，与原来的连接写法结果相同。
  - **读越界这次不动。** 流量服务编译与显示引用时读服务权益的 16 条、服务权益读流量服务的 36 条，要按“凭据经依赖倒置接口进入配置编译”逐步改成接口，不属于这次的完成标准。

## 2026-11-09：流量服务与服务权益拆成两个 crate（ADR 0131 步骤一、阶段 C 的拆分部分）的取舍

- 问题：用户要求继续 ADR 0131 步骤一的其余部分。sing-box crate 装着流量服务（约 2.5 万行）、服务权益（约 1 万行）与中国可达性（约 4500 行），流量服务有 26 处代码引用指向服务权益，拆成两个 crate 必须先去掉这些反向引用。
- 选择：
  - **按所有者拆，不按功能重写。** 每个文件按 `tools/feature-boundaries.toml` 已登记的所有者搬到 `crates/traffic`、`crates/access` 或 `crates/observability`，用 `git mv` 保留历史；只有两处改名：运维流程里属于流量服务的部署检查、发布批次与运行时清单（原 `operations_workflows/runtime/`）改为 `runtime_workflows/`，自己登记路由；Nexus 的设备会话（原 `nexus_nodes/sessions.rs`）改为服务权益的 `nexus_sessions`。
  - **20 处引用不需要接口。** 它们调用的 `entitlements::lock` 只转调流量服务的 `business::lock_publication`，改为直接调用发布锁，`entitlements::lock` 删除。外部节点版本（`Version`、`versions`）、Nexus 主机的会话密钥、运维流程的 `ids` 与 `digest` 只用流量服务的数据或不用数据库，搬进流量服务。
  - **真正需要服务权益的三件事用一个接口。** 编译进配置的用户限速与连接数、Nexus 主机的设备数限制、代理运维记录由流量服务声明 `users::Users`，服务权益回答，应用层接线。没接上时调用方的事务失败：宁可不发布，也不发布缺少用户限速的配置。Nexus 切换前的国内可达性同理由流量服务声明 `china_reachability::ChinaReachability`，观测回答。

## 2026-11-08：合并 #255 的取舍

  - 交付：B1 只移动与改名，不改数据库基线、协议与部署方式；它建立在尚未合并的阶段 A（PR #261）之上，所以追加在同一个分支与 PR 中，由用户决定合入。
- 理由：先让平台不再认识领域，再搬领域代码；每一步行为不变，路由集合静态比对一致。

## 2026-11-08：服务器重启后的运行时恢复

- 问题：bytevirt-my1 主机重启后，运行时由 systemd 拉起，Agent 一直报“controlled runtime instance differs from the successfully applied activation”，健康状态为失败，同一修订无法再应用。Agent 有意只在更高修订时才重启运行时，以免擅自中断流量；面板在配置不变时只沿用原修订，所以管理员没有直接恢复的办法，只能手动清除主机上的 Agent 状态。

  - 服务器详情的 sing-box 卡片在部署失败或健康检查未通过时显示这个按钮。遇到上述错误时，用中文说明原因，原始错误折叠显示。

- 理由：
  - 符合 Agent 现有设计：只有管理员的明确部署才能替换失效的激活，重启前需要人确认。

  - 激活仍有效时，重新部署按原配置应用，不会重启运行时，误点无害。
  - 让 Agent 在开机后自行确认未变的运行时、免去这一步，需要新的签名发布，留待下次 Agent 发布时评估。

## 2026-10-30：Clash 转换与有序来源标准化字段的兼容

- 问题：#194 的 HTTP 测试使用稀疏 JSON，但有序来源实际经过 `NormalizedOutbound` 与 `ExternalOutbound::from_normalized`，普通 HTTP 代理会带上 `path:""`、`headers:{}`；Clash 白名单不接受 `path`，导致这些节点全部被跳过，只有此类节点时订阅返回 409。HTTP/2 传输同样总是带上 `method` 与 `headers`，即使能等价表达也被直接拒绝。
- 选择：只修 Clash 转换边界。HTTP 代理允许缺省或空路径，保留原有凭据及请求头转换；自定义路径继续跳过。HTTP/2 仅接受缺省、空或 `PUT` 方法及缺省或空请求头，其他方法、自定义请求头、无 TLS 和 Trojan HTTP/2 仍跳过并说明。不开新功能、不改变来源解析、节点身份、存储格式或 sing-box 配置。
- 依据：[mihomo v1.19.29 HTTP 代理](https://github.com/MetaCubeX/mihomo/blob/v1.19.29/adapter/outbound/http.go) 使用普通 CONNECT；[H2 传输](https://github.com/MetaCubeX/mihomo/blob/v1.19.29/transport/vmess/h2.go) 固定使用 PUT，且没有自定义请求头字段；[sing-box v1.14.0 HTTP 传输](https://github.com/SagerNet/sing-box/blob/v1.14.0/transport/v2rayhttp/client.go) 在方法为空时使用 PUT。有序来源解析器填充的 GET 不能当作 PUT 静默丢弃。
- 回归通过真实 `NormalizedOutbound → ExternalOutbound → compile_clash` 路径覆盖默认字段及不能等价表达的边界。复用 #194；#190 仍为草稿，不纳入。已有验收源码摘要核对一致，修复后只补验编译器受影响范围，结果见本轮验收记录。

## 2026-10-24：主线缺陷修复第 3 步的取舍

- **跨断点保留页面（E13）：** 桌面使用可调宽度的分栏组件，手机使用纵向布局，两者的 DOM 结构不同。没有把两种布局合并为同一组件树（需要在手机上隐藏分栏并改动持久化的侧栏宽度），而是让页面渲染进一个独立的宿主节点，由当前布局挂载；切换断点只移动该节点，React 不卸载页面，打开的对话框与草稿保留。
- **语言偏好（E30）：** 页头切换语言视为本次会话的选择，不写回外观偏好；已保存的语言只在读取或修改偏好时应用。需要长期改变语言时在外观设置中保存。
- **批量操作（E32、E52）：** 选择不随筛选自动扩大或缩小，但操作只作用于当前可见的已选项，并明确提示被隐藏的已选项不会被操作，避免误操作看不见的对象。

## 2026-10-24：主线缺陷修复第 2 步的取舍

- **兼容通道成员的计量（E11）：** ADR 0092 允许新成员进入兼容通道，因此不把原生会员排除出交换。改为已用流量取旧计量与原生节点在同一旧周期内用量之和：两者统计的是不同节点，相加不会重复；节点日后接管时也不丢量。倍率与单机交接检查点仍按 `docs/nexus-agent-migration.md` 另行实现。
- **已发布迁移 0065（E9）：** 迁移文件的校验和已被记录，不能修改。选择由拥有迁移序列的组装 crate 在迁移前做同样的改名（临时停用归档触发器），而不是新增插件钩子：来源迁移与接管命令在登记插件前就会打开数据库，钩子覆盖不到。
- **通知投递（E41）：** 外部发送无法与数据库事务原子提交。选择先提交租约再发送：提交失败不会重发，进程在发送后崩溃时会在租约到期后重试一次（至少一次）。不选择“先标记已发送”，因为那会在崩溃时丢失通知。
- **发布后的服务事件（E18）：** 没有记录目标修订开始等待应用的时间，使用部署记录的创建时间并给 5 分钟宽限；服务本身不健康时不等待。
- **邀请等待（E27）：** 不在邀请人被停用时自动解除，避免绕过付费邀请规则；改为管理员显式解除，并阻止只改状态造成的半启用。

## 2026-10-24：主线缺陷修复第 1 步的取舍

- **凭据引用：** 受限管理员原本可以把任意凭据编号填入 DNS 账号、ACME 计划、会员邮件、DDNS 规则或证书部署。选择只能由所有者会话完成，受限管理员保留不改引用的编辑和经已授权 DNS 账号的委托路径。没有按凭据逐项授权，因为现有凭据中心没有可委托的范围模型，新增会扩大本次修复。
- **无服务器对象：** 没有关联服务器的网络文档、只含面板来源的工作台方案、工具与目标视为全局共享：读取保持对有读取权限者可见（与全局搜索的既有用例一致），修改须全局授权。费用记录涉及全面板成本，读写都须全局授权。
- **会员找回：** 用邮箱找回已有密码会同时移除已登记的 Passkey，管理员重置 Passkey 会清除会员密码；首次设置密码不影响 Passkey。这样任一找回都会让可能泄露的另一种凭据失效，代价是成员需要重新添加 Passkey 或经邮箱验证重设密码。
- **导入成员的登录邮箱：** ADR 0092 允许导入成员沿用原邮箱密码登录，而 ADR 0091 要求密码登录使用已验证邮箱。采用迁移 0075 记录原登录邮箱，邮箱未变时视同原系统身份，改动后须验证；本次修复前已被管理员改过邮箱的导入成员无法区分，记为已知限制。

## 2026-10-03：参考妙妙屋的节点管理

- 用户确认外部节点独立管理并可直接分配、生成 sing-box 订阅。采用节点目录元数据与独立外部授权，不改变受管服务器、单运行时或代理账本；见 ADR 0076。
- 参考项目核心是客户端节点库与订阅编排。导入使用真正的预览后选点提交，来源刷新保留本地别名与标签，新发现节点需采用；旧节点升级为已采用但不自动分配。外部停用影响后续订阅，不能撤销已下载的提供方凭据，也不静默改写已冻结链路。
- 批量操作选择最多 200 项并原子提交，冲突保留草稿。来源上游额度与本地流量分开；代理测速不能搬入参考项目额外 Mihomo 实例，仍受共用诊断框架和实机门禁约束。

## 2026-10-02：Passkey 与 DDNS 双栈

用户要求管理员和用户 Passkey，并确认只适配现有代理用户。用户侧采用插件内账户入口和管理员一次性开通链接，不把订阅令牌提升为账户登录权限，也不建立公开注册或平台全局用户，见 ADR 0059。用户同时要求 DDNS 三种地址选择；双栈复用现有独立 A/AAAA 规则，在一次事务中创建，保留各自历史、重试和暂停行为，见 ADR 0060。

## 2026-10-02：仓库整理的范围

用户要求先整理整体项目。本轮选择保持行为的入口拆分和文档导航：面板共享状态与路由按职责归组，前端分开会话、路径解析、导航、布局和登录；现有业务模块继续归所属核心或插件。旧 HTTP/Hash 路径、公共 Rust 导出、数据库迁移和签名安装入口保持兼容。大型测试、生成文件与历史证据不按行数机械拆分或删除，避免整理破坏验收引用和发布摘要。脚本仍保留原调用路径，用目录说明区分运维、构建、测试与实机驱动；本轮不新增依赖、不重启语言迁移、不恢复 CI。

## 2026-10-01：多条链路在代理节点内创建

用户要求重新规划链路创建归属，并明确选择“统一代理节点页面，直连节点和链路并列管理”。采用代理节点页统一管理直连与链路，策略组只引用已创建资源。将“多条”解释为同一页面能创建多条独立链路，同一入口服务器上的每条链路拥有独立入口监听；不将一个入口节点绑定多个出口，以免失去确定路由和独立授权。完整页面、原子创建、幂等、生命周期与验收见 设计方案。

用户进一步明确中间段可来自机场等订阅配置，采用“受管公开入口 + 有序混合代理跳”，中间/出口均可选受管或导入的具体节点，不要求机场安装 Agent，不把订阅 URL 当一跳。导入支持链接、Base64、sing-box JSON 和 Clash/Mihomo 节点 YAML；原规则、DNS、脚本及控制接口不执行。决策见 [ADR 0040](adr/0040-mixed-chains-and-subscriptions.md) 和 来源设计。

默认跟随同一明确节点的有效版本，另可固定快照；下载/解析失败、节点缺失或身份歧义保留已应用旧版并显示事实，不自动换节点或绕链直连。来源 URL/获取认证更换产生新身份 epoch，防止另一机场复用 ID 接替旧绑定；归档只停止刷新及新引用，明确授权撤销、链路删除及受管退役执行本地撤销。

最初交付为规划；用户本轮授权后已实现页面、接口和迁移，操作与验证边界见 [Agent 运维与混合链路](agent-runtime-and-chains.md)。旧接管版本保留原 ID、tag、凭据、授权、订阅、原生字节和历史计量；新建入口与链路事务内一起保存。一个链路的入口不会重复显示为直连，删除整个链路资源也不能自动将入口转为直连。完整路径版本冻结外部及受管端点，所有依赖按精确代数发布、探测及恢复屏障切换；资源完整、受管配置应用与实际路径验证分开，不能将 check 或配置健康当作跨机链路已连通。

## G4：接入、制品和历史记录

- 安装尚未产生设备 session，增加 `/api/bootstrap/{version}/{arch}?token=...`，只允许有效未消费注册 token 下载 Agent，下载不消费 token。运行时制品与配置包仍要求设备 Bearer 会话。
- 制品保存为 `artifacts/{agent|sing-box}/{version}/{amd64|arm64}`，每个版本目录使用 SHA256SUMS 列出架构文件哈希。面板校验文件与清单匹配才提供下载。
- 同设备升级可用新 token 再次注册同一公钥；已有服务器不允许替换成另一公钥。安装脚本先用暂存二进制完成注册，再激活版本。
- 服务器、节点和用户采用软删除，保留流量与部署历史。增加 usage_batches 表保证同一批次编号不能以不同记录集合重复入账；usage_records 仍保留规定唯一约束。
- 管理员会话 24 小时、设备会话 1 小时。管理员密码只在首次创建时生效，密码校验并发限制为 4，避免匿名请求同时分配无上限 Argon2 资源。

## G4：本地 Rust 链接器兼容

macOS 27 的动态库加载器暴露了 Rust/LLVM 删除调试信息后的 LINKEDIT 对齐问题。dev/test 显式设置 strip="none" 后编译通过，保留 debug=0 控制磁盘使用。参考上游问题：https://github.com/rust-lang/rust/issues/157750 。Linux 部署不依赖此工作机环境。

## G5：通用契约与运行恢复

- `Privileged`、`ServiceManager` 的 trait 定义放在 adapter-sdk，core 的 system 模块重导出并实现，避免具体适配器反向依赖 core。
- 注册身份额外持久化面板 origin，重试沿用同一设备密钥；密钥和目录在网络请求前落盘，禁止把既有身份意外注册到另一面板。
- 本地 status 返回 JSON，包含连接、模块版本、健康和待确认批次数；先占用私有 socket，再恢复状态，防止重复启动同时恢复同一意图。
- 计量序号与累计计数在 SQLite 中保存为十进制文本，支持协议的完整 u64 范围；每次采样的基准与 outbox 在同一事务提交。未知 ack 不改变账本。
- 断线只替换认证会话，对账与计量 worker 持续运行。相同已应用版本仍重新发送健康结果，修复回报丢失造成的面板状态落后。
- 制品同版本不可覆盖；缓存同时核对归档与已安装二进制的哈希。若首次安装在写入缓存元数据前中断，安全拒绝复用，需删除尚未激活的不完整版本后重试。
- 失败恢复优先重启旧版本以兼容跨内核回滚。未能读到重载前终值时取消应用；外部重载或异常终止仍可能产生无法观测的短缺失窗口，日志明确记录，已落盘批次不会丢失。

## G6：原生统计与重载边界

- 原样保留上游 proto 的 package；上游运行时实际注册服务名与 proto 不同，因此显式调用 `/v2ray.core.app.stats.command.StatsService/QueryStats`，使用 `patterns` 和 `reset=false`。
- `systemctl reload` 只保证发出 HUP。适配器在重载前建立已完成 HTTP/2 握手的统计连接，并等待该旧连接关闭，确认旧运行代已终止后才让 core 开启新计量周期；健康检查再等待新的端口和统计 API。
- 适配器支持稳定版 1.14.x，要求实际二进制版本与清单完全一致且包含统计标签。当前面板固定发布 1.14.2；没有扩展运行时版本选择界面。
- 首次成功应用或版本变化后补发静态信息，使面板及时看到运行时版本，无需等待下一次连接。

## G7：发布、已应用订阅和历史计量

- `dirty_at` 使用 PostgreSQL 时钟的 Unix 毫秒，精确等待至少五秒；模型修改与标脏在同一事务中，发布时锁定服务器，避免漏掉并发变更。启动后的发布器继续处理数据库中遗留的脏标记。
- 节点不支持迁移服务器或手动改端口；端口在锁定服务器后从默认范围取最小空位。节点私钥只保留于数据库、部署快照和设备配置包，不出现在管理列表或发布历史响应中。
- 配置包哈希相同时不创建 revision，仅刷新该版本的订阅元数据。订阅使用已应用且健康的快照，并与当前未删除授权的 UUID 取交集；撤销立即从订阅移除，重新授权要等新凭证成功应用。
- 认证心跳可修复丢失的成功回报，但只接受本服务器已发布且更高的 revision；不倒退已应用版本，不抹去最新失败目标的错误。
- 流量允许已经撤销或删除用户的历史统计名重发，前提是该身份曾为此服务器发布；整批事务提交后才确认。同一批次编号更改内容会被拒绝，记录顺序变化不影响去重。
- PostgreSQL 计量字段改用 NUMERIC(20,0) 保存协议完整 u64；汇总可超过 u64，API 使用十进制字符串传递，避免浏览器数字精度损失。

## G8：前端构建与路径权限

- 使用 hash 路由，不增加路由或组件库；未知 API 路径和缺失资源保留 404，避免被页面回退掩盖。
- 提交体积较小的 `web/dist`，使新检出的仓库可以直接 `cargo build/run`。CI 使用 lockfile 重新构建并检查产物一致，修改前端必须同步提交构建结果。debug 与 release 都使用内嵌资源。
- HTML 禁止缓存，带内容哈希的 JS/CSS 长期缓存；静态资源带正确 MIME 和 nosniff。
- 审查发现自定义身份目录或 status socket 父目录可能指向已有共享目录。改为仅为新建目录设置私有权限，保留已有目录权限；密钥和 socket 仍保持 0600，并验证不安全目录条件。

## G9：部署与构建边界

- Compose 使用 PostgreSQL 16 和非 root 面板容器，分别使用命名卷；数据库不映射宿主端口，面板默认只映射到宿主回环地址。公开地址和密码由部署者提供，数据库密码示例使用十六进制，避免 URL 转义歧义。
- 安装脚本将既有 TOML 的解析、路径覆盖保留和设备 origin 校验交给 Agent 注册命令，不使用精确文本 grep 判断面板地址。成功注册后才原子写配置并切换 Agent；升级需要为同一服务器重新生成一次性安装命令，已消费的旧命令不可复用。
- 上游 `release/DEFAULT_BUILD_TAGS` 包含 `with_naive_outbound`，保留全部标签的 Linux 构建需要 CGO/glibc 和上游 Chromium 工具链。固定 Linux/amd64 构建容器，交叉输出 amd64/arm64；只追加 `with_v2ray_api`，不追加 purego/musl 标签，不修改上游源码。只有 Agent 要求 musl 静态链接。
- sing-box 固定 v1.14.2 及对应提交，使用上游指定 cronet 工具链版本；GPG keyring 使用临时私有目录，避免影响构建者的默认密钥环。归档仅包含一个可执行文件，固定归档元数据；同版本同架构产物不可覆盖，添加另一架构时保留并核验既有校验和。
- 本机为 macOS 且无 Docker；本地已启动真实 PostgreSQL、面板和浏览器，并验证真实上游运行时 check/统计/HUP。Docker 部署和 Linux musl 构建通过 GitHub CI 验证，结果在最终报告单列；真实 Debian systemd、公网 Reality 客户端与网络条件仍需执行手工验收。

## Agent 能力对齐：用户确认全部补齐

- 用户确认将基础监控细节、离线遥测补报、持续拨测、通用命令、升级恢复和非 Linux 常驻部署全部纳入，覆盖原来的仅编译产物限制与自更新排除项；按 ADR 0022 分阶段实现。
- sing-box 上游支持 musl。原脚本只调用 glibc 工具链，属于本仓库缺口；新增官方 musl 工具链与标签，不删除默认功能或修改上游源码。
- 辅助 outbox 和命令表采用幂等建表，不提高账本 `user_version`，避免旧版本回退时拒绝打开数据库。压缩上传复用已有 `flate2` 依赖。
- 管理员可以拨测内网、回环和公网的单播目标；命令使用设备服务账号执行。命令执行状态在启动进程之前落盘，重启后的未完成命令统一标记中断，不重放无法确认副作用的操作。失联超过一天暂停使用缓存拨测配置。
- OpenRC 一次性诊断由同一 Agent 二进制的内部任务入口运行，在独立服务中监督；它不是对外开放的特权 helper。挂载命名空间使用系统 `unshare`，保留 Linux 专属 NodeQuality 范围。

- 原生服务采用系统内置 launchd、rc.d/daemon 和 Windows 计划任务，Agent 与运行时分开注册；Windows 不增加需要 unsafe 的服务控制器库。运行时 DLL 通过通用文件白名单描述，core 保持运行时无关。
- 自动更新只使用面板导入的稳定版，初始关闭；本地 PID/版本检查允许离线启动。Supervisor 与 Agent 同属系统服务，代理进程归另一服务；更新前的持久试运行状态用于恢复中断升级。Windows 文件内容刷盘后原子替换引用，目录元数据断电语义仍是已知验证边界。
- FreeBSD 保留代理普通账户，因此默认使用非特权节点端口；需要 443 等低端口时由管理员配置宿主端口授权。安装器不自动修改全局 sysctl 或加载端口策略模块，避免覆盖现有主机策略；详见 README 和 FreeBSD `mac_portacl(4)`。
- FreeBSD 的 sysinfo 0.33 磁盘枚举调用 `getmntinfo`，其[官方实现](https://github.com/freebsd/freebsd-src/blob/releng/15.0/lib/libc/gen/getmntinfo.c)会修改并重新分配进程全局缓冲区。连接上报和采样可能并发构造 Collector，因此以进程级互斥锁保护完整磁盘枚举及 libgeom 快照；不新增 unsafe 或修改上游依赖。CI 增加重复启动采样和可用时的原生崩溃回溯。
- Windows 新建运行时账户明确加入普通 Users 组，使用固定 SID 和本地账户对象，避免本地化名称与域同名账户歧义，依据 [Add-LocalGroupMember 文档](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.localaccounts/add-localgroupmember?view=powershell-5.1)。运行时保持非管理员；原生 CI 校验账户分组及真实任务执行。Windows ARM64 实测启动权限检查可能超过 60 秒，更新试运行给出 120 秒有界健康检查，其余平台仍为 60 秒。
- Windows runner 的任务继承 DACL 给 SYSTEM/Administrators 的掩码为 `0x1f019f`，不含文件执行位，因此 Agent 可以读写任务但无法启动运行时。注册后按 [SetSecurityDescriptor](https://learn.microsoft.com/en-us/windows/win32/taskschd/registeredtask-setsecuritydescriptor) 明确将本项目任务的控制权限限定为 SYSTEM 和 Administrators，禁止继承及自动添加运行账户控制 ACE；任务仍以原普通账户执行，不改变运行时文件权限。
- Windows ARM64 的测试日志显示升级已激活但状态保存超过夹具等待，安装也在大量权限操作期间超时。权限读写改用内置 .NET Framework 的 [File.SetAccessControl](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.setaccesscontrol?view=netframework-4.8.1) 及目录对应接口，合并同次目录创建和制品文件权限，避免反复自动加载 PowerShell 文件系统/安全模块；新文件在写入内容前设置 ACL。服务启停使用同一任务计划程序的 COM 接口，避免每次导入 CIM 模块；重启先等待旧任务停止。仍保留 ACL 拒绝检查与普通账户隔离，不添加依赖或常驻 helper。
- Windows 任务 DACL 修复后的事件确认错误 `0x80070569`：普通运行账户缺少批处理登录权。安装通过系统 [secedit](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/secedit-configure) 读取并保留现有 `SeBatchLogonRight`，只追加该专用账户 SID；不更改拒绝策略及其他用户权利。新账户先禁用，设置随机密码后再启用。CI 比较安装前后及重复安装后的全部用户权利，验证只发生预期追加。
- Windows 用户权利模板允许以账户名或带星号的 SID 表示同一主体（[MS-GPSB 2.2.6](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-gpsb/3413b381-a445-4d17-b77e-5bbfadda253b)）。重复安装识别这两种表示；原生测试统一转换为 SID 后比较，保留全量权限差异断言与失败详情，避免仅按原始文本误报。

## 磁盘容量：容器挂载与文件系统去重

- 磁盘总量沿用已挂载文件系统的容量口径，不改为裸块设备标称容量；已用空间仍为 `total_space - available_space`，包含普通进程不可用的保留空间，与 `df` 的 Used 列可能不同。Unix 的静态总量、动态已用和逐盘列表共用一次筛选后的快照，读取失败、容量无效或溢出继续表示未知。
- [sysinfo 0.33.1 的 Linux 枚举](https://github.com/GuillaumeGomez/sysinfo/blob/v0.33.1/src/unix/linux/disk.rs)会返回 overlay 与单文件绑定挂载；原来仅按名称累加时，真实分区与名为 overlay 的视图各计一次。按[内核 overlayfs 语义](https://docs.kernel.org/filesystems/overlayfs.html)，Linux 排除非根 overlay/overlayfs/fuse.overlayfs 与单文件挂载；容器中的 `/` overlay 保留。
- Unix 使用挂载点的设备标识去重绑定挂载与设备别名，优先保留根及较浅挂载；元数据不可读时回退设备名，无名时回退挂载路径。Btrfs [子卷共享文件系统存储](https://btrfs.readthedocs.io/en/latest/Subvolumes.html)，继续按可解析的源设备名称去重，不因子卷设备标识不同重复累加；I/O 基线同时使用名称与挂载点。
- Windows 保留原 sysinfo 逐盘列表与按名称首条去重的总量规则。[固定 sysinfo 的 Windows 枚举](https://github.com/GuillaumeGomez/sysinfo/blob/v0.33.1/src/windows/disk.rs)会为同一卷的每个挂载路径生成一条记录，因此不能仅凭路径将它们计为独立容量。不同卷标签相同或为空仍有既有歧义，须在取得真实卷 ID 后另行实现和原生验收；本项不声称修复该歧义、不新增 unsafe、依赖或外部命令。容量无效、溢出和首条记录的未知语义保留。
- 不根据相等容量猜测两个文件系统是否同盘；容器内无法访问 overlay 后端时，也不推断它与额外目录卷的物理归属。此项修复不提供跨命名空间或所有存储池的物理容量映射。

## 签名与多平台整合后的 CI 修复

- Windows 的文本模式写入会将 LF 转成 CRLF，使安装到磁盘的签名证明不再符合 canonical 格式。夹具、清单及固定安装器都按 UTF-8 原始字节写入；不让验证器替换换行或放宽签名检查。回归在 Linux 模拟 Windows 文本模式，并使用独立 minisign 验证正确证明及拒绝篡改。
- 当前 cryptography 50.0.2 的发布文件没有 Windows ARM64 wheel，直接 pip 安装会进入本机构建。原生 CI 改用 `apsp-protocol` 已有的 ed25519-dalek/blake2 测试签名实现，编译独立 example；仅内嵌公开 TEST_ONLY 密钥，只接受有界 stdin，不接受密钥参数。合并上游 `541f52d` 后统一使用其 `ci-fixture-sign` 和 `APSP_CI_FIXTURE_SIGNER`，同时覆盖 macOS 与 Windows；未增加生产依赖，也不向 CI 提供正式私钥。
- BusyBox `install -d` 会让隐式父目录受 `umask 027` 影响。安装器显式创建共享的 `/opt/apsp`、`/opt/apsp/plugins` 和 `/var/lib/apsp` 为 0755，保证独立普通运行账户可遍历；身份和 core 账本仍为 0700，运行时私有配置仍按专用组限制。隔离 Alpine 实际启动验证保留，不通过把运行时改为 root 绕过权限问题。
- 静态 musl Agent 可以运行在 glibc 主机上，编译 ABI 不能兼作外部运行时的 libc。保留 `libc` 的 Agent 更新语义，新增可选 `runtime_libc`；在 core 读取系统程序有界 ELF64 头中的 `PT_INTERP` 判断 GNU/musl，不执行额外工具、不依赖 init 类型、不新增依赖。面板与 core 的签名缓存选择使用宿主信息，旧协议字段缺失仍兼容。解析参考 [ELF Header](https://refspecs.linuxfoundation.org/elf/gabi4+/ch4.eheader.html) 与 [Program Header](https://refspecs.linuxfoundation.org/elf/gabi4+/ch5.pheader.html)；无法识别时保留编译 ABI 回退，不将未知 libc 任意映射到 GNU。
- 合入上游 `13f2975` 后统一使用其 `runtime_platform` 实现，移除重复解析与选择逻辑。GNU 宿主上的静态 Agent 保留已有 musl、旧目录、GNU 运行时的优先级，以避免同一已签证明包含多个平台时改变现有不可变缓存的选择；Agent 自更新仍按编译 ABI。
- 上游把扩展平台检查改为手动；按本次此前的多平台自动构建要求，`CI` 继续在 push/PR 构建全部平台，OpenRC 保留在 Linux musl 任务内。上游的独立手动平台工作流保留，便于按需复验。
- macOS 的软链接继承进程 umask，`readlink` 又检查链接自身的读取权限；launchd 的 `umask 027` 因此会阻止普通运行账户解析 root 创建的 `current`。依据 [Apple XNU 的 symlink/readlink 实现](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/vfs/vfs_syscalls.c)，在 `SystemOps::atomic_symlink` 发布前使用 `chmod -h 755` 设置临时链接自身权限；不改变目标文件、私有目录权限或整个进程的 umask。仍保留签名、路径边界、摘要与离线缓存复验，并在 macOS CI 用 `umask 077` 检查链接可读、目标权限不变及悬空链接替换。

## 2026-10-01：策略组与套餐组的分配语义

本轮按用户新增要求扩展 sing-box 插件，不恢复已删除的平台全局代理用户模型。策略组定义可使用的普通节点及两跳链路；多个组与旧单独授权取并集，避免取消一个来源误撤其他来源的权限。套餐组是独立模板，每个用户保留一个当前快照，模板编辑不追溯改变已分配用户。详见 [ADR 0035](adr/0035-singbox-policy-package-groups.md) 和 [操作/API 说明](singbox-groups.md)。

用户未指定首月折算、结转和续期累加，本轮选择完整月度额度、无结转、从分配时刻起计算有效天数。更换套餐不删除流水，按新模板的周期边界统计已有流量；界面明确提示期限是重新起算而非在旧到期日累加。没有套餐的旧用户和新用户保留不限制流量与有效期的兼容模式，必须明确分配套餐才能启用限制。

用户要求策略组包含链路，因此补齐可执行的原生两跳配置，而不是只保存没有运行时效果的链路编号。暂不支持任意多跳、同机链路或入口直接授权；链路内部凭据不进入订阅，用户流量只在入口计量。跨月采样批次完整归入排他结束时刻前一秒的月份，不按时间比例猜测字节分布。配额/到期通过订阅资格和运行时整包发布共同执行，离线与尚未上报的流量仍存在滞后，不能承诺立即断流。生产双机、长连接及离线恢复验收另行执行，本 PR 不部署。

- 共享受管端点采用保守编辑规则：名称和启用状态可修改，监听/连接参数与拓扑通过替代资源更换，避免覆盖正在使用的恢复快照。链路名称默认不改客户端订阅名称，显式同步另行提交。
- 每入口最多 64 条存活混合链路，为双代 path-checks 留出 128 项上限；每台运行时最多 1024 个保留路径恢复标识。每设备最多四个待办验证、有效期五分钟，避免批量创建后等待队列中的请求虚假超时。后续历史归并需新的恢复证明，不能删除 Agent 下界来释放额度。
- 来源同身份参数更新若使整条路径不可编译，仅记录该链路失败并保留原版本，使用保存点隔离其他链路；源参数不能触发自动换节点或直连。

## 2026-10-02：CDT 启停策略的边界选择

## PR160 复审：失联、撤销与未知执行结果

- 终端输出和输入必须绑定创建时的管理员与会话；列表元数据和具备当前服务器终端写权限的紧急关闭保留。原始 PTY 输入只发给实际终端，不进入审计详情。
- 本地关闭、撤销和失联回收先于网络上报；未确认的事件保留待回报，但面板拒绝事件不能延长既有进程寿命。
- 临时 sysctl / 防火墙变更使用所属快照身份与共享锁；回退只恢复仍符合本次期望值的对象，拒绝覆盖后来发生的人工或其他操作变更。未知清理仍保留阻塞身份。
- DNS 外部写入先持久化单次意图及冻结权限、凭据版本与远端快照，再发送请求；未确认请求只允许只读核对。旧范围和当前范围共同决定历史可见性。
- 运维人工核对由新鲜、关联精确原操作的成功只读设备回执支持；保存人工结论时不覆盖原设备结果、状态和摘要，迟到真实回执继续接收。隔离恢复数据库使用独立随机口令，不依赖源库连接串口令形式。
- 网络工作台在派发及 Agent 领取时重查来源、目标、工具版本和许可；撤销请求确认式取消，不把拒绝派发当作从未启动。面板 TCP 的解析和全部样本共同消费总截止，HTTP 在解析后、发送前再核授权期限。
- 磁盘验机的临时文件大小与报告输出上限分别处理；临时文件创建后立即登记并解除目录链接，工具输出使用有界管道。源码和隔离回归通过不代替真实 fio、systemd、证书部署、WireGuard、DNS 或完整 NodeQuality 签收。

### PR160 CPU 能力声明的实际服务后端

决定将 CPU 硬上限能力声明绑定 `ServiceManager`，默认拒绝；只有真实 systemd 后端且控制器可用时声明。全局平台探针不足以代表 OpenRC 等后端的可执行约束。端到端模拟服务显式声明测试能力并检查预算，保留真实启动检查，不将模拟声明扩展到原生签收。


### PR160 本地验收的输入与清理取舍

- 删除无调用私有函数也重新生成同工作区默认图；65实际二进制改变目标完整补验，46逐字一致产物保留。`.d`只作为实际直接来源，包图及外部运行输入分开记录，未保存的原producer源码或IO轨迹不补造。
- 真实虚拟Passkey与49隔离浏览器夹具分开认证；缺浏览器零启动、旧按钮定位失败和完整修复结果各保留，不把24默认忽略减一。作者JSON只表示原blob及当时环境，不泛化为本聊天原生执行。
- 验证完成后只保最新有界结果、原错误和源码身份，再精确清理所属runtime、数据库、target、依赖及完整raw；逻辑材料量与实际可用空间观测分开。删除后的旧路径不承诺可读，不重跑已交付范围以重建历史收据；后续新PR依据当前实际存在材料决定完整受影响验收。

## 2026-10-03：重新架构阶段二的范围调整

- 用户确认先做 ADR 0085 的阶段一、二。阶段二原计划同时合并订阅抓取和解析，并用逐字节对照保证已存外部节点不生成新版本。
- 实施前逐项核对两套解析器，发现差异不只在安全限制，还在解析语义：
  - YAML 标量：B 把 `0x`/`0o` 开头的值解析为数字，并接受 `!!int` 等显式标签；A 把它们当字符串，或直接拒绝标签。
  - YAML 合并键：多个合并来源有相同键时，B 报错，A 取第一个。
  - 格式识别：两边识别 Base64 和 YAML 的条件不同。
  - URI 参数：两边接受的查询参数和协议别名不同，例如 A 接受 `socks5h`。
  - 名称规则：长度和禁止字符不同；B 会隐藏与凭据相同的名称。
  - 输出：A 输出经过校验的原始 sing-box JSON，B 输出类型化模型并做规范化。
- 统一到任一侧都会改变部分现有订阅的解析结果：有的生成新版本，有的刷新直接失败。这违反 ADR 0085 “已存外部节点不会因为升级而生成新版本”的约束。若保留两种方言再包进一个模块，并没有真正减少维护面，阶段三删除一套来源时还要再拆。
- 选择：阶段二只合并抓取器，规则取两边并集。安全规则只在一处维护；两套来源各自保留错误码和调用方式。解析器合并并入阶段三：选定保留哪套来源时，另一套的解析器随其存储一起删除，迁移方案再说明受影响的订阅如何处理。

- 选择：用户确认显示入口，并以说明代替被拒绝的读取。「告警设置」与「告警事件」「延迟检测」一样声明监控告警权限并要求全服务器授权，侧栏和命令面板据此显示；页面先读取当前管理员，只有所有者读取面板设置，其他管理员在开关与阈值的位置看到“告警开关、阈值和 Telegram 通知只有所有者可以查看和修改。”。所有者读取失败时仍显示错误，规则、Webhook 与渠道状态照常加载。

## 2026-10-24：Nexus 运行接管的快照来源、授权边界与限制差异

- 问题：Codex 中断前用脚本按旧节点逻辑手工推导了 7 台主机的候选，自定义出口、分流和本地 `custom_config` 的主机全部跳过；复核发现这些候选的 Reality 握手端口是字符串 `"443"`，面板会拒绝，绕过校验则新运行时无法启动。另外，准备后没有撤销途径；迁移节点仍可被加入策略组；旧节点按套餐执行的限速与设备数，apsp Agent 不执行。
- 选择：快照只由旧节点自身的 `buildConfig` 生成（`tools/nexus-legacy-export`），`tools/nexus_runtime_snapshot.py` 转换并严格校验类型，整台主机任一节点不能转换就不写快照；编译器接受各节点完全相同的主机级路由选项（出站网卡、默认解析器）。新增仅限从未启动、没有部署的“撤销准备”；迁移节点拒绝加入策略组。限速与设备数差异由 `compare-users` 统计并写入运行手册，不阻止切换。
- 理由：模拟旧逻辑无法覆盖弱类型转换和本地合并，复用原代码才能保证客户端看到的服务不变；不同主机级选项无法无歧义合并，仍然拒绝。撤销只删除从未发布的准备记录，启动过的主机保留发布和流量历史。策略组会生成新 UUID 与密钥，破坏原链接。去掉限速与设备数只会放宽而不会中断现有使用，按“不影响以前的使用”的要求可以接受；需要恢复这两项时属于新运行时能力，另行实现。

## 2026-10-24：界面第五轮第一步的实施选择

- 滚动归属有两种做法：主列在所有宽度负责滚动，或手机改用文档自然滚动。选择前者：外框结构在两种宽度一致，手机页头和菜单固定在上方不随页面滚走；页面内已有的吸顶顶栏、贴底批量栏按同一个滚动容器工作，不需要分两套写法。
- 跨断点保留状态有两种做法：只增删外围元素，或把内容渲染进稳定的承载元素再移动它。外框选择前者：分栏组始终存在，手机时只移除侧栏面板。`ListDetailLayout` 选择后者：手机上下堆叠无法用分栏组的内联尺寸表示，改为门户承载，布局切换只移动承载元素。
- 浏览器后退、前进发生时地址已经改变，无法事先阻止。选择在路由收到 hashchange 时询问，用户留下则用 `pushState` 写回原地址（不产生第二次 hashchange）。后退被拒绝时，原来的“前进”记录会被这条新记录替代；这是 hash 路由下不改动历史栈就能恢复地址的最小做法。
- 有未保存草稿时，同一页面内只改查询参数的地址变化也会询问，与原链接拦截“地址不同就询问”的规则一致；目前登记草稿的只有添加服务器、运维计划、设备群操作与网络检测方案，它们编辑期间不会自行改写地址。
- 命令面板在其他弹窗打开时不响应快捷键，而不是在弹窗上方打开后再询问：模态弹窗中的表单此时无法通过侧栏离开，阻止打开最直接，也避免面板与弹窗争夺焦点。
- 评审建议把动态状态改为显式 `t()`，并停止对 React 管理的节点二次改写。全量迁移涉及数千条中文，本轮修正翻译器的来源判断（覆盖全部现有节点），并先把服务器列表与详情的连接状态改为 `t()`；后续页面按同一规则逐步迁移。

## 2026-10-24：界面第五轮第二步的实施选择

- 页头的语言选择可以只作用于当前会话，也可以保存为管理员偏好。选择后者：设置页的同一选项本来就保存偏好，两个入口行为一致；只作用于会话时，下次登录或另一窗口仍会回到旧语言，与评审描述的“被改回”是同一种体验。保存失败不撤销选择，下次读取到的已保存值照常生效。
- 公开看板的浅/深色选择仍按浏览器保存，管理端主题仍按管理员保存；两者都在各自显示期间写入 `<html>`。没有把看板主题并入管理员偏好：公开看板也供未登录访客使用，没有管理员身份可保存。
- 服务器批量操作的确认框中，“进入维护”“停止接收新任务”使用警示样式，“恢复接收任务”使用普通样式；三者都先确认，因为它们都会立即改变这些服务器能否接收任务、终端和远程命令。
- 批量操作的目标取“当前可见 ∩ 已勾选”，被筛选或搜索隐藏的已选对象保持勾选但不修改，而不是在筛选变化时自动取消勾选：用户切换筛选查看时不会丢失已做的选择，隐藏数量在操作栏和确认框中写明。
- 弹窗打开者已不在页面上或无法获得焦点时，焦点交给页面主体 `main`（可聚焦但不进入 Tab 顺序）。没有改为聚焦页面标题：不是每个页面都有标题，`main` 在所有后台页面都存在，屏幕阅读器会播报所在区域。
- 多选控件保持原生 `select multiple`，只取消固定高度和下拉箭头，没有换成复选框列表：两处多选（链路出口扩展、网络检测服务器集合）的提交逻辑读取 `selectedOptions`，保持原生控件不改变表单与键盘行为。

## 2026-10-24：界面第五轮第三步的实施选择

- 导航顺序按评审和路线图工作包 0.2 调整：代理服务移到第一组，组内为服务概览、代理节点、代理用户、策略与套餐，后来加入的成员运营排在最后。评审写作“节点与链路”，入口名仍保留「代理节点」：链路已在该页的“链路”视图中，改名会牵动文档、测试和已有习惯，留待 0.2 统一处理“实验”标记时一并考虑。登录后的默认首页仍是服务器看板，等待决定 D6。
- 弹窗退出动画有两种做法：每个调用点改为常驻并传入 `open`，或用一层 `DialogPresence` 保留被移除的弹窗直到动画结束。选择后者：74 处调用的内容大多依赖“正在编辑的对象”非空，改为常驻需要逐处处理空值；包一层后弹窗内容保持移除前的样子，行为不变。调用点用 TypeScript 语法树批量改写，自带 `open` 的三个编辑器改为在组件内部包裹。
- 退出动画期间 Radix 保持页面其余部分对辅助技术隐藏，直到弹窗离开文档（约 0.18 秒），这与常见的带退出动画的模态弹窗一致。关闭中的弹窗只设为 `inert`，没有再加 `aria-hidden`：浏览器的辅助技术已跳过 inert 内容，测试中的“等待弹窗隐藏”因此会等到弹窗真正离开，不会在退出途中读取页面。为避免两个弹窗同时出现在页面上，新弹窗打开时立即结束其他弹窗的退出。
- Motion 的退出动画随动画帧推进，夹具安装页面时钟后（无论是否暂停）退出都不会完成，页面会一直对辅助技术隐藏。现实中只有后台标签页会暂停动画帧，回到前台后动画照常结束。选择让系统设置“减少动态效果”时弹窗立即关闭（这本身也是该设置的合理行为），控制页面时钟的夹具请求减少动态效果；没有在产品代码中加入不受页面时钟控制的计时。实际退出动画由 `visual-hierarchy.mjs` 在正常时钟下覆盖。
- 实现中发现：关闭一个有未保存输入的弹窗后，在退出动画结束前点击导航会误报“未保存”。离开保护改为只在弹窗仍在页面上时生效（`useLeaveGuard` 读取 Motion 的 presence 状态）。
- 紧凑密度保留全局缩小的间距单位，在按钮、输入框、选择框、复选框、开关、菜单项和侧栏链接上恢复舒适密度的单位。没有逐个改写内容区的间距类名：表格、面板和区块都使用同一套间距刻度，按控件恢复更不容易遗漏。
- 汇率缓存从 Zustand 移回看板的数据读取一侧：store 只保存访客选择的币种，汇率由读取它的组件经 context 提供，重新进入看板时的过渡值放在读取模块中。没有只把它登记为例外：移动后与“服务端数据不放进 store”的规则一致，改动只涉及一个文件。
- 服务器列表新增“地区”筛选，与“分组”一起放入更多筛选；手机卡片字段单独保存在视图中，默认只显示处理器和内存。已保存的旧视图没有这两个字段，应用时使用默认值。

## 2026-10-25：首次空运行时安装后预检无法通过

- 问题：恢复真实 CI 验收时发现，首次空运行时安装后流程会卡死。精确核对只在服务器没有待发布业务时（`dirty_at` 为空）认定目标为当前目标，而空安装特意保留待确认的业务节点，所以 Agent 的核对回执被判为 `superseded`。重新采集的完整预检又要求运行时统计监听 `127.0.0.1:18085` 空闲或归“已核对”的受管进程，空运行时自己占用该端口，于是端口检查永远失败，业务无法确认发布。生产面板尚无已安装 Agent，所以还没有人遇到。
- 选择：不放宽核对认定，部署状态在业务发布前仍显示已应用 0、未健康。端口归属改为也接受 Agent 五分钟内成功回答当前已发布目标绑定的核对，同时仍要求实际 unit MainPID 匹配；见 ADR 0080 补充。验收驱动在空安装后等待已应用，或等待 Agent 回答该版本的核对请求，再重新采集预检。
- 待定：已有部署的服务器新增监听时同样需要五分钟内的核对回执，但业务待发布期间界面禁用主动核对，Agent 也只在重连或应用后自动核对。是否在请求预检时一并请求核对（会把健康暂时置为否），或在界面放开待发布期间的核对，需要单独决定。空安装版本是否应显示为已应用也一并评估。

## 2026-10-25：全功能审查后按使用逻辑重组

用户要求扫描每项功能与交互体验、并行验证、研究论坛需求，并“无需审核，按最佳决定来”完成分类、重新布局、插件合并拆分与方向统一。决定见 [ADR 0098](adr/0098-usage-driven-navigation-and-tiers.md)，路线图第五节的 D1–D11 同时定案。主要取舍：

- **侧栏分组。** 六组：总览、代理服务、服务器、监控告警、系统、实验功能。插件中心放在“服务器”而不是“系统”：插件按服务器启用，“系统”组已有四个入口。DDNS 与阿里云 CDT 也作用于具体服务器，一并归入“服务器”。
- **运维工具。** 并入服务器详情的「运维（实验）」，地址沿用 `/#/servers/{id}/fleet`；批量接入移到 `/#/servers/batch`。`/#/fleet` 继续显示服务器选择，侧栏高亮「服务器列表」，没有改成跳转，以免打断已有书签上的操作。
- **冻结功能的显示开关。** 选择面板级设置（`panel_settings.settings.show_frozen_features`，默认关闭），而不是每位管理员各自的偏好：功能地图规定“在面板设置中可显示”。设置以 JSON 保存并带默认值，不需要迁移。外框从 `/api/control-center/me` 读取开关，不增加请求。隐藏只影响界面，不是权限控制，接口照常。
- **核心旅程不依赖降级页面。** 部署预检要求的“只读运行时预检”面板授权原本只能在运维工具里开，现在可在预检区域就地开启。写入的仍是同一份面板策略（同样需要 `servers:write`、`security:write` 与近期验证）；Agent 本机的同名授权仍需操作者在服务器上开启。
- **首页。** 登录后进入「概览」（原服务概览）。“需要处理”只列面板已有数据能判断的事项：离线服务器、sing-box 安装失败、未恢复告警、30 天内续费。代理用户的到期与额度需要新的聚合接口，留给路线图 2.7。每个数据源都可以缺席：管理员无权读取时，对应卡片不显示，不报错。
- **单一编辑位置。** 监控历史保存期限只在「面板设置」修改，保存时同步记录保留策略；缩短期限需要近期验证，因为会提前删除历史。系统自检中只读显示，`PUT /api/control-center/retention/monitoring` 返回 409。`PATCH /api/settings` 改为部分更新，取代 2026-10-24 条目中“每页保存前重新读取再整包提交”的做法：后者在两页同时编辑时仍会互相覆盖。
- **停止类操作免近期验证；批量登记补上。** 取消远程命令、关闭终端会话只是结束已获授权的工作，不再要求重新输入密码。`/api/fleet/batch-enrollment` 不含 `/enrollment` 子串，原规则漏掉了它，现在与单台登记一样需要近期验证。终端输入每五分钟重新验证一次的规则不变，这是有意的安全选择。
- **批量维护必须有结束时间。** 原来从服务器列表批量“进入维护”不设结束时间，会无限期暂停离线告警。现在在确认框里选择 1–72 小时；单台的维护时段仍在服务器详情的运维分页设置。
- **自助修改密码。** 新增 `POST /api/security/password`，需要当前密码，启用二步验证时还需验证码，并与登录共用限速。和关闭二步验证一样，修改后撤销其他会话以及所有者的管理员 Passkey，防止被植入的 Passkey 在改密后继续有效。审计按键名脱敏，`current_password`、`new_password`、`totp_code` 都不会写入。
- **链路创建入口。** 统一入口提前到来源迁移之前：始终打开有序链路表单，mixed 链路编辑器从界面移除，`/chains/batch` 接口保留。迁移前只有数字编号来源的管理员，需要先在有序来源中添加来源；订阅来源视图会说明这一点，并给出迁移命令。
- **代理用户操作与订阅。**
  - 预览指纹不再包含实时用量，在线用户的批量操作不会因为预览与应用之间新到的流量而被拒绝。
  - 延期从“现在”与原到期日中较晚者起算，结果仍已到期时直接拒绝。
  - 受限用户的两种订阅格式都返回带原因的 409，审计结果记为 `restricted`。
  - 成功的订阅响应带 `Subscription-Userinfo`、`Profile-Title`（base64 形式，可容纳中文名）、`Profile-Update-Interval: 24`。
- **Xboard 迁移的凭据模型（D4）。** 以已实施的 ADR 0092、0095 为准：成员与订阅令牌迁入，原订阅地址兼容，运行接管保留客户端身份；本轮审查推荐的“每节点独立凭据”只用于今后在 apsp 中新建的代理用户，不改变已迁入的身份。
- **本轮发现但未修复。** 下列问题记入路线图：
  - **费用与续费账本（`plugins/expenses`）。** 自动续费项目被后台顺延后再手动“续期”，会再推进一期，付款也记到已顺延后的账期。手动项目逾期后从“30 天内续费”、日历与提醒中消失。年度预计中服务器与手动项目的口径不一致。提醒去重键含版本号，编辑备注会重发提醒。这些都涉及生产中的真实账本数据，单独修复并补测试。
  - **其余工作包。** 代理用户暂停状态、部署控制台统一、节点证书状态、sing-box 停用语义、故障事件并入告警事件、告警设置分页。

## 2026-11-01：中国可达性监控的自行决定

[ADR 0105](adr/0105-china-reachability-monitor.md) 实现时，下列问题由实现者自行决定，均可调整：

- **UDP 节点：** Globalping 只能测 TCP。对 Hysteria2、TUIC 和 mKCP、QUIC 传输做 TCP 检测，会把正常节点读成“服务不可用”。选择不发送检测并显示“不适用”。未选：只测对照端口，这样不能说明 UDP 端口本身的情况。
- **`unconfirmed` 算封锁状态：** 它同样要连续两轮确认，也会触发告警。节点确实从中国连不上，只是原因未定，不告警会漏掉这类故障。
- **`service_down` 立即生效：** 从封锁变为服务不可用时会发送一条“不再处于封锁状态”的消息，正文写明当前状态。继续显示封锁会与事实不符。
- **`partial` 的优先级：** “多数探测点连接成功”和“某运营商失败”可能同时成立。选择只要有运营商整体失败就算 `partial`，因为这一信息对线路更有用。
- **告警路径：** 沿用费用提醒的插件表和投递方式，不写入 `server_alert_events`，所以这些事件不显示在「告警事件」页，而是显示在本功能页面。
- **接口仅限所有者：** 任务要求管理员可用。由于页面包含 Nexus 清单且能决定地址外发，选择更严格的所有者会话，只读管理员和 API 令牌不可用。
- **界面位置：** 「监控告警」组已有四个入口，达到功能地图的上限，因此作为「延迟检测」的第二个视图，地址为 `/#/latency/reachability`。

## OpenRC 上 Agent 升级停掉运行时（2026-11-05）

- 现象：Agent 0.3.4 → 0.3.5 自动更新时，三台 Alpine 主机（aliyun-hk1/hk2/hk3）的运行时被停掉 2–4 分钟。原因是 `SystemOps::execute` 执行 `rc-service` 时没有隔离进程组，OpenRC 的 `supervise-daemon` 留在 Agent 工作进程的进程组里，升级时 supervisor 对该进程组发 SIGTERM。systemd 主机不受影响。

- 没做：让 Agent 在同一版本的运行时停止时自动 `start`。这会改变「同版本轮询不重启运行时」的约定，也会推翻管理员有意的停止；需要单独决定。现在的恢复办法是在主机上手动 `rc-service apsp-singbox@main start`，见 [设备平台与能力](platforms.md#openrc)。

## 原权限组并入策略组（2026-11-06）

用户要求把已有数据里套餐对应的权限在策略组里做好，即路线图 1.3。按无需审核的约定自行决定，见 [ADR 0115](adr/0115-original-permission-groups-as-policy-groups.md)。

- **订阅一条都不变**：迁移线路进入策略组，但 `singbox_desired_accesses` 排除它们，策略组不会写 `accesses` 或生成新 UUID；运行时仍下发 `legacy_uuid`。用 2026-11-05 16:51 UTC 的生产备份在本地核对，迁移前后的发布成员、成员摘要、设备预算、门户可用性、诊断与兼容桥记录逐字节相同。
- **成员一次性落成，不随套餐变动**：迁移时按当前套餐的映射放进对应组，到期用户也放进去（续期后线路照旧）。之后线路只看策略组，修改套餐不再改变线路；这与 ADR 0112“策略组决定节点、套餐决定额度”一致。没有选“成员由套餐动态推导”，那样策略组只是只读视图，两套权限仍在。
- **原面板的组号由策略组推出**：原面板每个用户只有一个 `group_id`。取用户所在、对应原组的策略组中套餐映射的那一个，否则组号最小的，都不在则为空。用户同时在多个原组时，原面板只列其中一个组的线路；完整的多组订阅等路线图 1.4 由 apsp 生成订阅。
- **迁移线路可以放进任何策略组**：只对有原身份的迁移用户生效，自建用户在这类组里拿不到这些线路；界面在编辑原权限组时说明。把迁移线路放进非原组的策略组，apsp 会接受这些用户的连接，但原面板生成的订阅不会列出，直到 1.4。
- **`PATCH /nexus-nodes/{id}/groups` 保留**：仍用于记录原面板上改过的组，同时把已接管线路移入或移出对应的原组策略组（不动管理员自建的组），不再要求原组先有套餐映射，缺少的原组策略组按需创建。它没有界面，日常编辑只在策略组里。
- **暂停接管主机上的线路也在组里**：它们由原面板运行，在编辑框中显示为“迁移线路，所在主机目前由原面板运行”，可以保留或取消，不按“已不可用”阻止保存；恢复接管后按组授权。
- **诊断保留“订阅由原系统提供”**：订阅确实仍由原面板生成，去掉这条说明要等 1.4。诊断的依据改为策略组，并标出“原面板会列出但策略组未授权”的已接管线路。
- **原面板的 `v2_server.group_ids` 不同步**：在 apsp 里把迁移线路移出原组策略组后，原面板的订阅仍会列出这条线路，但连接会被拒绝；诊断会标出。兼容桥不写服务器表，这一差异留到 1.4/1.5 一并消除。

## 阿里云更换公网 IP（2026-10-30 起草，2026-11-06 完成）

用户在 2026-10-30 要求把换 IP 脚本做成功能并释放旧 IP，起草版本未合并；2026-11-06 用户说“继续”后移植到当前主线，决定见 [ADR 0116](adr/0116-alicloud-eip-rotation.md)。

- **判断方式与失败动作（起草时）**：用 Globalping 中国探针做 TCP 握手，排除阿里云内网探针，初筛加复测；证据不足或全部不通时绑回原地址，只有复测通过才释放旧地址。未选自动发现被封并自动换 IP（误判会释放地址，且 IP 变化影响所有客户端）、自建国内探针（增加部署负担）、换绑 ECS 固定公网 IP（阿里云不支持，转换为 EIP 也会改变计费）。
- **入口与记录**：按「阿里云 CDT」页重排后的结构（每个事实一次、操作进「资源操作」菜单、历史只有一份），入口是资源菜单里的「更换公网 IP」，进度和结果是「操作记录」中的一条，结束通知并入这一条；不再单独设「公网 IP 更换记录」面板。
- **不持锁调用云端**：沿用第三轮性能整理（#224）的规则，每一步在没有事务时调用云端，保存时只在 `version` 未变时写入。代价是同一步可能在崩溃或冲突后重做；每一步都按云端现状决定动作、申请沿用已保存的令牌，所以重做不会多申请或误释放。
- **账户刷新与快照**：进行中跳过这台实例的快照，避免显示即将释放的候选；结束时由流程写入最终地址，`checked_at` 取保存时刻，早先开始的刷新不会覆盖。待人工核对时恢复刷新，便于核对。
- **共享带宽的计费方式**：生产 EIP 在共享带宽中，接口可能报告共享带宽的 `PayByDominantTraffic`，不能用来申请 EIP。选择在共享带宽中不检查旧地址的计费方式，新地址按流量计费申请后加入同一共享带宽（与真实执行过的脚本一致）。未选“拒绝共享带宽中的 EIP”（等于功能对生产不可用）和“照抄报告的计费方式”（申请会被拒绝）。
- **再次验证**：确认、取消和结束核对由请求守卫的阿里云高风险规则统一要求证明（ADR 0108），处理函数不再重复检查；预览只读，与其他预览一致不要求证明。
- **IP 变化的下游**：插件之间不互相依赖，不由阿里云插件改写代理节点地址。Agent 上报地址、域名解析和本页快照自动跟随；节点公开地址写成旧 IP 的需要手动更新，已更换的记录直接链接到关联服务器的节点列表。
- **互斥**：沿用“资源空闲”检查，进行中或待核对的更换让变配、各类启停（含 CDT 守护）、安全组调整和移除登记等待；另外禁止把涉及的 EIP 单独登记。待核对时 CDT 守护也会等待，与其他待核对操作的现有规则一致，因此结束通知明确要求尽快人工处理。

## 2026-11-07：S-UI 对齐的边界选择

- 地区分组采用节点名称包含词数组（如「香港」「HK」），不通过额外在线 IP 定位猜测地区；同一规则在订阅生成时重新筛选当前可用授权。
- 连接列表和批量断开每服务器每次最多 256 条，超出显示截断，允许分批操作；请求绑定应用版本和认证主体，不使用来源 IP 代替用户身份。
- 证书复用为同机配置快照与同配置提供方共享。来源配置编辑不隐式修改所有关联节点；避免跨服务器传播 DNS 凭据。
- FreeBSD 上游没有对应 Cronet 库，因此不承诺 Naive 出站；其他平台依各自构建条件启用。真实提供方与跨平台部署以单独验收记录为准。
