# 流量 outbox 有界读取独立验收

对应第 1 步 P0「有界读取」与 [Issue #18](https://github.com/theLucius7/apsp/issues/18)。本次只处理 Agent 的流量账本读取、批次大小和传输调度；独立提交、独立 PR。

## 行为与预算

- `pending_usage()` 在 SQL 中先选最多 **64** 个可发送批次，再按全局序号取累计字节预算内的前缀。单轮 usage 消息总预算为 **1,048,575 字节**，包含每条消息预留的 128 字节 envelope；读取和反序列化只发生在这个前缀内。
- SQLite 使用 `octet_length(batch)` 读取字节元数据，不把超限正文读进 Rust。待确认序号排序和字节索引采用可重复执行的增量索引创建，保留 `user_version=1`，让试运行失败后的旧 Agent 能重新打开账本；原有批次、身份、ACK 和累计基准不改写。
- 新样本按 **128 KiB** 消息预算切批，并保持每批不超过 10,000 条记录。所有切批、全局序号和累计基准在同一事务中落盘；其中一批失败就整体回滚。`sample_usage()` 返回第一批，完整样本始终由持久 outbox 重放。
- 仍按 15 秒周期启动发送轮次，每轮允许连续调度最多 1 秒。每条 usage 消息发送后主动让出执行权，输入、心跳和控制消息在下一轮 `select` 中优先处理；尚未发送的窗口留到下一发送轮。正在进行的一次 socket 写入保留原有 10 秒超时，所以 1 秒是批次调度预算，不是整个连接循环的硬截止时间。
- 旧超限批次保留原文和 `(epoch, seq)`，不伪造 ACK、不阻塞后续可发送批次，也不令连接因消息过大而反复断开。日志明确报错；本地 `apsp-agent status` 中 `oversized_usage_batches` 和 `usage_outbox_error` 可见。待确认总数仍包含它们，退役流程会继续等待实际对账。

面板按 `(server_id, epoch, seq)` 及正文摘要幂等入账，没有连续序号要求，因此跳过无法传输的旧超限批次后，后续批次仍能准确入账。旧超限批次的恢复必须另行核对面板账本；直接改写相同身份、删除或手动确认可能破坏已入账数据，本 PR 不宣称恢复了这部分历史账本。

## 自动验收

在仓库根目录执行；数据库地址使用自己的隔离 PostgreSQL 测试库，角色需可创建测试数据库。

```sh
export APSP_RELEASE_PUBLIC_KEYS="$(cat crates/protocol/tests/fixtures/public-keys.json)"
cargo fmt --all --check
cargo clippy --locked --all-targets -- -D warnings
DATABASE_URL='<测试数据库地址>' cargo test --locked
```

专项入口：

```sh
cargo test --locked -p apsp-agent-core --test usage --test usage_bounds
cargo test --locked -p apsp-agent-core \
  backlog_and_legacy_giant_preserve_heartbeat_control_ack_and_restart_replay
```

| 场景 | 验收断言 |
| --- | --- |
| 4,096 批积压 | 每次最多 64 批；按完整 `u64` 序号排序；下一窗口之外的无效正文不被解析 |
| 混合大小批次 | 累计 envelope 字节受限；只返回有序前缀；首批大于新切批目标但仍能发送时继续前进 |
| 2 MiB 旧超限正文 | 正文不被解析；原文与未确认身份保留；后续批次可以发送、ACK；重开数据库仍显示阻塞计数 |
| 新的巨大样本 | 全部记录精确保留；每批 wire 大小不超过 128 KiB；多个窗口持续前进；重启与相同累计样本不重复计量 |
| 切批后续序号耗尽或写入失败 | 之前已插入的切批、序号和累计基准整体回滚；再次采样仍保留完整增量 |
| Agent 数据库重开、面板断连 | 回环真实 WebSocket 握手与两次连接；丢 ACK 批次原样重传；已 ACK 的第一批不再出现 |
| 心跳与 ACK 控制 | 4,096 批积压及旧超限正文同时存在时，20 秒心跳持续；两轮各 64 批且均受字节预算限制；ACK 在下轮生效 |
| 旧 SQLite 升级与回滚 | schema 1 保持不变，增量索引加入后旧 Agent 的迁移仍能打开账本；既有批次原样重传，排序查询使用有界读取的索引 |

403、429、查询超时、诊断取消和部分诊断报告的实现不在这个 PR 内，后续对应项需要自己的测试。这里的失败重试针对 usage ACK 与 WebSocket 断连。

## 专用 Debian 12 节点验收

以下需要专用测试节点，不能用本机回环测试替代：

1. 使用小内存节点，暂停专用测试面板连接并持续产生可核对的代理流量；记录 outbox 数量、Agent RSS、最后心跳时间。恢复连接后核对流量总和、心跳连续性和 64 批/字节预算。
2. 在独立的小磁盘测试目录复现 SQLite 写入不足；释放测试空间后核对未成功事务没有提前推进基准，下一样本完整入账。自动测试的 SQL 触发器模拟写入失败，只验证原子性。
3. 保持持续代理流量，分别重启 Agent、临时断开面板；恢复后核对 ACK 去重、累计总和和服务 PID。该 PR 不修改运行时生命周期。
4. 完整验机过程中重复步骤 1、3，并记录资源、心跳和运行时是否被杀。资源预算、采集解耦、取消清理和完整验机本身分别由后续 PR 验收。

本 PR 的自动测试证明有界读取、调度和账本恢复；小内存/磁盘不足实机及完整验机持续流量验收仍待专用测试节点完成。
